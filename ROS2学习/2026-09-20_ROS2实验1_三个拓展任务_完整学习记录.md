## 2. 拓展一：50 Hz 高频通信与两种 QoS 对比

### 2.1 问题动机：发布成功 ≠ 订阅者必定处理成功

基础实验只验证了低频消息可以发布和接收。高频下，消息可能因发送端调度、传输、接收缓存或回调处理等环节出现延迟或缺失。老师要求对照两种 **QoS（Quality of Service，服务质量）** 可靠性策略，观察相同目标发布频率下的实际接收表现。

**QoS 是消息如何传输与缓存的规则集合**；这次使用的设置包括可靠性策略、历史缓存策略与深度。

### 2.2 RELIABLE 与 BEST_EFFORT 分别是什么

| 项目 | `RELIABLE`（可靠传输） | `BEST_EFFORT`（尽力而为传输） |
|---|---|---|
| 主要语义 | 通过可靠性交付机制尽量保证数据到达 | 尽力发送，不保证每条消息都成功到达 |
| 未成功交付 | 底层可使用确认、重传等机制 | 不提供可靠性重传保证 |
| 可能结果 | 在缓存有限、负载过高、节点停止等条件下，应用仍可能缺消息 | 即使没有可靠性重传，在良好链路中也可能连续收到全部消息 |
| 工程选择 | 考虑完整性、延迟与额外可靠性开销 | 常用于更重视新鲜度、能容忍丢失个别样本的数据流 |

**不能把它们记为“RELIABLE 一定不丢、BEST_EFFORT 一定丢”，也不能直接记为“BEST_EFFORT 一定更快”。** QoS 是机制选择；实际接收率和缺失数量必须实验测量。

另外，本实验仍使用：

```python
history=HistoryPolicy.KEEP_LAST
depth=10
```

它表示历史策略仅保留最近的有限条消息。**RELIABLE + KEEP_LAST(10) 不代表新 Subscriber 上线时会自动收到此前全部历史消息**；不能把它当作永久存储。未专门配置历史持久性策略时，本次实验中晚启动的 Subscriber 不应被假设能补齐发布者早先的所有消息。

### 2.3 QoS 兼容性：我们曾经特别检查的坑

基础 Subscriber 用整数 `10` 作为 QoS 参数，默认请求可靠传输。若把 Publisher 改为 `BEST_EFFORT`，但 Subscriber 仍请求 `RELIABLE`，可靠性 QoS **不兼容**，可能完全收不到数据；这不是高频下的“偶发丢包”。

本次对照采用：

```text
实验 A：RELIABLE Publisher → RELIABLE Subscriber
实验 B：BEST_EFFORT Publisher → BEST_EFFORT Subscriber
```

**更准确的兼容性理解：** BEST_EFFORT Publisher 不能满足 RELIABLE Subscriber 的请求；反过来，RELIABLE Publisher 能满足 BEST_EFFORT Subscriber 的可靠性需求。这次两端设置相同，是为了对照直观，而不是因为所有 QoS 参数必须完全相同。

### 2.4 为什么 `0.02 s` 对应 `50 Hz`

设定定时器周期 `T` 后，理想发布频率 `f` 为：

\[
 f = \frac{1}{T}
\]

因此，`T = 0.02 s` 时：

\[
 f = \frac{1}{0.02} = 50\ \mathrm{Hz}
\]

Publisher 原来的：

```python
self.timer = self.create_timer(0.5, self.timer_callback)
```

改为：

```python
self.timer = self.create_timer(0.02, self.timer_callback)
```

**目标频率**是 50 Hz，但 Timer 到期只是让回调具备执行条件；实际执行受 Executor 与系统调度影响，仍需测量。

### 2.5 先测 RELIABLE 组实际频率

保持两端 `RELIABLE`，编译并启动学生节点后：

```bash
ros2 topic hz /lab1/student_msg
```

实际截图：

```text
average rate: 49.999 / 50.000 Hz
min: 0.019s
max: 0.021s
std dev: 约 0.00010–0.00011s
```

**读数意义：** `ros2 topic hz` 自身会建立一个临时订阅者，因此它直接测量的是**该命令行订阅者实际收到消息的间隔/频率**，不是 Publisher 内部 Timer 执行频率；接收频率接近 50 Hz 也不足以独立证明“没有任何消息缺失”。

### 2.6 为何要增加“消息序号缺失”统计

原代码的：

```python
self.received_count += 1
```

只能记录 Subscriber 自己实际处理了多少条消息。Publisher 可能先启动，因此不能简单用“发布端累计序号 − 接收端累计数量”算丢包。

我们利用原消息格式：

```text
学号: 2025302201003, 计数: 125
```

先提取其末尾的序号，再比较**连续两次实际收到的序号**：

```text
Publisher 理想序号：100, 101, 102, 103, 104
Subscriber 收到：  100, 101,      103, 104
                                    ↑
                         102 未被观察到
```

当上一条为 `last_seq`、当前为 `current_seq` 时：

\[
 \mathrm{gap} = \mathrm{current\_seq} - \mathrm{last\_seq} - 1
\]

例如从 `101` 跳到 `104`，就有 `104 − 101 − 1 = 2` 个未观察到的序号，即 `102` 和 `103`。

### 2.7 实际增加的 Python 代码与逐行含义

在 `StudentSubscriber.__init__()` 的接收计数器下面增加：

```python
self.received_count = 0   # 当前进程实际处理的消息数
self.last_seq = None      # 还未收到首条消息，因此上一序号未知
self.lost_count = 0       # 本次观测到的序号缺失累计值
```

`message_callback()` 使用本次实际编写的逻辑（仅做换行排版）：

```python
def message_callback(self, msg):
    # 每收到一条消息，实际接收数 +1
    self.received_count += 1

    # 从固定消息格式的字符串里提取序号
    current_seq = int(msg.data.rsplit("计数:", 1)[1].strip())

    # 从第二条实际收到的消息起，判断相邻序号是否连续
    if self.last_seq is not None:
        gap = current_seq - self.last_seq - 1
        if gap > 0:
            self.lost_count += gap
            self.get_logger().warn(
                f'发现序号缺失：{gap} 条，'
                f'累计缺失：{self.lost_count} 条'
            )

    self.last_seq = current_seq
    self.get_logger().info(f'收到: {msg.data}')

    if self.received_count % 10 == 0:
        self.get_logger().info(
            f'累计接收: {self.received_count} 条，'
            f'累计序号缺失: {self.lost_count} 条'
        )
```

**Python 新知识回顾：**

- `msg.data`：`String` 消息中的普通 Python 字符串。
- `rsplit("计数:", 1)`：从右边按 `计数:` 最多分割一次；`[1]` 取得其后半段。
- `.strip()`：去掉字符串首尾空白；`int(...)`：将数字文本转换成整数，才能做减法。
- `None`：尚无有效值；`is not None`：第一条实际接收消息只用于建立起点，不计算之前尚未监听的序号。
- `gap > 0`：只有当前序号比上一序号至少大 2 时，才增加缺失计数。
- `self.last_seq = current_seq`：每次更新比较基准。
- `% 10 == 0`：实际接收数每达到 10 的整数倍时额外打印统计。

**方法边界：** 这是应用层**序号缺失数量**，不能凭它判断缺失具体发生在传输链路、有限队列、Executor 调度还是其他环节；尚未等到下一条消息时，也无法直接发现观测区间末尾缺失。这里还默认单一 Publisher 序号单调递增、没有重启复位或重排；如果换实验组，先停止旧节点再重启，以免混淆不同批次。

### 2.10 两组对照数据与结论

| 对比项 | RELIABLE → RELIABLE | BEST_EFFORT → BEST_EFFORT |
|---|---:|---:|
| 目标频率 | 50 Hz | 50 Hz |
| `ros2 topic hz` 截图读数 | 约 49.999–50.000 Hz | 约 49.999–50.001 Hz |
| 截图时学生订阅者累计接收 | 8340 条 | 2490 条 |
| 同一截图阶段的累计序号缺失 | 0 条 | 0 条 |

**现象：** 在本次本地容器环境及截图对应的观测阶段，两个配置都能以约 50 Hz 接收，未观察到消息序号缺失。  
**原因分析：** 当前链路与系统负载下没有显现由可靠性策略带来的接收频率或序号完整性差异；“BEST_EFFORT 不保证交付”并不意味着每次测试都一定产生缺失。  
**结论：** 两种 QoS 在本次测试条件下都实现了接近 50 Hz 的接收；实验未证明它们具有相同的可靠性交付机制，也未证明某一策略在所有条件下都更快。

**注意：** 这两组截图的运行时长不同，`8340` 与 `2490` **不可直接当作“同时间窗口吞吐量”比较**，更不能用两组累计接收数的差来算丢包。老师本次要求的基础对照已完成，因此没有额外重做统一时长测试。

### 本板块自测

**问：** 如果发布端设为 BEST_EFFORT，订阅端仍要求 RELIABLE，而订阅者完全收不到消息，能否将其写成“50 Hz 高频导致严重丢包”？  
**答：** 不能；应先排查 QoS 兼容性。BEST_EFFORT Publisher 不能满足 RELIABLE Subscriber 的可靠性请求，这与消息过快而偶发缺失是不同问题。

## 3. 拓展二：一个 Publisher 与三个 Subscriber 协作

### 3.1 为什么多订阅者不是“每人分走一部分消息”

ROS2 Topic 的发布—订阅机制允许**多个独立的订阅者各自接收同一个话题的数据**。它不是默认把消息轮流派发给不同 Subscriber 的工作队列。

```text
                     /student_publisher
                              │
                              ▼
                      /lab1/student_msg
                              │
                  ┌───────────┼───────────┐
                  ▼           ▼           ▼
   /student_subscriber_a   ..._b       ..._c
```

每个订阅者实例拥有自己的 `received_count`、`last_seq` 和 `lost_count`，所以可独立处理、独立统计；三个进程即使执行同一个 Python 文件，也不是共用同一份计数器。

### 3.2 实施：复用已完成的 Subscriber，不复制三份源代码

停止之前的单个 Subscriber，保留一个 Publisher。三个终端分别启动同一可执行程序，并通过 ROS2 参数重映射改名：

```bash
# 终端 A
ros2 run lab1_topics student_subscriber --ros-args -r __node:=student_subscriber_a

# 终端 B
ros2 run lab1_topics student_subscriber --ros-args -r __node:=student_subscriber_b

# 终端 C
ros2 run lab1_topics student_subscriber --ros-args -r __node:=student_subscriber_c
```

如果新终端未加载工作空间，先执行 `source /home/student/install/setup.bash`。

`--ros-args` 引入 ROS2 命令行参数；`-r __node:=...` 对本次运行的**节点名称进行重映射**。它并未修改 Python 源文件，也未改变订阅话题。此次复用了前一阶段最后编译出的 BEST_EFFORT 版本。

### 3.3 两种验证：节点列表 + 通信拓扑

使用：

```bash
ros2 node list
```

实际可见：

```text
/student_publisher
/student_subscriber_a
/student_subscriber_b
/student_subscriber_c
```

另外还出现 `/rosapi`、`/rosapi_params`、`/rosbridge_websocket` 等实验网页平台自己的节点，不属于这四个学生节点。

在仿真桌面使用 `rqt_graph` 刷新，可看到 `/student_publisher` 通过同一个 `/lab1/student_msg` 连到三个订阅者；截图中三个箭头不是三份不同的消息源，而是同一个话题上的三个订阅连接。

### 3.4 多终端同时观察的真实结果

终端分屏截图中，三个 Subscriber A、B、C 都分别出现了：

```text
计数: 31328
计数: 31329
计数: 31330
```

**证明：** 在截图覆盖的这些序号上，三名订阅者都独立收到了相同的发布消息；不是 A 收到 31328、B 只收到 31329、C 只收到 31330。

三者的“累计接收数量”即使不同，也不自动表示通信错误：启动时刻可能不同，后续各自的调度和消息处理也相互独立。

### 3.5 一个不能忽略的后续现象：Subscriber A 累计缺失 1125 条

同一张多终端长时间运行截图里，Subscriber A 曾输出：

```text
累计接收: 29600 条，累计序号缺失: 1125 条
```

这与前面 **BEST_EFFORT 组较早测量时的 `2490 条接收、0 条缺失` 是不同运行阶段的结果**，不能在报告或复习时把它们误合成一条数据。三个订阅者在截图中的连续相同序号，证明多订阅者模型成立；A 的长时间累计缺失则说明独立订阅者在另一观测阶段可能出现序号缺口。

**该截图不能单独证明 1125 条均为网络传输层丢包，也不能把缺失归因于“增加多个订阅者”或“BEST_EFFORT 必然丢包”。** 终端逐条打印、队列缓存、系统负载等都可能影响应用层观测，但本次没有做进一步隔离变量的专项测试。

### 本板块自测

**问：** 三个 Subscriber 都订阅 `/lab1/student_msg`，它们各自打印的 `received_count` 不相等，是否说明 Topic 把消息平均分给了三个人？  
**答：** 不是。`received_count` 是各自进程启动后处理的消息数量；对照共同收到的 `msg.data` 序号，才能验证他们在相同发布消息上是否都有接收。

## 4. 拓展三：Launch 一键启动两个学生节点

### 4.1 动机：以前的启动方式不便于多节点系统

基础实验需要分别在不同终端执行：

```bash
ros2 run lab1_topics student_publisher
ros2 run lab1_topics student_subscriber
```

**Launch（启动管理机制）** 用一个启动描述文件集中声明多个节点及其参数，让 `ros2 launch` 统一管理启动和退出。它不替代 Topic，也不负责“转发消息”；原有 Publisher / Subscriber 仍使用原来的通信逻辑。

### 4.2 先阅读老师现有的 Launch 示例

上传的现有示例文件内容以 Demo 节点为对象：

```python
from launch import LaunchDescription
from launch_ros.actions import Node


def generate_launch_description():
    return LaunchDescription([
        Node(package='lab1_topics', executable='demo_publisher',
             name='demo_publisher', output='screen'),
        Node(package='lab1_topics', executable='demo_subscriber',
             name='demo_subscriber', output='screen'),
    ])
```

这里 `generate_launch_description()` 是 Python Launch 文件约定的入口函数；返回的 `LaunchDescription` 描述将被启动的节点；每个 `Node` 包含：

| 参数 | 意义 |
|---|---|
| `package` | ROS2 包名，本工程实际为 `lab1_topics`，不是课堂 PPT 示例中的 `lab1_pkg` |
| `executable` | 在该包中已安装、可执行的程序名 |
| `name` | 节点运行时的 ROS 名称 |
| `output='screen'` | 让进程输出显示到启动终端，方便观察 |

**Python 细节：** `LaunchDescription([Node(...), Node(...)])` 将两个启动动作放进一个列表；`return` 把这份启动计划交还给 Launch 系统；它不是逐行手动运行两次 `ros2 run`。

### 4.3 新建学生专用 Launch 文件，不覆盖老师的 Demo

在 `/home/student/src/lab1_topics/launch/` 新建：

```text
student_topics.launch.py
```

实际实现的核心结构：

```python
from launch import LaunchDescription
from launch_ros.actions import Node


def generate_launch_description():
    return LaunchDescription([
        Node(
            package='lab1_topics',
            executable='student_publisher',
            name='student_publisher',
            output='screen',
        ),
        Node(
            package='lab1_topics',
            executable='student_subscriber',
            name='student_subscriber',
            output='screen',
        ),

```

老师 PPT 用的是示例包名和文件名，实际执行时以本工程已有的 `lab1_topics` 包、`student_publisher`、`student_subscriber` 为准。

### 4.4 为什么需要检查 `CMakeLists.txt` 而不是只写 Launch 文件

`ros2 launch` 需要从已安装的 ROS2 包共享目录找到 Launch 文件。上传的真实 `CMakeLists.txt` 中已有：

```cmake
install(DIRECTORY launch
  DESTINATION share/${PROJECT_NAME})
```

意味着编译安装时，源代码中的 `launch/` 目录会被安装到该功能包的共享资源目录。真实 `CMakeLists.txt` 也已通过 `install(PROGRAMS ... RENAME student_publisher)`、`RENAME student_subscriber` 安装两个 Python 可执行程序。因此，**本次无需修改 `CMakeLists.txt` 或 `package.xml`**；新文件保存、重新编译并加载环境即可。

不要混淆两个路径的用途：

```text
lib/lab1_topics/          → ros2 run 寻找节点可执行文件
share/lab1_topics/launch/ → ros2 launch 寻找启动描述文件
```

## 8. 今日学习后的整体理解

### 8.1 三个拓展解决的是三个不同的问题

```text
QoS 对比        → 同一个 Topic 上，消息采用什么传输可靠性规则？
多订阅者协作    → 一个话题能否被多个独立节点同时接收并各自处理？
Launch 一键启动 → 如何集中声明并启动组成实验系统的多个节点？
```

它们处于不同层次：**通信策略 → 通信拓扑 → 系统启动管理**。Launch 不改变 QoS；三个 Subscriber 不需要修改 Publisher 的消息格式；QoS 也不决定 Launch 是否能找到节点可执行文件。

### 8.2 复习用最短操作链

```bash
# 进入容器网页版 VS Code 终端后，从工作空间编译
cd /home/student
colcon build --packages-select lab1_topics
source install/setup.bash

# 拓展一：单独启动 Publisher + Subscriber，再测接收频率
ros2 topic hz /lab1/student_msg

# 拓展二：另外三个终端以不同名字启动同一 Subscriber
ros2 run lab1_topics student_subscriber --ros-args -r __node:=student_subscriber_a
ros2 run lab1_topics student_subscriber --ros-args -r __node:=student_subscriber_b
ros2 run lab1_topics student_subscriber --ros-args -r __node:=student_subscriber_c
ros2 node list

# 拓展三：先 Ctrl+C 停止旧的学生节点，再一键启动
ros2 launch lab1_topics student_topics.launch.py
```

上面**不是要求在同一个终端按顺序运行所有长驻命令**；`ros2 run` / `ros2 launch` 会持续运行，应在各自终端启动，切换任务前先停止旧节点。操作时检查当前版本的 QoS，避免把前一阶段遗留的 Publisher / Subscriber 混进新实验。

### 8.3 目前已经掌握 / 暂不深入

已能够解释并实际验证：`50 Hz ↔ 0.02 s`；两种 Reliability Policy 的语义；QoS 两端兼容性；`ros2 topic hz` 测量范围；用 Python 从 `String.data` 提取序号；用 `last_seq` 识别缺口；单 Topic 的多订阅者模型；`--ros-args -r __node:=...`；Python Launch 的 `LaunchDescription`、`Node`；CMake 对 Python 可执行文件与 `launch/` 的安装位置。

尚未做专项实验：不同系统负载、不同消息大小下的 QoS 定量性能比较；消息队列溢出与底层传输损失的精确区分；统一时长、多次重复试验的置信统计；复杂 Launch 参数与生命周期管理。这些不是本次课堂拓展的完成前提。

**今日一句话总结：** 在已完成的基础 Topic 通信上，使用 50 Hz 与序号统计验证了两种 QoS 的实际表现，使用三个独立 Subscriber 观察了话题的一对多分发，并通过复用已有包配置实现 Launch 一键启动；同时学会把不同时段的数据分开记录，并在停止 `--rm` 容器前做好代码备份。
