## 4. 题目 5：为什么要从 `HAL_Delay()` 改成非阻塞调度

之前流水灯常见写法：

```c
led_on(0U);
HAL_Delay(250U);
led_off(0U);
HAL_Delay(250U);
```

这种写法逻辑直观，但会阻塞 CPU。

程序执行到：

```c
HAL_Delay(250U);
```

后，需要等 250 ms 结束才能继续向下运行。

如果灯效正在 Delay 时：

```text
signal = 1
```

突然变成：

```text
signal = 3
```

程序不会立刻处理新的模式，而要先等旧 Delay 结束。

因此题目 5 要求改成：

```text
执行动作
↓
记录开始时间
↓
立即返回主循环
↓
每轮查询时间有没有到
↓
时间到了才执行下一步
```

这就是今天最核心的概念：

> **非阻塞不是“不需要时间”，而是不让 CPU 停在一个位置等时间过去。**

## 5. `HAL_GetTick()` 的作用

`HAL_GetTick()` 可以返回系统启动以来经过的毫秒数。

例如：

```text
程序运行到某一时刻：
HAL_GetTick() = 1000
```

过 250 ms：

```text
HAL_GetTick() = 1250
```

因此可以通过：

```c
HAL_GetTick() - start_tick
```

计算已经过去多久。

相比：

```c
HAL_Delay(250U);
```

区别是：

```text
HAL_Delay()
→ 直接在这里等待

HAL_GetTick()
→ 只是读取当前时间
→ 程序可以继续执行其他逻辑
```

## 6. 软件计时器 `timer_t`

为了避免每个模式都单独保存“开始时间、持续时间、是否有效”，今天把这些状态封装进结构体：

```c
typedef struct
{
    uint32_t start_tick;
    uint32_t duration_ms;
    uint8_t active;
} timer_t;
```

### 6.1 `start_tick`

记录本次计时从什么时候开始。

### 6.2 `duration_ms`

记录本次需要等待多少毫秒。

### 6.3 `active`

记录当前这次计时是否仍然有效。

因此一个 `timer_t` 就可以完整描述：

```text
何时开始
+
等待多久
+
当前是否正在计时
```

---

## 7. `timer_start()`：启动一次计时

```c
static void timer_start(timer_t *timer, uint32_t duration_ms)
{
    timer->start_tick = HAL_GetTick();
    timer->duration_ms = duration_ms;
    timer->active = 1U;
}
```

例如：

```c
timer_start(&led_timer, 250U);
```

实际发生：

```text
led_timer.start_tick
→ 记录当前 HAL_GetTick()

led_timer.duration_ms
→ 250

led_timer.active
→ 1
```

之后不需要停下来等 250 ms。

---

## 8. `timer_expired()`：查询计时是否到期

```c
static uint8_t timer_expired(timer_t *timer)
{
    if (timer->active == 0U)
    {
        return 0U;
    }

    if ((HAL_GetTick() - timer->start_tick) >= timer->duration_ms)
    {
        timer->active = 0U;
        return 1U;
    }

    return 0U;
}
```

执行流程：

```text
计时器有效吗？
↓
如果无效
→ 返回 0

如果有效
↓
时间到了吗？
├─ 没到 → 返回 0
└─ 到了 → active 清零，返回 1
```

## 9. One-shot Timer 单次触发语义

今天专门理解了：

```c
timer->active = 0U;
```

为什么要在到期时执行。

如果没有这一步，那么时间一旦超过持续时间：

```text
250 ms
251 ms
252 ms
253 ms
...
```

每一轮 `timer_expired()` 都会认为已经到期，可能反复触发状态变化。

现在采用：

```text
第一次到期
↓
返回 1
↓
active = 0
↓
下一轮直接返回 0
```

只有重新：

```c
timer_start(...)
```

才开始下一次计时。

因此它是：

> **One-shot Timer：单次触发计时器。**

## 10. 对“软件计时器”的重要认知修正

学习过程中一开始容易把软件计时器理解成：

> 启动以后，它自己在后台执行一个循环。

后来明确：

```text
timer_t 不会自己运行
timer_start() 也不会创建新线程
timer_expired() 也不会主动被系统调用
```

真正不断运行的是：

```c
while (1)
{
    flow_led();
}
```

软件计时器只是保存状态。

主循环不停询问：

```c
timer_expired(&led_timer)
```

这才形成“计时效果”。

## 12. 为什么 IDLE 中不能每轮重新启动 Timer

今天讨论过：

> IDLE 中能不能每一轮都 `timer_start()`？

结论：不应该。

如果每一轮都重新启动：

```c
timer_start(&led_timer, 250U);
```

那么：

```text
start_tick 每轮都刷新
```

于是时间差几乎永远到不了 250 ms。

所以 IDLE 最合理的状态是：

```c
led_timer.active = 0U;
```

即当前没有需要推进的 LED 定时动作。

## 13. LED 状态机

为了记录灯效当前正在亮阶段还是灭阶段：

```c
typedef enum
{
    LED_STEP_ON = 0,
    LED_STEP_OFF
} led_step_t;
```

状态变量：

```c
static led_step_t current_step = LED_STEP_ON;
```

另外：

```c
static uint8_t current_led = 0U;
```

保存当前操作到哪一颗灯。

因此 LED 状态机的运行信息包括：

```text
current_led
→ 当前灯位置

current_step
→ 当前亮 / 灭阶段

led_timer
→ 当前阶段的时间状态
```

## 14. SINGLE 模式运行过程

进入 SINGLE 后：

```c
led_on(current_led);
timer_start(&led_timer, 250U);
```

初始：

```text
current_led = 0
current_step = ON
LED0 点亮
timer = 250 ms
```

如果 ON 阶段到期：

```c
led_off(current_led);
current_step = LED_STEP_OFF;
timer_start(&led_timer, 250U);
```

OFF 阶段到期后：

```c
current_led++;

if (current_led >= LED_COUNT)
{
    current_led = 0U;
}

led_on(current_led);
current_step = LED_STEP_ON;
timer_start(&led_timer, 250U);
```

形成：

```text
LED0亮
→ LED0灭
→ LED1亮
→ LED1灭
→ LED2亮
→ LED2灭
→ LED3亮
→ LED3灭
→ 回到 LED0
```

## 15. PAIR 模式

双灯模式采用相邻双灯滑动：

```text
LED0 + LED1
↓
LED1 + LED2
↓
LED2 + LED3
↓
回到 LED0 + LED1
```

PAIR 依然使用：

```text
ON
→ OFF
→ 下一组
→ ON
```

关键边界：

```c
if (current_led >= LED_COUNT - 1U)
{
    current_led = 0U;
}
```

因为要访问：

```c
current_led + 1U
```

所以 `current_led` 最大只能到倒数第二颗灯。

---

## 16. ALL 模式

ALL 模式：

```text
全部 LED 亮
↓ 250 ms
全部 LED 灭
↓ 250 ms
全部 LED 亮
```

依旧使用：

```text
current_step
+
led_timer
```

所以 SINGLE、PAIR、ALL 虽然视觉效果不同，但底层都使用同一套“状态 + 软件计时器”机制。

## 23. LED 与蜂鸣器能不能共用 `led_timer`

进入题目 6 后首先讨论：

> 能不能直接复用 `led_timer`？

自己正确判断：

> 不能，因为 LED 和蜂鸣器的时间不同，会互相覆盖。

例如 PAIR：

```text
LED：250 ms
蜂鸣器：200 ms ON / 800 ms OFF
```

如果两个功能共用同一个 `timer_t`，第二次 `timer_start()` 会覆盖第一次保存的：

```text
start_tick
duration_ms
active
```

因此最终采用：

```c
static timer_t led_timer;
static timer_t buzzer_timer;
```

今天形成一个重要工程认识：

> **可以复用同一套算法和函数，但不能把两个独立任务的运行状态强行放在同一个变量中。**

也就是：

```text
timer_start()
timer_expired()
→ 可以共用

led_timer
buzzer_timer
→ 必须分开
```

## 28. `const mode_config *` 的复习

今天专门确认：

```c
const mode_config *current_config;
```

表示：

```text
current_config 本身
→ 可以改为指向别的配置

通过 current_config 指向的数据
→ 不允许修改
```

所以：

```c
current_config = &pair_config;
current_config = &all_config;
```

合法。

进一步区分：

```c
mode_config * const p;
```

表示指针本身固定、目标数据可改；

```c
const mode_config * const p;
```

表示指针和目标数据都不可改。

```c
typedef enum
{
    BUZZER_STEP_ON = 0,
    BUZZER_STEP_OFF
} buzzer_step_t;
```

变量：

```c
static buzzer_step_t buzzer_step = BUZZER_STEP_ON;
```

用于记录蜂鸣器当前处于 ON 还是 OFF 阶段。

---

## 31. 为什么不能复用 LED 的 `current_step`

因为 LED 与蜂鸣器的节奏并不同步。

例如 PAIR：

```text
LED
→ 可能正在 250 ms 的 ON 阶段

蜂鸣器
→ 同时可能正在 800 ms 的 OFF 阶段
```

如果共用一个 step，两个状态机会互相覆盖。

因此：

```text
current_step
→ 只管理 LED

buzzer_step
→ 只管理蜂鸣器
```

与独立 Timer 的设计一致。

---

## 32. 模式切换时先清理旧蜂鸣器

在 `mode_init()` 中增加：

```c
buzzer_off();
buzzer_step = BUZZER_STEP_ON;
buzzer_timer.active = 0U;
```

含义：

```text
buzzer_off()
→ 立即关闭上一模式蜂鸣

buzzer_timer.active = 0
→ 上一模式计时作废

buzzer_step = ON
→ 下一次有效蜂鸣从 ON 阶段开始
```

这样从 PAIR / ALL 切到其他模式时，不会残留旧蜂鸣节奏。

## 33. `buzzer_step = BUZZER_STEP_ON` 放在哪里的讨论

这里今天有一次比较有价值的讨论。

最开始认为：

> IDLE 实际蜂鸣器是 OFF，如果公共部分写 `BUZZER_STEP_ON`，软件状态和硬件状态似乎矛盾。

随后自己提出：

> 任务 5 的 `current_step = LED_STEP_ON` 不也是在公共初始化部分设置的吗？

重新分析后确认：

> 可以统一放在 `mode_init()` 公共部分。

原因是 IDLE / SINGLE 下：

```text
buzzer_timer.active = 0
并且 buzzer_off()
```

所以 `buzzer_step = ON` 只是下一次有效调度的“初始阶段预置值”，并不表示蜂鸣器当前真的在响。

这个讨论也帮助重新认识：

> 状态变量描述的是调度阶段，不能脱离“该状态机当前是否有效运行”单独解释。

## 35. `buzzer_update()`：蜂鸣器独立状态机

随后决定创建：

```c
static void buzzer_update(void);
```

这里曾讨论：

> 是否一定要单独封装函数？

结论：

> 功能上可以直接写在 `flow_led()` 中，但独立函数更合理。

因为蜂鸣器已经拥有：

```text
buzzer_timer
+
buzzer_step
+
current_config
+
独立状态转换
```

本质上已经是一套独立状态机。

最终：

```c
static void buzzer_update(void)
{
    if (timer_expired(&buzzer_timer))
    {
        if (buzzer_step == BUZZER_STEP_ON)
        {
            buzzer_off();
            buzzer_step = BUZZER_STEP_OFF;
            timer_start(
                &buzzer_timer,
                current_config->beep.off_ms
            );
        }
        else
        {
            buzzer_on();
            buzzer_step = BUZZER_STEP_ON;
            timer_start(
                &buzzer_timer,
                current_config->beep.on_ms
            );
        }
    }
}
```

## 38. `buzzer_enable == 0` 时是否必须提前 `return`

最开始考虑在 `buzzer_update()` 中额外：

```c
if (current_config->buzzer_enable == 0U)
{
    return;
}
```

后来检查当前程序后发现：

```text

↓

↓

↓

```

```c
if (timer->active == 0U)
{
    return 0U;
}
```

> 直接依赖 `buzzer_timer.active`，保持代码简洁。

## 39. 最终 `flow_led()` 的整体职责

每次：

```c
flow_led();
```

大致执行：

```text
1. 保存 previous_mode
2. 根据 signal 更新 current_mode
3. 模式变化则 mode_init()
4. 根据 current_mode 推进 LED 状态机
5. 调用 buzzer_update()
6. 返回 main
```

因此 LED 与蜂鸣器并不是开了两个线程，而是：

> 主循环足够快地轮询两套独立状态机，使它们在表现上可以并行工作。

## 59. 今日总结

今天主要完成了 8.9 新任务中的题目 5 和题目 6。

题目 5 最大的变化，是把之前基于 `HAL_Delay()` 的阻塞式灯效改造成：

```text
HAL_GetTick()
+
软件 One-shot Timer
+
状态机
```

组成的非阻塞调度。

通过：

```c
timer_t
timer_start()
timer_expired()
```

把时间管理独立出来，再通过：

```c
current_step
current_led
current_mode
```

保存灯效当前运行到哪一步。

同时使用 `previous_mode` 检测 `signal` 对应模式是否变化，在变化时调用 `mode_init()` 清理旧状态并建立新状态，实现不依赖 Delay 的快速模式切换。

题目 6 则在题目 5 基础上继续增加蜂鸣器状态机。

没有重新设计另一套计时方法，而是复用：

```c
timer_t
timer_start()
timer_expired()
```

同时增加独立：

```c
buzzer_timer
buzzer_step
```

避免 LED 与蜂鸣器运行状态互相覆盖。

进一步通过：

```c
beep_config
mode_config
current_config
```

让：

```text
PAIR → 200 ms ON / 800 ms OFF
ALL  → 50 ms ON / 100 ms OFF
```

共享同一个 `buzzer_update()`，而不是复制两套蜂鸣器代码。

今天学习过程中还多次围绕已有实现进行讨论和修正，例如：

- Timer 是否应该共用；
- `mode_config` 是否真的需要；

- `buzzer_enable == 0` 是否需要提前 `return`；
