- `Lift` 对 `Motor_t` 的依赖注入；
- 位置模式 / 速度模式的实物验证。

因此今天不是重新设计 Motor，而是继续思考：

> **Motor 上面应该如何建立真正面向比赛机构和比赛任务的软件层。**

# 二、最开始的目标：从 Gripper 主线继续

开始时原计划主要围绕 **Gripper / 执行机构** 展开。

最初确认：

> 今天继续研究 Gripper 主线是合理的，不需要重新大改学习计划。

但随着对校内赛真实任务继续拆分，发现如果只单独讨论一个 Gripper，很容易局部设计正确、整体调用关系却不清楚。

因此今天主线发生了一个重要升级：

```text
单独设计 Gripper
↓
先分析完整比赛任务
↓
再拆 Task
↓
再拆 Mechanism
↓
最后决定各 Mechanism 需要什么执行器
```

这一转变是今天最重要的学习过程之一。

最终不再从“我需要几个电机、几个气缸”出发设计软件，而是从：

> **比赛到底要完成哪些完整任务？**

开始进行系统拆解。

# 三、首先确定：Task 和 Mechanism 不是一回事

今天首先建立了两个非常重要的软件层级。

## 1. Task

Task 表示：

> **一个完整的比赛任务。**

例如：

```text
获取方块
放置方块
获取灵石
放置灵石
```

Task 不直接控制电机。

Task 负责：

```text
多个 Mechanism
按照什么顺序执行
↓
等待哪个动作完成
↓
什么时候进入下一动作
```

---

## 2. Mechanism

Mechanism 表示：

> **一个职责相对独立的真实机械子系统。**

它有：

- 自己的执行器；
- 自己的状态；
- 自己的动作；
- 自己的完成条件；
- 自己的安全逻辑。

Mechanism 不是：

```text
一个电机 = 一个 Mechanism
```

也不是：

```text
一个完整比赛任务 = 一个 Mechanism
```

例如后来确定：

```text
BlockArm
= 两个耦合 Motor
+ 连杆机构
+ 吸盘末端位置控制
```

即使里面有两个电机，它仍然是一个 Mechanism。

---

# 四、从比赛任务出发拆出 4 个 Task

经过规则和机构需求分析，第一版正式保留四个核心 Task：

```text
1. PickBlockTask
   获取方块

2. PlaceBlockTask
   放置方块

3. PickBallTask
   获取灵石

4. PlaceBallTask
   放置灵石
```

对于掉落方块：

```text
重新获取掉落方块
```

当前不单独增加一个 Task。

第一版直接复用：

```text
PickBlockTask
```

只有以后真实机械证明“掉落方块”和“正常物资区方块”需要完全不同的动作流程时，再单独设计。

# 五、根据 Task 进一步拆分 Mechanism

最终确定四个 Mechanism。

---

## 1. BlockArm

组成：

```text
两个耦合 Motor
+
连杆机构
+
方块吸盘末端
```

职责：

> 控制方块吸盘末端移动到各固定业务工作位置。

包括：

```text
Pick
Safe
PlaceBottom
PlaceLevel1
PlaceLevel2
```

两个电机不是独立的：

```text
一个负责高度
另一个负责前后
```

这种简单关系。

而是通过机构耦合共同决定末端位置。

因此上层不直接分别指定两个电机，而只说：

```text
MoveToPick
MoveToSafe
MoveToPlace...
```

具体两个 Motor 的协调属于 BlockArm 内部。

---

## 2. BlockVacuum

职责：

```text
吸取方块
保持方块
释放方块
```

BlockVacuum 不负责末端移动位置。

它和 BlockArm 是两个独立 Mechanism：

```text
BlockArm
→ 把吸盘送到位置

BlockVacuum
→ 执行吸取 / 释放
```

---

## 3. BallGripper

机械组成：

```text
气缸
+
抓球爪
```

职责：

```text
Open
Grab
ReturnToDefault
```

不负责整个抓球机构的旋转。

---

## 4. BallRotaryAxis

机械组成：

```text
一个 Motor
+
旋转轴
+
整套 BallGripper
```

职责：

```text
MoveToPick
MoveToPlace
MoveToSafe
```

负责抓球机构整体角度。

---

# 六、形成 Task → Mechanism 的清晰关系

最终：

```text
PickBlockTask
├─ BlockArm
└─ BlockVacuum

PlaceBlockTask
├─ BlockArm
└─ BlockVacuum

PickBallTask
├─ BallGripper
└─ BallRotaryAxis

PlaceBallTask
├─ BallRotaryAxis
└─ BallGripper
```

这里进一步确认了两个重要认识。

### 一个 Mechanism 可以被多个 Task 复用

例如：

```text
BlockArm
```

既用于：

```text
PickBlockTask
```

也用于：

```text
PlaceBlockTask
```

---

### 一个 Task 可以多次调用同一个 Mechanism

例如 PickBlock：

```text
BlockArm_MoveToPick()
↓
BlockVacuum_Grab()
↓
BlockArm_MoveToSafe()
```

同一个 BlockArm 在一次 Task 中使用了两次。

因此模块划分不能按照“动作出现次数”拆文件。

---

# 七、第一版 Task 采用严格串行

今天明确确定：

> **第一版所有 Task 采用严格串行。**

也就是：

```text
动作 A
↓
明确完成
↓
动作 B
↓
明确完成
↓
动作 C
```

暂时不做：

```text
A 还没完全完成
B 就提前开始
```

原因：

- 容易调试；
- 容易确认状态；
- 安全边界清晰；
- 第一版先正确，再优化比赛效率。

后续可以再做：

```text
底盘运动 + 机构预定位
多个互不冲突 Mechanism 并行
多个 Task 并行
```

但这些都属于优化方向。

---

# 八、今天再次明确：函数返回不等于物理动作完成

这是今天所有 Task / Mechanism 状态机设计的基础。

例如：

```c
BlockArm_MoveToPick();
```

返回只是：

```text
“前往 Pick 的任务已经启动”
```

不是：

```text
“机械臂已经到 Pick”
```

真正流程：

```text
MoveToPick()
↓
state = MOVING
↓
Process() 周期运行
↓
读取反馈
↓
满足到位条件
↓
state = REACHED
```

Task 必须等待：

```c
BlockArm_GetState() == BLOCK_ARM_REACHED
```

才能进入下一步。

---

# 九、Task 状态机的关键写法

今天明确了一个非常重要的代码实现方式：

> **进入某个 Task 阶段时发一次动作命令，之后 Process 只等待完成状态。**

不能写成：

```c
case MOVE_TO_PICK:
    BlockArm_MoveToPick();    // 每个周期重新调用
```

否则可能不断：

- 重置运动计数器；
- 重置到位计数；
- 重新发送目标；
- 导致永远无法正常完成。

正确思想：

```text
Start()
↓
调用一次 BlockArm_MoveToPick()
↓
Task state = MOVE_TO_PICK
```

之后：

```c
case MOVE_TO_PICK:

    if (BlockArm_GetState() == REACHED)
    {
        BlockVacuum_Grab();      // 下一动作只发一次
        state = GRAB;
    }
    break;
```

这个思想以后会直接用于 Task `.c` 文件的 `switch-case`。

# 十四、BlockArm 的详细设计

这是今天设计最完整的 Mechanism。

## 1. API

```c
BlockArm_Init(Motor_t *motor_a, Motor_t *motor_b);

BlockArm_Home();
BlockArm_Stop();

BlockArm_MoveToPick();
BlockArm_MoveToSafe();

BlockArm_MoveToPlaceBottom();
BlockArm_MoveToPlaceLevel1();
BlockArm_MoveToPlaceLevel2();

BlockArm_GetState();
BlockArm_Process();
```

---

## 2. 状态

```text
UNHOMED
HOMING
READY
MOVING
REACHED
STOPPED
FAULT
```

状态流：

```text
UNHOMED
↓ Home()
HOMING
├─ 成功 → READY
├─ Stop → UNHOMED
└─ 异常 → FAULT
```

正常运动：

```text
READY / REACHED / STOPPED
↓ MoveToXXX()
MOVING
├─ 到位 → REACHED
├─ Stop → STOPPED
└─ 异常 → FAULT
```

---

## 3. Stop 的理解

今天特别区分：

```text
Stop
≠ Motor_Disable
```

BlockArm_Stop 表示：

> 取消当前运动目标，并进入可控停止 / 保持状态。

原因：

机械臂可能受到重力作用。

如果直接 Disable：

```text
电机失去控制力
↓
机构可能下落
```

因此 Stop 应该更加接近：

```text
取消旧目标
+
保持当前位置
```

如果在 MOVING：

```text
→ STOPPED
```

如果在 HOMING：

```text
→ UNHOMED
```

因为 Homing 没完成，机械坐标不能认为有效。

---

## 4. 内部数据

今天明确 BlockArm 需要保留：

```text
Motor_t *motor_a
Motor_t *motor_b

state

target_a
target_b

current_a
current_b

zero_a
zero_b

homing_count / timer

tolerance
reached_count

motion_count / timer

软件运动范围
```

具体目标到底保存：

```text
两个 Motor 输出轴角度
```

还是：

```text
真实机构空间目标
```

等真实连杆模型确定后再决定。

---

## 5. 不保存 target_type

今天明确不需要：

```text
PICK
SAFE
PLACE_BOTTOM
...
```

这样的运行时 `current_target` 枚举。

因为业务目标已经通过：

```c
MoveToPick()
MoveToSafe()
MoveToPlace...
```

表达。

进入 MOVING 后，状态机真正需要的是：

```text
真实运动目标
```

而不是业务名字。

---

## 6. 内部辅助函数

最终只保留真正有独立职责的：

```c
static void BlockArm_UpdatePosition(void);
static bool BlockArm_IsReached(void);
static void BlockArm_StopMotion(void);
```

不额外创建：

```c
BlockArm_SetTarget();
```

因为只是为了包装 `Motor_SetPosition()` 再套一层，没有真正增加语义。

Homing 逻辑第一版也可以先直接放：

```text
BlockArm_Process()
→ HOMING 分支
```

如果后面变复杂再抽函数。

# 十五、BlockVacuum 的详细设计

接口：

```c
BlockVacuum_Init();

BlockVacuum_Grab();
BlockVacuum_Release();

BlockVacuum_GetState();
BlockVacuum_Process();
```

状态：

```text
RELEASED
GRABBING
GRABBED
RELEASING
FAULT
```

第一版按照复杂情况保留：

```c
BlockVacuum_Process();
```

因为如果有：

```text
GRABBING
→ GRABBED
```

这样的过程状态，就需要周期逻辑推进。

---

## 两种完成判断方案

### 有压力传感器

```text
开启真空
↓
检测压力达到阈值
↓
GRABBED
```

这种情况下：

```text
GRABBED
```

可以较可靠表示吸附已经建立。

### 无压力反馈

```text
开启真空
↓
延时一定时间
↓
GRABBED
```

这种情况下：

```text
GRABBED
```

只是：

> 软件认为吸取动作已经执行完成。

不能严格证明：

> 方块真的已经吸稳。

这一区分以后写代码和注释时必须保持。

---

## 内部数据

可保留：

```text
state

grab / release action timer

timeout

可选：
vacuum_pressure
vacuum_threshold
```

当前不设计 `Home()`。

也不设计 `Stop()`，因为 Vacuum 的 Stop 语义不明确。

## DEFAULT 没有写死为 CLOSED

这一点今天专门保留。



```text
GRABBED
= 软件认为抓取动作完成
```

不一定证明球真实存在。

## 内部数据

当前考虑：

```text
state

action timer

可选：
气缸位置反馈
抓球反馈

timeout
```

不设计 Home。

当前也不设计 Stop，因为气动机构的 Stop 安全语义还不清楚。

# 十八、连续位置机构的到位判断

适用于：

```text
BlockArm
BallRotaryAxis
```

第一版不建议：

```text
当前误差一进入 tolerance
↓
立刻 REACHED
```

而建议：

```text
误差进入 tolerance
+
连续满足 N 个 Process 周期
↓
REACHED
```

所以需要：

```text
tolerance
reached_count
```

注意：

```text
reached_count
```

本身没有固定物理时间意义。

真正时间：

```text
Process 周期 × reached_count
```

如果 Process 调度频率改变，计数阈值也需要重新理解。

# 十九、FAULT 传播的第一版边界

今天对 Fault 进行了较深入讨论，最后重新限定了第一版范围。

最终第一版只做到：

```text
Mechanism 检测异常
↓
Mechanism 自己处理本机构安全
↓
Mechanism → FAULT
↓
Task 检测到 FAULT
↓
Task → FAULT
↓
停止继续执行后续流程
```

其中：

```text
Mechanism
```

负责真正硬件安全。

例如：

```text
BlockArm
→ 停止 / 保持 Motor

Task
→ 只停止完整任务流程
```

Task 不越级直接操作：

```text
Motor
GPIO
Valve
```

# 二十、Ownership / Mechanism 控制权原则

今天正式确认：

> **同一个 Mechanism 同一时刻只能有一个有效上层控制者。**

正常比赛推荐：

```text
Operator
↓
Task
↓
Mechanism
```

例如如果：

```text
PickBlockTask
```

正在等待：

```text
BlockArm 到 Pick
```

这时不能另外直接：

```c
BlockArm_MoveToSafe();
```

否则：

```text
Task
仍然认为目标是 Pick

BlockArm
实际目标已经变成 Safe
```

状态机会失去一致性。

因此正常比赛模式不允许 Operator 越过 Task 抢控制。

# 二十三、Motor 层是否还有效？

在完成上层架构以后，今天最后重新检查了已有 Motor 抽象。

结论：

> **Motor_t 依然非常有效，而且现在定位反而更加清晰。**

它不是：

```text
所有 Mechanism 的统一下层
```

而是：

> **Mechanism 可以依赖的一种执行器抽象。**

因此：

```text
BlockArm
↓

```

以及：

```text

```

都继续成立。

已有 Motor + Adapter 架构不需要推翻。

# 二十四、是否需要建立 Cylinder 层？

今天最后讨论了气缸是否也应该像 Motor 一样封装。

结论：

> **可以建立一个小而明确的 Cylinder 执行器抽象，但不要机械复制 Motor 的复杂结构。**

推荐：

```text
BallGripper
↓
Cylinder
↓
Solenoid Valve Driver
↓
GPIO / HAL
```

可能的最小 API：

```c
Cylinder_Init();

Cylinder_Extend();
Cylinder_Retract();

Cylinder_GetState();
```

状态可以类似：

```text
RETRACTED
EXTENDED
UNKNOWN
```

---

## 没反馈时必须区分“命令状态”和“真实状态”

如果没有磁性开关：

```text
Cylinder_GetState()
```

可能只能说明：

> 当前下发的是 Extend 还是 Retract。

不能说：

> 真实气缸一定已经到位。

如果以后有磁性开关，再升级为真实反馈状态。

# 二十五、不要建立万能 Actuator_t

今天最后明确：

> 当前不要为了架构整齐建立一个统一万能 `Actuator_t`。

因为：

```text
Motor
→ position / speed

Cylinder
→ extend / retract

Vacuum
→ grab / release / pressure
```

三类执行器没有足够强的公共语义。

正确做法是：

```text
Mechanism
↓
真正适合自己的执行器接口
```

而不是：

```text
所有东西
↓
强行 Actuator_t
```

# 二十八、今天最重要的设计认识

## 1. 软件分层不是为了“看起来整齐”

真正依据是职责。

最终：

```text
Task
→ 比赛任务顺序

Mechanism
→ 机械子系统业务动作

Motor / Cylinder / Vacuum
→ 执行器能力

Driver
→ 具体设备和协议

HAL
→ MCU 外设操作
```

---

## 2. 不要根据硬件数量划 Mechanism

```text
两个 Motor
```

完全可以属于：

```text
一个 BlockArm Mechanism
```

只要它们共同完成一个独立机械职责。

---

## 3. Task 不替 Mechanism 做控制

Task 只负责：

```text
什么时候开始
什么时候等
什么时候进入下一步
```

Mechanism 自己负责：

```text
怎么移动
怎么判断完成
怎么处理自己的硬件异常
```

---

## 4. 一个函数返回不代表机械任务结束

状态机必须明确区分：

```text
启动动作
```

和：

```text
完成动作
```

这是非阻塞嵌入式程序非常核心的任务边界。

---

## 5. 先建立保守第一版，再优化

第一版：

```text
严格串行
单 Task
明确完成状态
明确 Ownership
```

后续再考虑：

```text
并行
自动重试
Fault Recovery
Task Cancel
资源管理
Operator 自动化
```
