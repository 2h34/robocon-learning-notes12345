> 整理日期：2026-09-01  
> 整理基线：Git `2b84edf`（`9.1 dj直插f4can1`）  
> 工程：`LEFTNOW·`、`RIGHTNOW`  
> 说明：本文以当前源码为准。`[事实]` 表示能从源码直接确认，`[推测]` 表示根据结构作出的合理解释，`[待验证]` 表示仍需编译、CAN 抓包或实机测试。

## 1. 我现在对整个程序的理解

这套程序不是“收到 CAN 帧后在中断里直接驱动电机”，而是一个分层、异步的控制系统：

```text
主控 CAN 命令
    ↓
CAN 接收中断：识别协议、累计点击、投递 Master_Command
    ↓
BlockArmServiceTask（5 ms）：消费命令、推进业务状态机
    ↓
PickBlockTask / PlaceBlockTask：决定动作顺序
    ↓
BlockArm / BlockVacuum：把业务动作翻译为机构目标
    ↓
DJI / ZDrive / Solenoid：驱动硬件并更新反馈
    ↓
任务终态判断：通过 CAN 回 accepted / finish / reject
```

核心思想是：

- CAN 层只负责“收什么命令、回什么消息”，不应该决定具体电机角度。
- Task 层只负责“先移动、再吸取或释放、何时算完成”。
- Mechanism 层维护机械臂和真空机构的状态，并向电机层给目标。
- Motor/FML 层处理协议、PID、反馈、CAN 发送队列和 GPIO 时序。
- FreeRTOS 任务与定时器中断分别承担“慢状态机”和“快电机控制”。

## 2. 工程分层与模块职责

| 层级 | 目录/文件 | 当前职责 | 不应承担的职责 |
|---|---|---|---|
| 硬件初始化 | `Core/Src/main.c`、`can.c`、`tim.c` | 时钟、GPIO、CAN、定时器、FreeRTOS 初始化 | 取放业务流程 |
| 中断适配 | `IRQ/Src/CAN_IRQHandler.c`、`TIM_IRQHandler.c` | CAN 收帧分流、协议解析、电机周期调用 | 长时间阻塞、完整取放动作 |
| 应用调度 | `APL/Src/myostasks.c` | 5 ms 总调度、命令消费、完成回执 | 直接写电机 CAN 帧 |
| 业务任务 | `Task/Src/PickBlockTask.c`、`PlaceBlockTask.c` | 取块/放块流程状态机 | PID、CAN 滤波器、GPIO 位操作 |
| 机构抽象 | `Mechanism/Src/BlockArm.c`、`BlockVacuum.c` | 双电机协同、姿态目标、真空状态 | 主控协议 ID 判断 |
| 电机驱动 | `Motor/Src/DJmotor.c`、`ZDrive.c` | 电机模式、PID、反馈解析、寻零 | 判断“取块任务是否完成” |
| 通用功能 | `FML/Src/CanQueue.c`、`Solenoid.c`、`pid.c` | CAN 队列、电磁阀移位输出、PID 算法 | 上层业务状态 |
| 板级提示 | `HDL/Src/Led.c`、`Beep.c` | LED 流水灯、蜂鸣器 | 机构状态机 |

这个边界已经基本合理。后续改协议时应尽量只动通信层和应用调度层；改机械目标时主要动 `BlockArm.c`；改电机控制时主要动 `Motor` 层。

## 3. 上电初始化顺序

`main()` 当前顺序如下：

1. `HAL_Init()`，初始化 HAL 和系统节拍。
2. `SystemClock_Config()`，使用 25 MHz HSE，把系统时钟配置到 168 MHz。
3. 初始化 GPIO、DMA、TIM2、TIM3、CAN1、CAN2。
4. 初始化蜂鸣器和 CAN 软件发送队列。
5. 初始化电磁阀通道 1。
6. 初始化 4 个 DJI 电机对象和 6 个 ZDrive 对象。
7. 绑定机构使用的电机：
   - `LEFTNOW·`：`DJmotor[0] + Zmotor[0]`
   - `RIGHTNOW`：`DJmotor[1] + Zmotor[0]`
8. 初始化 `BlockVacuum`、`PickBlockTask`、`PlaceBlockTask`。
9. 创建 FreeRTOS 任务并启动调度器。

`[事实]` UART1/UART2 的初始化及 `UART_Start_Recieve()` 当前在 `main.c` 中被注释，因此 UART 接收回调虽然保留，运行时并未由当前启动流程启用。

## 4. 两条运行节拍

### 4.1 5 ms 机构服务任务

`BlockArmServiceTask()` 每 5 ms 按固定顺序执行：

```text
BlockArm_Process()
→ BlockVacuum_Process()
→ PickBlockTask_Process()
→ PlaceBlockTask_Process()
→ Comm_ClickProcess()
→ 读取并清除 Master_Command
→ 执行新命令
→ Comm_CheckFinish()
→ 调试 flag
→ osDelayUntil(下一周期)
```

这个顺序意味着：本周期先推进旧状态，再消费刚收到的命令；新命令造成的状态变化通常从下一周期开始继续推进。

### 4.2 TIM2 电机节拍

`TIM2` 的定时器输入时钟为 84 MHz，预分频 `84-1`，周期 `1000-1`，因此中断频率为 1 kHz。

| 调用 | 频率 | 作用 |
|---|---:|---|
| `ZdriveDequeue()` | 每 1 ms | 从软件队列向 CAN 总线发送 ZDrive 帧 |
| `DJmotor_Func()` | 每 2 ms | 运行 DJI 模式/PID 并发送电流命令 |
| `ZdriveFunc()` | 每 5 ms | 切换 ZDrive 模式、下发目标、查询位置和速度 |

`[事实/风险]` `MOTOR_ZDRIVE_CAN_BUS_1` 和 `_BUS_2` 当前都等于 CAN2，但中断中仍连续调用了两次 `ZdriveDequeue(CAN2)`；而每次出队内部又最多发送 2 帧，所以同一毫秒最多尝试出队 4 帧。它可能是有意提高吞吐，也可能是总线拆分后遗留，需结合 CAN 负载确认。

## 5. 主控 CAN 通信逻辑

### 5.1 当前总线和帧格式

`[事实]` 当前主控通信走 CAN1，DJI 反馈也走 CAN1；ZDrive 走 CAN2。两路波特率配置均为：

```text
42 MHz / [3 × (1 + 9 + 4)] = 1 Mbps
```

主控发给从板的扩展帧前缀是 `0x010105xx`，从板回复使用 `0x050101xx`，低 8 位 `xx` 是操作 ID。

### 5.2 左右臂操作 ID 不相同

| 功能 | 左臂 ID | 右臂 ID |
|---|---:|---:|
| 开始取块 | `0x03` | `0x05` |
| 开始放块/移动到放置位 | `0x04` | `0x06` |
| 确认释放 | `0x07` | `0x08` |
| 查询 | `0x00` | `0x00` |
| 使能/失能 | `0x01` | `0x01` |
| 错误 | `0xEE` | `0xEE` |
| 复位 | `0xFF` | `0xFF` |

这组 ID 差异是协议设计的一部分，不应为了“左右代码一致”而改成相同 ID。

### 5.3 当前两个目录的实际映射

| 工程目录 | 绑定 DJI | 激活的通信处理器 | 完成回执 ID | 姿态特点 |
|---|---:|---|---|---|
| `LEFTNOW·` | `DJmotor[0]` | `Master_message_handler_right()` | `0x05/0x06/0x08` | 当前使用一组角度方向 |
| `RIGHTNOW` | `DJmotor[1]` | `Master_message_handler_left()` | `0x03/0x04/0x07` | DJI 目标大体镜像，部分 ZDrive 目标也不同 |

`[事实]` 上表是当前源码真实状态。  
`[待验证]` 目录名和激活处理器看起来相反，但不能只凭名字判定为错误：有可能目录名代表机械侧，而烧录/主控定义采用了另一套左右视角。必须用“实际烧录到哪块板、主控把哪只臂定义为左臂”来最终确认。

### 5.4 一次完整的命令路径

以右臂取块 ID `0x05` 为例，当前 `LEFTNOW·` 中的路径是：

```text
CAN1 扩展帧 0x01010505
→ CAN1 FIFO1 回调
→ 检查 (ExtId >> 8) == 0x010105
→ Master_message_handler_right()
→ Comm_RecordClick(0x05)
→ 等最后一次帧后 1000 ms
→ Comm_ClickProcess() 按重复次数生成 Low/High/SecondPick
→ 写入 Master_Command
→ 5 ms 任务消费命令
→ PickBlockTask_Start...()
→ 状态机完成后 Comm_CheckFinish()
→ 回复 0x05010105，数据中标记 finish
```

### 5.5 “重复帧次数”选择层级

取块和放块不是读取数据区的层级参数，而是统计 1 秒间隔内同一操作帧的重复次数：

| 同一 ID 次数 | 取块含义 | 放块含义 |
|---:|---|---|
| 1 | 低位取块 | 底层放置 |
| 2 | 高位取块 | 第一层放置 |
| 3 | 二层取块 | 第二层放置 |
| 4 或其他 | 拒绝/忙回复 |

`[事实/差异]` 现有协议文档中仍有用 `Data[0]` 表示层级的描述，但当前代码实际采用点击计数。联调时必须以主控实际发帧方式为准，并最终统一文档与实现。

### 5.6 当前过滤器能否接收主控消息

`[事实]` 当前 CAN1 可以把主控扩展帧送到软件：

- Filter Bank 0 用列表模式接收标准帧 `0x201~0x204` 到 FIFO0，交给 DJI 驱动。
- Filter Bank 1 使用全 0 掩码送到 FIFO1，软件再检查扩展帧和 `0x010105` 前缀。
- 因而，只要物理接线、收发器、1 Mbps 波特率和扩展 ID 正确，当前过滤路径能接收主控消息。

它不是严格的硬件 ID 白名单；无关帧也可能先进入 FIFO1，再由软件丢弃。功能上可收，抗总线噪声和负载能力仍需抓包验证。

## 6. 命令邮箱与完成回执

CAN 中断不直接调用取放状态机，而是把语义命令写入全局 `volatile uint8_t Master_Command`。5 ms 任务每次读取后立即清为 `Master_Default`。

完成回执由 `s_finish_process` 保存“正在等待完成的原始操作 ID”：

| 操作 | 判定完成的条件 |
|---|---|
| Reset `0xFF` | Arm=`READY`，Pick=`IDLE`，Place=`IDLE` |
| Pick | Pick=`DONE` |
| Place | Place=`MANUAL_ALIGN`，即只表示已经到达放置附近，等待释放 |
| Release | Place=`DONE` |

`Comm_SendFinish()` 只有在 HAL 成功加入发送邮箱后才清除 `s_finish_process`，因此 finish 具备任务周期重试。普通 accepted/reject 回复没有同样的重试机制。

## 7. BlockArm 机构状态机

### 7.1 状态含义

| 状态 | 含义 |
|---|---|
| `DISABLED` | 两个电机彻底失能，不下发位置目标 |
| `UNHOMED` | 已解除失能，但还未完成寻零 |
| `HOMING` | DJI 与 ZDrive 同时向机械限位低速运动，等待堵转/静止判断 |
| `HOME_TO_SAFE` | 记录零点后移动到初始安全位 |
| `READY` | 寻零和初始安全移动完成，可接新任务 |
| `MOVING` | 正在移动到取、放或 Safe 目标 |
| `REACHED` | 连续到位判定完成 |
| `STOPPED` | 保存当前位置为目标并保持 |
| `FAULT` | 状态非法、驱动未绑定或寻零超时等故障 |

主要转移：

```text
上电：DISABLED
使能：DISABLED → UNHOMED
归零：UNHOMED → HOMING
双电机寻零完成：HOMING → HOME_TO_SAFE
初始安全位到位：HOME_TO_SAFE → READY
启动姿态：READY/REACHED/STOPPED → MOVING → REACHED
复位到 Safe：STOPPED/REACHED → MOVING → REACHED → READY
失能：任意正常状态 → DISABLED
```

### 7.2 到位与超时

- DJI 和 ZDrive 的反馈与目标误差都小于 `1°`，连续 10 个 5 ms 周期满足，才认为到位，约 50 ms。
- 寻零超过 10000 个任务周期仍未完成则进入 `FAULT`，约 50 s。
- 普通移动的 `motion_count` 已累加，但移动超时、掉线和机构异常判断仍是 TODO。

### 7.3 当前姿态目标

单位是两台电机的输出端角度，顺序为 `DJI / ZDrive`：

| 目标 | `LEFTNOW·` | `RIGHTNOW` |
|---|---:|---:|
| Low Pick | `-12 / 118` | `12 / 118` |
| High Pick | `-21 / 101` | `28 / 105` |
| Second Pick | `40 / 50` | `-40 / 50` |
| Place Bottom | `-20 / 90` | `20 / 95` |
| Place Level 1 | `49 / 50` | `-45 / 50` |
| Place Level 2 | `85 / 44` | `-82 / 44` |
| Reset Safe | `10 / 40` | `-10 / 40` |
| Homing 后初始 Safe | `0 / 10` | `0 / 10` |

`[事实]` 这些是当前代码常量。`[待验证]` 注释中仍带有 TODO，且没有标定表版本、机械限位或碰撞区说明，不能仅凭代码认定所有姿态已经安全。

### 7.4 人工微调

接口和状态已经存在，目标每 20 ms 可调整一次。但目前只有 `LOW_PICK + FORWARD` 真正让 DJI、ZDrive 各增加 `1°`；其余方向和姿态仍为空实现。因此当前“人工微调”不能视为完整功能。

## 8. 取块状态机

当前流程：

```text
IDLE/DONE
→ 收到 Low/High/Second Pick
→ MOVE_TO_PICK_PREPARE
→ Arm 到 REACHED
→ MANUAL_ALIGN
→ 延时后自动 ConfirmGrab
→ GRAB
→ Vacuum 到 GRABBED
→ DONE
```

启动条件：

- Pick 状态必须是 `IDLE` 或 `DONE`。
- Arm 必须是 `READY`、`REACHED` 或 `STOPPED`。
- Vacuum 必须是 `RELEASED` 或 `GRABBED`。

自动吸取延时：

- `LEFTNOW·`：约 `151 × 5 ms ≈ 0.76 s`。
- `RIGHTNOW`：约 `201 × 5 ms ≈ 1.01 s`。

`[事实]` 状态名仍叫 `MANUAL_ALIGN`，但代码会在延时后自动调用 `PickBlockTask_ConfirmGrab()`。  
`[事实]` 取块成功后自动回 Safe 的代码已注释，因此 Pick=`DONE` 时机械臂仍停在取块姿态附近。

## 9. 放块与释放状态机

当前流程被拆成两条主控命令：

```text
第一条 Place 命令：
IDLE/DONE → MOVE_TO_PLACE_PREPARE → MANUAL_ALIGN
                                       ↓ 回 Place finish

第二条 Release 命令：
MANUAL_ALIGN → RELEASE → Vacuum 到 RELEASED → DONE
                                           ↓ 回 Release finish
```

启动 Place 的额外条件是 Vacuum 必须为 `GRABBED`。Release 只有在 Place=`MANUAL_ALIGN` 时才有效。

`[事实]` 放块完成后自动回 Safe 同样被注释，Release=`DONE` 时机械臂仍保持在放置姿态附近。

## 10. 真空机构

`BlockVacuum` 通过 `solenoid_on(1, cmd)` 控制 4 位电磁阀输出：

- `0x0F`：建立真空。
- `0x00`：释放/关闭。

状态机：

```text
RELEASED → GRABBING → GRABBED
GRABBED  → RELEASING → RELEASED
```

当前没有压力传感器闭环，只按 5 ms 周期计时：

- 建立真空约 2.0 s 后直接认为 `GRABBED`。
- 释放约 2.5 s 后直接认为 `RELEASED`。

因此这里的 `GRABBED` 表示“吸气等待时间已到”，不等价于“传感器确认方块已经吸牢”。

## 11. 电机层

### 11.1 DJI M3508

- 配置 4 个 M3508，CAN1 标准反馈 ID 为 `0x201~0x204`。
- `LEFTNOW·` 的机构使用数组 0，`RIGHTNOW` 使用数组 1。
- 机构层使用位置模式；电机层内部是位置环到速度目标、再由速度 PID 得到电流。
- 寻零模式以低速向限位运动，连续检测编码器位移很小时置 `ZeroFlag`。
- 失能时 `Begin=false`、模式为 Disable、电流目标为 0。

### 11.2 ZDrive

- 初始化 6 个对象，节点 ID 为 `1~6`，机构使用 `Zmotor[0]`（节点 1）。
- 6 个节点当前全部配置在 CAN2。
- CAN 标准 ID 由“低 4 位电机 ID + 高位操作码”组成。
- `ZdriveFunc()` 负责模式切换、目标更新以及广播查询位置 `Pur` 和速度 `Vel`。
- 寻零以 `-1 rpm` 运动；连续 20 次位置变化小于 `0.5°` 后认为静止并完成。

`[风险]` ZDrive 错误码虽然已解析，但 `Zdrive_ErrHandle()` 仍为空，暂未把驱动错误转换为机构 `FAULT` 或安全失能。

## 12. Disable、Reset 和安全语义

### Disable

- DJI、ZDrive 都彻底失能，不保持力矩。
- 真空机构复位为释放。
- Pick/Place 状态直接重新初始化。
- 清除正在等待的 finish。

这更接近“软件急停/断力”，机械结构可能因重力移动，不能自动等同于物理急停安全。

### Reset

- 先停止正在运行的 Pick/Place，使 Arm 尽量进入 `STOPPED`。
- Arm 处于 `STOPPED` 或 `REACHED` 时，移动到 Reset Safe。
- Pick/Place 进入 `RESET_TO_SAFE`，等待 Arm=`READY` 后回 `IDLE`。
- 真空复位在 Reset 分支中被注释，因此 Reset 不会主动释放方块。

这个行为可能是为了避免复位时掉块，但必须和主控安全策略统一。

## 13. 当前已确认的问题与风险

### 优先级 P0：联调前必须确认

1. **目录名与协议处理器映射相反。** 源码事实已经确认，但实际是否错误取决于烧录对象和左右定义。
2. **协议文档与实现不一致。** 当前层级选择靠重复帧次数，不是数据字节。
3. **任务是否真正启动没有反馈。** `PickBlockTask_Start...()` 和 `PlaceBlockTask_Start...()` 返回 `void`；即使因前置状态不满足而直接返回，调度层仍会登记 `s_finish_process`，之后可能永远等不到完成。
4. **单字节命令邮箱可能丢命令。** ISR 和任务共享 `Master_Command`，任务的“读取后清零”不是完整原子队列；两条命令靠得太近时，后写可能覆盖前写，或在清零窗口被抹掉。
5. **硬件验证证据不足。** 仓库中的 `rebuild_ascii.log` 显示 2026-08-27 曾经 `0 Error / 0 Warning`，但当前提交日期是 2026-09-01，不能证明当前 HEAD 已重新编译，更不能证明实机动作安全。

### 优先级 P1：稳定性与安全

1. `is_busy()` 只把 `HOMING`、`HOME_TO_SAFE`、`MOVING` 视为忙；它没有检查 Pick/Place、真空计时、`FAULT`、`UNHOMED`、`REACHED` 等完整业务状态，查询可能报告“可用”但任务实际上不能启动。
2. accepted/reject 发送忽略 `HAL_CAN_AddTxMessage()` 返回值，邮箱满时会静默丢回复；只有 finish 会重试。
3. 多处发送函数虽接收 `hcan` 参数，却硬编码 `&hcan1`，形成总线迁移隐患。
4. 多数操作没有统一检查 `RTR`、`IDE`、DLC 和数据内容。
5. 普通移动未实现超时、反馈掉线、限位、碰撞和电机故障联动。
6. 真空状态纯计时，无压力反馈，无法识别吸取失败或中途掉块。
7. 调试 `flag` 仍保留在正式 5 ms 任务路径，联调时要防止观察器误写。

### 优先级 P2：可维护性

1. 左右工程大部分源码复制，差异散落在处理器选择、完成 ID、DJI 下标、角度和延时中，容易改一边漏一边。
2. 目标角度写在 `BlockArm.c` 的 switch 中，没有单独标定表、版本号和机械配置说明。
3. `LOWPICK/HIGHPICK/...` 等部分宏已不再决定当前点击计数行为，容易误导阅读者。
4. 状态名 `MANUAL_ALIGN` 与当前自动延时抓取行为不一致。

## 14. 如果以后把主控—从板通信迁到 CAN2

当前只读结论是：不能只把 `hcan1` 替换成 `hcan2`。至少要同步处理以下位置：

1. **物理接口**：CAN1 使用 `PA11/PA12`，CAN2 使用 `PB5/PB6`，要确认板上收发器和终端电阻实际连接。
2. **过滤器**：CAN2 当前主要接收 ZDrive 标准帧；需要为主控扩展帧设计明确的过滤和 FIFO 分流。
3. **回调分发**：CAN2 FIFO1 当前只调用 `ZdriveReceive()`；要按 `IDE`/ID 前缀把扩展帧送到主控处理器，把标准帧留给 ZDrive。
4. **所有发送路径**：`send_disable_message()`、`send_busy_message()`、`send_receive_message()`、查询/使能回复、`Comm_SendFinish()` 和点击确认都硬编码了 CAN1 或主动传 `&hcan1`。
5. **自动重发设置**：CAN1 开启 AutoBusOff、AutoWakeUp、AutoRetransmission；CAN2 当前关闭，迁移后要重新决定容错策略。
6. **总线拓扑**：两块从板都初始化 ZDrive ID `1~6`。如果两块板的 CAN2 和两套 ZDrive 被并到同一物理总线，重复节点 ID 会造成交叉控制和反馈冲突；只有在两路 CAN2 物理隔离或重新分配节点 ID 时才安全。
7. **公共命令响应**：查询、使能、复位 ID 对左右臂相同。如果两块从板在同一总线上同时以相同扩展 ID 回复，而数据不同，会在仲裁后发生数据段冲突；需要主控寻址或响应时序设计。

因此 CAN2 迁移本质上是“通信路由和物理拓扑调整”，不是单变量替换。

## 15. 学习过程复盘

### 最初理解

从旧框架文档看，系统被设计成：Task 编排动作，BlockArm/BlockVacuum 封装机构，电机层执行控制。文档中还保留“人工确认抓取、动作后回 Safe”等较理想化流程。

### 阅读源码后发现的偏差

- 当前取块在粗定位后按延时自动吸取，不再等待人工确认。
- Pick 和 Release 完成后不自动回 Safe。
- 放置被拆成“到位”和“确认释放”两条命令。
- 左右臂使用不同任务 ID、不同 DJI 数组对象和镜像/标定角度。
- 协议实现用重复帧次数选择层级，而部分文档仍描述数据字节选择。

### 纠正后的最终模型

当前程序应理解成“主控触发 + 从板异步状态机 + 分阶段 finish 回执”：

1. 主控用臂专属操作 ID 选择 Pick/Place/Release。
2. 取/放层级由同一 ID 的重复次数决定。
3. 从板先 accepted，5 ms 任务再启动状态机。
4. Arm 通过两台异构电机的反馈判定姿态到位。
5. 真空机构目前通过定时而不是传感器确认。
6. Pick 完成表示吸取计时结束；Place 完成表示到达等待释放位置；Release 完成表示释放计时结束。
7. Reset 才负责回统一 Safe，普通任务完成后不自动回 Safe。

### 当前掌握证据

- **理解层**：可以从入口追踪到通信、任务、机构、电机和回执。
- **应用层**：左右臂 ID、DJI 下标、目标角度和延时差异已经能定位。
- **设计层**：已有清晰分层和状态机，但接口返回值、通信队列、安全反馈还需要补强。
- **调试层**：已有 flag 和状态变量可观察，但缺少系统化日志、CAN 错误计数和故障注入记录。
- **迁移层**：CAN2 改造影响面已能列出，但尚未实施和验证。

这里不能直接写“已经完全掌握”或“程序已经完成”：当前证据最多支持“主要业务链路已经搭好，仍有若干联调和安全闭环问题”。

## 16. 建议的验证顺序

### A. 静态/编译验证

- 分别对 `LEFTNOW·`、`RIGHTNOW` 做全量 Rebuild，保存当前提交对应的日志。
- 确认无错误、无未解释警告，并记录固件大小。
- 检查两边 Keil 工程是否引用了各自目录下的源文件。

### B. 只接 CAN、不接执行器

- 用 CAN 分析仪发送查询、使能、左右臂各自操作 ID。
- 验证错误臂 ID 被忽略，正确臂 ID 被接收。
- 验证 1/2/3 次帧在最后一帧后约 1 s 分别生成三个层级命令。
- 人为占满发送邮箱，观察 accepted 与 finish 的不同丢包行为。
- 高频连续发送两种命令，验证 `Master_Command` 是否发生覆盖。

### C. 单电机低风险验证

- 架空或拆除负载，确认 DJI 和 ZDrive 寻零方向。
- 确认堵转电流、堵转时间和机械限位可承受。
- 验证反馈单位、减速比、零点偏移和目标正负方向。

### D. 机构流程验证

- 逐个验证 7 个姿态，记录实测角度、误差和是否碰撞。
- 验证连续 10 次到位是否会因反馈抖动卡住。
- 验证 Pick 自动延时、真空约 2 s、Release 约 2.5 s 的实际效果。
- 在每个中间状态发送 Disable/Reset，观察机构和方块是否安全。
- 分别验证“持有方块复位”和“未持有方块复位”。

### E. 双臂联调

- 建立一张明确映射表：物理左/右臂、烧录工程、主控 ID、DJI ID、ZDrive ID、CAN 物理总线。
- 同时执行两臂，确认没有 ID 冲突、回执混淆和电源压降。
- 最后才考虑把主控通信迁到 CAN2。

## 18. 一页复习摘要

```text
主控通信：CAN1，1 Mbps，扩展帧 0x010105xx
左臂任务：03 Pick / 04 Place / 07 Release
右臂任务：05 Pick / 06 Place / 08 Release
层级选择：同一任务帧重复 1/2/3 次，等待间隔 1 s

机构任务：FreeRTOS 5 ms
电机调度：TIM2 1 kHz；DJI 2 ms；ZDrive 5 ms
执行机构：1 个 DJI + 1 个 ZDrive + 真空电磁阀

取块：移动 → 延时自动吸取 → 真空计时 → DONE
放块：移动 → MANUAL_ALIGN → 主控 Release → 释放计时 → DONE
普通任务：完成后不自动回 Safe
Reset：停止任务 → 回 Safe → READY/IDLE
Disable：电机断力 + 真空释放 + 清任务

当前最大风险：
目录/协议左右映射待实物确认；命令邮箱可能丢命令；
任务启动失败仍登记 finish；运动超时/掉线/真空反馈尚未闭环；
CAN2 与 ZDrive 共线迁移存在路由和重复节点 ID 风险。
```
