# 三、Motor 层与 Mechanism 层

## 1. 两层的核心区别

### Motor 层

Motor 层回答：

> 电机应该怎样运动？

典型语义：

```text
SetPosition
SetSpeed
SetCurrent
Zero
```

例如：

```c
DJI_motor_SetPosition(...)
```

只表达“让某台 DJI 电机运动到某个目标位置”。

它不应该知道：

- 这是升降机构；
- 当前在放第几层；
- 方块要放到哪个建造点；
- 这个动作在比赛中有什么意义。

### Mechanism 层

Mechanism 层回答：

> 机器人机构要完成什么动作？

例如：

```text
Grab
Release
Lift
Zero
到达目标高度
```

一个机构目标不应该直接等于一个电机角度。

例如：

```text
“升到目标高度”
↓
机构目标高度
↓
根据传动关系换算
↓
电机目标位置
↓
Motor 层执行
```

因此：

```text
机构语义
≠
电机语义
```

## 2. 为什么业务层不应该直接依赖 DJI

如果业务代码到处直接写：

```c
DJI_motor_SetPosition(...)
```

那么上层就会被迫知道：

- 哪台电机属于哪个机构；
- 机械传动比；
- 电机安装方向；
- 机构零点；
- 目标高度对应多少电机角度；
- 当前底层使用 DJI 还是 ZDrive。

机械结构或驱动器一变化，上层代码就会被迫修改。

更合理的层级应为：

```text
操作手 / 上层业务逻辑
↓
Mechanism
↓
Motor / Servo / Pneumatic
↓
具体 Driver
↓
执行器
```

上层依赖“机构能做什么”，而不是依赖“机构下面用了什么具体执行器”。

# 四、机构任务建模

今天使用的基本建模思路为：

```text
目标
↓
命令
↓
物理结果
↓
反馈 / 完成条件
↓
执行器
↓
动作过程
↓
等待点
↓
异常
```

以“把已经抓住的方块抬升到指定高度”为例。

## 1. 目标

```text
把已经抓住的方块抬升到指定高度。
```

不是：

```text
让电机转 2000°
```

## 2. 命令

上层给机构的命令应该表达机构目标，例如：

```text
升到目标高度 H
```

命令本身和系统内部执行链路不是同一个概念。

## 3. 成功后的物理结果

```text
方块仍然被稳定夹持，
并随升降机构运动到指定高度。
```

## 4. 完成判断

不能用“函数调用结束”判断完成。

应该根据：

```text
目标高度
+
当前实际高度
+
允许误差
↓
判断是否到位
```

例如：

```text
|actual_height - target_height| <= tolerance
```

即可认为 Lift 到位。

---

# 五、命令 ≠ 物理任务完成

这是今天最重要的结论之一。

例如：

```c
DJI_motor_SetPosition(...);
```

函数返回只表示：

> 目标已经设置。

并不表示：

> 电机和机构已经运动到目标位置。

真实过程是：

```text
设置目标
↓
Motor 控制器持续运行
↓
电机实际运动
↓
传动机构运动
↓
反馈变化
↓
满足完成条件
↓
Mechanism 判断动作完成
```

因此需要明确区分：

```text
命令发出
≠
动作完成
```

# 六、机构状态机

已经学过状态机基础，因此今天直接把它应用到真实机构。

以：

```text
抓取
↓
抬升
```

为例，最小状态流可以是：

```text
未抓取
↓ [操作手发出 Grab]
抓取中
↓ [满足抓稳条件]
已经抓稳
↓ [操作手发出 Lift]
抬升中
↓ [满足目标高度到位条件]
已到目标高度
```

这里形成了两类不同的状态切换条件：

### 操作手命令

负责：

> 什么时候开始一个动作？

例如：

```text
HOLDING
↓ Lift 命令
LIFTING
```

### 物理反馈 / 完成条件

负责：

> 这个动作什么时候真正完成？

例如：

```text
LIFTING
↓ 到位条件满足
REACHED
```

## 状态机在纯手动比赛中的作用

纯手动并不等于所有电机步骤都必须由操作手逐步控制。

更合理的边界是：

```text
操作手
→ 决定什么时候 Grab / Lift / Release

Mechanism
→ 负责把一次已发起的动作完整执行并判断完成
```

例如在 `GRABBING` 状态下，如果操作手误按 Lift：

```text
状态不满足前置条件
↓
拒绝 / 忽略本次 Lift 命令
↓
保持 GRABBING
```

状态机因此还承担：

> 判断当前动作是否合法。

---

# 七、机构内部状态与状态接口

今天澄清了：

```text
机构内部状态
≠
必须向上公开状态接口
```

Mechanism 自己可能必须维护：

```text
IDLE
MOVING
REACHED
FAULT
```

用于：

- 判断动作是否合法；
- 判断动作是否完成；
- 管理自身执行过程。

但是否提供：

```text
IsReached
GetState
```

之类的状态接口，要看上层是否真的需要使用这些信息。

如果以后需要动作联锁、组合动作、自动推进已授权流程、故障显示或上位机状态显示，再提供必要的状态接口。

# 八、任务进度状态与机构状态

今天短暂讨论了两类状态的层级区别：

### 机构状态

回答：

> 某个机构现在物理上正在做什么？

例如：

```text
Lift:
MOVING
REACHED
FAULT
```

### 任务进度状态

回答：

> 当前业务流程进行到哪一步？

例如如果复用一个“下一层”按键，可能需要记录：

```text
下一次应该放底层 / 中层 / 顶层
```

任务进度状态属于更高层业务逻辑，不应该混进 Lift 本身。

今天没有继续扩展完整比赛任务状态机，因为校内赛是纯手动控制，目前只需要掌握这一层级区别。

# 九、Lift 模块建模

Lift 是今天第一个完整机构模型。

## 1. Lift 对外最小能力

```text
1. 归零
2. 运动到指定高度
3. 停止当前运动
4. 必要时提供动作完成 / 状态信息
```

## 2. Lift 内部需要掌握的信息

```text
目标高度
→ 想去哪

当前实际位置 / 反馈
→ 现在在哪

当前机构状态
→ 当前正在干什么

Zero / Homing 信息
→ 是否已经建立可靠的机构坐标基准
```

## 3. 到位判断

不能只根据当前 `state` 判断到位，因为：

```text
反馈
↓
判断到位
↓
更新 state
```

更准确的因果关系是：

```text
目标高度
+
实际高度
+
允许误差
↓
判断到位
↓
MOVING → REACHED
```

# 十、Zero / Homing

今天明确：

```text
Zero
≠
直接命令机构去 0 mm
```

刚上电时，即使编码器能反馈电机角度，也未必知道：

```text
这个电机角度对应机构实际多少 mm
```

Zero 的本质是：

> 建立机构真实位置与软件坐标之间的基准关系。

典型流程：

```text
开始归零
↓
机构寻找可靠物理参考
↓
检测到零点条件
↓
将当前位置定义为机构零点
↓
建立机构坐标系
↓
zeroed = true
```

因此：

```text
Zero
→ 建立坐标基准

Move
→ 在已有坐标基准中进行位置控制
```

# 十一、电机、舵机、气缸的控制逻辑差异

结合队内《常用动力源》资料，今天只从控制组视角建立基本直觉。

## 1. 电机

更适合：

```text
连续可控
多位置
速度控制
位置控制
力矩控制
```

例如 Lift 需要多个不同高度精确停止，更倾向使用电机。

## 2. 气缸

更适合：

```text
状态较少
开 / 关
伸 / 缩
快速动作
较大力
```

队内资料强调：

- 气动适合状态少的机构；
- 控制方便、可提供较大力 / 扭矩；
- 精度通常弱于电机；
- 气缸应作为驱动 / 触发装置，而不应承担导向与提高机构刚度的职责。

## 3. 舵机

今天通过视频补充了舵机控制。

普通 PWM 舵机可以理解为内部已经集成：

```text
电机
+
减速
+
位置反馈
+
内部位置控制
```

STM32 通常通过 PWM 高电平脉宽表达目标位置。

因此控制端更像：

```text
目标角度
↓
舵机内部闭环
↓
输出轴运动到目标附近
```

不需要像 DJI 电机一样自己实现完整的位置 → 速度 → 电流控制链。

需要注意：

```text
PWM 命令
→ 目标角度
```

并不意味着真实机构角度天然完全精确，实际还可能受到舵机型号、安装零位、负载、机械间隙和机构几何关系影响，因此真实机构仍可能需要标定。

# 十二、Gripper 模块建模

Gripper 负责：

> 把 Grab / Release 等夹爪机构语义转换成具体执行器目标，并管理夹爪动作过程。

## 1. Gripper 不负责

- 操作手什么时候决定抓取 / 释放；
- DJI PID / CAN 等电机底层控制；
- 舵机 PWM 的底层驱动实现；
- 电磁阀 GPIO 的底层实现；
- Lift 等其他机构的具体动作。

## 2. 最小对外能力

```text
Grab
Release
```

如果以后上层需要读取状态，再增加必要状态接口。

## 3. 不同执行器下的 Gripper

### 舵机夹爪

```text
Grab
↓
目标夹紧角度
```

### 气缸夹爪

```text
Grab
↓
电磁阀切换到夹紧状态
```

### 电机夹爪

```text
Grab
↓
目标位置 / 必要时结合电流等信息
```

但对上层而言仍然可以保持：

```text
Grab
Release
```

这体现了 Mechanism 层对具体执行器的隔离。

# 十三、最终综合流程：抓取 → 抬升 → 释放

今天最后完成了一个正常流程模型：

```text
操作手：Grab
↓
Gripper 开始抓取
↓
Gripper 内部确定执行器目标
↓
执行器打开
↓
Gripper 判断打开到位
↓
Gripper 下发夹紧目标
↓
执行器夹紧
↓
Gripper 判断抓稳
↓
Grab 完成

操作手：Lift
↓
Lift 确定目标高度
↓
机构坐标 → 执行器目标
↓
升降机构运动
↓
Lift 根据反馈判断到达目标高度
↓
Lift 完成

操作手：Release
↓
Gripper 下发释放目标
↓
执行器打开
↓
Gripper 判断释放动作完成
↓
本次动作流程结束
```

这里每个机构都管理自己的状态：

```text
Gripper
→ 判断夹爪是否打开 / 抓稳 / 释放完成

Lift
→ 判断升降机构是否到位
```

不再使用一个模糊的 `mechanism` 统一处理所有机构。

# 十四、最终软件层级认识

今天最终形成的层级为：

```text
操作手
↓
遥控器 / 上位机输入
↓
上层业务逻辑
↓
Gripper / Lift 等 Mechanism
↓
Motor / Servo / Pneumatic
↓
具体 Driver
↓
真实执行器
↓
机械传动
↓
机构运动
↓
Feedback
```

各层的核心问题：

```text
操作手 / 上层：
现在要做什么？

Mechanism：
这个机构怎样完成目标？
当前能不能执行？
什么时候算完成？

Motor / Servo / Pneumatic：
执行器怎样完成给定目标？

Driver：
怎样产生 CAN / PWM / GPIO 等底层控制信号？
```

# 十五、今天出现的主要理解偏差与修正

## 1. “输入”和“执行流程”混淆

最开始把“上位机发送命令 → Mechanism → Motor”整体理解为输入。

修正为：

```text
输入
= 上层给 Mechanism 的目标

执行流程
= Mechanism 收到目标以后如何完成它
```

## 2. “实际高度”和“目标高度”混淆

最开始描述为：

```text
先确认实际高度
→ 再计算电机目标
```

后明确：

```text
目标高度
→ 用于生成电机目标

实际高度
→ 用于反馈和判断是否到位
```

## 3. “状态决定是否到位”因果关系反向

最开始认为：

```text
根据 mechanism state 判断是否到位
```

修正为：

```text
根据真实反馈判断是否到位
↓
再更新 mechanism state
```

即：

> 反馈用来判断状态，状态用来描述判断结果。

## 4. Gripper 职责理解过窄

最开始认为 Gripper“不负责执行机构具体动作”。

修正后：

> Gripper 负责组织夹爪机构完成 Grab / Release，但不负责底层执行器本身如何实现 PWM、PID、CAN 或电磁阀驱动。

## 5. “上层决定操作手做什么”表述错误

修正为：

```text
操作手产生动作意图
↓
上层软件解释输入并形成机构目标
↓
Mechanism 执行
```

操作手是动作意图来源，上层不是“决定操作手该做什么”。

# 十七、今天最值得记住的一点

今天最核心的变化不是学会了某个新函数，而是建立了新的软件抽象层：

```text
以前：
“我要让电机怎么转”

现在：
“我要让机构完成什么动作”
↓
再由机构模块决定具体执行器怎么动
```

因此：

> **Motor 模块负责“电机怎么动”，Mechanism 模块负责“机器人机构要完成什么动作”。**

同时：

> **命令发出不等于物理任务完成，机构必须结合真实反馈管理自己的动作过程和状态。**
