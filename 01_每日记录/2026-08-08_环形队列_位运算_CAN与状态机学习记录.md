## 4. 今日完成内容

### 4.1 指针基础回顾

今天首先补充了后续作业需要使用的指针知识。

普通变量：

```c
int x = 10;
```

指针变量：

```c
int *p = &x;
```

其中：

```text
&x
→ 取得 x 的地址

p
→ 保存 x 的地址

*p
→ 访问 p 所指向地址中的数据
```

例如：

```c
*p = 20;
```

表示通过指针修改变量 `x`。

今天进一步明确：

> 指针不是“数据本身”，而是保存某个对象所在的内存地址。

---

### 4.2 为什么队列函数要传指针

例如：

```c
void packet_queue_init(packet_queue *q);
```

参数不是：

```c
packet_queue q
```

而是：

```c
packet_queue *q
```

原因是：

> 函数需要真正修改外部队列对象，而不是修改队列的临时副本。

因此：

```c
q->head = 0;
q->tail = 0;
q->count = 0;
```

修改的是调用者真正的 `packet_queue`。

---

### 4.3 结构体的 `.` 与 `->`

普通结构体对象：

```c
packet_queue q;
q.head = 0;
```

结构体指针：

```c
packet_queue *q;
q->head = 0;
```

因此：

```text
普通对象 → .
对象指针 → ->
```

并且：

```c
q->head
```

本质等价于：

```c
(*q).head
```

---

### 4.4 输出参数

题目 3 的函数：

```c
bool command_pack_unpack(
    const command_packet *pkt,
    uint8_t *blink_count,
    uint8_t *led_mask
);
```

这里有三个不同角色：

```text
pkt
→ 输入：待解析协议包

blink_count
→ 输出参数：闪烁次数

led_mask
→ 输出参数：LED 掩码
```

函数自身：

```c
return true;
return false;
```

用于返回：

> 解包是否成功。

而：

```c
*blink_count = ...;
*led_mask = ...;
```

则通过指针向调用者输出两个结果。

今天进一步理解了一个常见 C 语言思路：

> 当函数需要返回多个结果时，可以通过指针参数把结果写回外部变量。

---

### 4.5 `const` 参数

题目中经常出现：

```c
const command_packet *pkt;
```

可以理解为：

> 函数只能读取 `pkt` 指向的数据，不应该通过这个指针修改原协议包。

也就是：

```text
const command_packet *pkt
→ 指针可以指向 command_packet
→ 但不能通过 pkt 修改该 command_packet
```

这是一种接口设计上的保护。

## 5. 题目 1：环形队列

### 5.1 为什么需要环形队列

普通数组有固定长度，如果一直从头写到尾，写到最后以后就没有新的数组下标。

环形队列把数组理解成：

```text
0 → 1 → 2 → ... → N-1
↑                 ↓
└─────────────────┘
```

即：

> 到最后一个位置以后重新回到数组下标 0。

这样可以重复利用已经被读走的数据位置。

---

### 5.2 本题的队列结构

```c
typedef struct
{
    command_packet buf[PACKET_QUEUE_SIZE];
    uint8_t head;
    uint8_t tail;
    uint8_t count;
} packet_queue;
```

三个关键变量：

```text
head
→ 指向“下一次读取”的位置

tail
→ 指向“下一次写入”的位置

count
→ 当前队列中实际有多少个数据包
```

今天特别明确了：

> `head` 和 `tail` 保存的是数组位置，而 `count` 保存的是有效元素数量。

---

### 5.3 队列初始化

```c
void packet_queue_init(packet_queue *q)
{
    q->head = 0;
    q->tail = 0;
    q->count = 0;
}
```

初始化表示：

```text
没有数据
下一次读位置 = 0
下一次写位置 = 0
```

---

### 5.4 入队 `push`

逻辑：

```text
先判断是否已满
→ 将数据写入 tail
→ tail 后移
→ count++
```

代码核心：

```c
q->buf[q->tail] = *pkt;

q->tail =
    (q->tail + 1) % PACKET_QUEUE_SIZE;

q->count++;
```

其中：

```c
*pkt
```

表示取出指针所指向的完整 `command_packet` 对象。

---

### 5.5 出队 `pop`

逻辑：

```text
先判断是否为空
→ 从 head 读取
→ head 后移
→ count--
```

核心：

```c
*pkt = q->buf[q->head];

q->head =
    (q->head + 1) % PACKET_QUEUE_SIZE;

q->count--;
```

---

### 5.6 为什么使用 `%`

例如：

```c
q->tail =
    (q->tail + 1) % PACKET_QUEUE_SIZE;
```

假设：

```text
PACKET_QUEUE_SIZE = 16
tail = 15
```

则：

```text
(15 + 1) % 16
= 0
```

于是位置自动从：

```text
15
```

回到：

```text
0
```

这就是环形队列形成“环”的关键。

---

### 5.7 队列判空、判满

判空：

```c
return q->count == 0U;
```

判满：

```c
return q->count == PACKET_QUEUE_SIZE;
```

今天理解了 `count` 的一个重要作用：

> 如果只看 `head == tail`，它既可能表示队列为空，也可能表示已经绕了一圈而队列满；使用 `count` 可以明确区分两种情况。

```text
0
```

### 6.2 Byte

```text
1 Byte = 8 bit
```

```text
1010 0110
```

```text

```

### 6.3 十六进制

十六进制数字：

```text
0~9
A~F
```

一个十六进制位对应：

```text
4 bit
```

因此：

```text
2 个十六进制位
= 8 bit

```

```text
0x5A
```

```text

```

所以：

```text
0x5A = 0101 1010
```

今天特别纠正了：

## 7. 位运算

今天重点使用了四种：

```text
&
|
<<
>>
```

---

### 7.1 按位与 `&`

用途：

> 使用掩码保留某些 bit。

例如：

```c
led_mask & 0x0F
```

因为：

```text
0x0F
= 0000 1111
```

所以高 4 位会被清零，低 4 位被保留。

---

### 7.2 按位或 `|`

用途：

> 把多个互不冲突的 bit 字段组合在一起。

例如：

```c
(blink_count << 4)
|
(led_mask & 0x0F)
```

可以把：

```text
闪烁次数
LED 掩码
```

放进同一个 Byte。

---

### 7.3 左移 `<<`

例如：

```c
1U << n
```

可以生成：

```text
bit n = 1
其他位 = 0
```

的掩码。

今天再次确认：

> **bit0 是最右边的一位。**

---

### 7.4 右移 `>>`

例如：

```c
pkt->cmd >> 4
```

可以把原本位于高 4 位的闪烁次数移动到低位，以便直接读取数值。

---

### 7.5 Mask 掩码

本次逻辑 LED：

```c
#define LED_MASK_LED1 0x01U
#define LED_MASK_LED2 0x02U
#define LED_MASK_LED3 0x04U
#define LED_MASK_LED4 0x08U
```

对应：

```text
LED1 → bit0
LED2 → bit1
LED3 → bit2
LED4 → bit3
```

LED1 + LED2：

```c
LED_MASK_LED1 | LED_MASK_LED2
```

得到：

```text
0001 | 0010
= 0011
= 0x03
```

---

## 8. 整数提升 Integer Promotion

今天还接触了位运算中的隐含规则：

> 即使变量本身是 `uint8_t`，参与移位、加法等表达式时，C 语言往往会先把它提升为 `int` 或 `unsigned int` 再计算。

因此代码中会看到：

```c
(uint8_t)(...)
```

例如：

```c
pkt->cmd =
    (uint8_t)(
        (blink_count << CMD_BLINK_SHIFT)
        |
        (led_mask & CMD_LED_MASK)
    );
```

这表示：

```text
先完成表达式运算
→ 最后明确保留为 8 bit
```

## 9. 题目 2：位运算封包

### 9.1 协议包结构

```c
typedef struct
{
    uint8_t header[2];
    uint8_t cmd;
    uint8_t checksum;
} command_packet;
```

总长度：

```text
4 Byte
```

布局：

```text
Byte 0
→ header[0]
→ 0x0A

Byte 1
→ header[1]
→ 0x5A

Byte 2
→ cmd

Byte 3
→ checksum
```

---

### 9.2 Header 包头

```c
#define HEADER_HIGH_BYTE 0x0AU
#define HEADER_LOW_BYTE  0x5AU
#define HEADER_WORD      0x0A5AU
```

包头可以作为：

> 识别数据是否符合当前自定义协议的标志。

---

### 9.3 `cmd` 的位段设计

一个 Byte：

```text
bit7 bit6 bit5 bit4 | bit3 bit2 bit1 bit0
```

规定：

```text
高 4 位
→ blink_count

低 4 位
→ led_mask
```

对应：

```c
#define CMD_BLINK_SHIFT 4U
#define CMD_LED_MASK    0x0FU
```

---

### 9.4 封包过程

```c
pkt->cmd =
    (uint8_t)(
        (blink_count << CMD_BLINK_SHIFT)
        |
        (led_mask & CMD_LED_MASK)
    );
```

过程：

```text
blink_count
↓ 左移 4 位
放入 cmd 高 4 位

led_mask
↓ 与 0x0F
只保留低 4 位

两部分按位或
↓
组合成 cmd
```

---

### 9.5 实际测试：3 次闪烁 + LED1、LED2

闪烁次数：

```text
3 = 0011
```

左移：

```text
0011 0000
```

LED1 + LED2：

```text
LED1 = 0001
LED2 = 0010

OR
= 0011
```

组合：

```text
0011 0000
0000 0011
---------
0011 0011
```

所以：

```text
cmd = 0x33
```

## 10. checksum 校验和

定义：

```c
#define PACKET_CHECKSUM(h0, h1, cmd) \
    ((uint8_t)((h0) + (h1) + (cmd)))
```

测试：

```text
header[0] = 0x0A
header[1] = 0x5A
cmd       = 0x33
```

计算：

```text
0x0A + 0x5A + 0x33
= 0x97
```

因此完整测试包：

```text
{0x0A, 0x5A, 0x33, 0x97}
```

含义：

> LED1、LED2 闪烁 3 次。

## 11. 逻辑 LED Mask 与实际 GPIO Mask

这是今天一个比较重要的新认识。

协议层规定：

```text
bit0 → LED1
bit1 → LED2
bit2 → LED3
bit3 → LED4
```

但硬件实际 LED 在：

```text
PB3
PB4
PB5
PB6
```

所以协议里的：

```text
0000 0011
```

不能直接作为 GPIO pin mask。

需要：

```c
uint8_t led_pins =
    (uint8_t)(
        (led_mask & CMD_LED_MASK) << 3
    );
```

例如：

```text
0000 0011
<< 3
=
0001 1000
```

刚好对应：

```text
PB3 + PB4
```

因此今天形成了一个重要层次意识：

```text
协议逻辑编号
≠
硬件物理引脚编号
```

中间经常需要进行映射。

## 12. 题目 3：位运算解包

### 12.1 解包整体流程

```text
接收到 command_packet
↓
检查 Header
↓
检查 checksum
↓
提取 blink_count
↓
提取 led_mask
↓
返回 true
```

任意一项失败：

```c
return false;
```

---

### 12.2 拼接 16 bit Header

```c
uint16_t header_word =
    ((uint16_t)pkt->header[0] << 8)
    |
    pkt->header[1];
```

如果：

```text
header[0] = 0x0A
header[1] = 0x5A
```

则：

```text
0x000A << 8
= 0x0A00

0x0A00 | 0x005A
= 0x0A5A
```

然后：

```c
if (header_word != HEADER_WORD)
{
    return false;
}
```

---

### 12.3 为什么先转 `uint16_t`

```c
(uint16_t)pkt->header[0]
```

表达得更清楚：

> 现在要把原来的 8 bit 数据作为 16 bit 数据进行左移和拼接。

---

### 12.4 checksum 校验

接收端重新计算：

```c
uint8_t checksum =
    PACKET_CHECKSUM(
        pkt->header[0],
        pkt->header[1],
        pkt->cmd
    );
```

比较：

```c
if (checksum != pkt->checksum)
{
    return false;
}
```

这体现：

```text
发送端计算校验
→ 传输
→ 接收端重新计算
→ 比较
```

---

### 12.5 解出 `blink_count`

```c
*blink_count =
    (uint8_t)(
        pkt->cmd >> CMD_BLINK_SHIFT
    );
```

即：

```text
BBBB LLLL
>> 4
=
0000 BBBB
```

---

### 12.6 解出 `led_mask`

```c
*led_mask =
    (uint8_t)(
        pkt->cmd & CMD_LED_MASK
    );
```

即：

```text
BBBB LLLL
&
0000 1111
=
0000 LLLL
```

## 14. 题目 4：CAN 2.0 标准数据帧

### 14.1 CAN 基本概念

CAN：

**Controller Area Network**

中文：

**控制器局域网络**

常用于：

- 汽车电子；
- 电机控制器；
- 机器人内部通信；
- 工业自动化。

今天重点建立的认识：

> CAN 是共享总线、类似广播的通信，不应简单理解成“一个节点直接把数据发给某一个地址”。

---

### 14.2 Classic CAN 标准数据帧字段

今天学习的是：

> Classic CAN / CAN 2.0 的 11 bit 标准 ID 数据帧。

| 字段 | 英文全称 | 位数 | 作用 |
|---|---|---:|---|
| SOF | Start of Frame | 1 bit | 表示一帧开始 |
| ID | Identifier | 11 bit | 消息标识、参与仲裁 |
| RTR | Remote Transmission Request | 1 bit | 区分数据帧与远程帧 |
| IDE | Identifier Extension | 1 bit | 区分标准 ID 与扩展 ID |
| r0 | Reserved bit | 1 bit | 保留位 |
| DLC | Data Length Code | 4 bit | 表示 Data 长度 |
| Data | Data Field | 0~64 bit | 实际业务数据 |
| CRC Sequence | Cyclic Redundancy Check Sequence | 15 bit | CRC 检错 |
| CRC Delimiter | CRC Delimiter | 1 bit | 分隔 |
| ACK Slot | Acknowledge Slot | 1 bit | 接收确认 |
| ACK Delimiter | Acknowledge Delimiter | 1 bit | 分隔 |
| EOF | End of Frame | 7 bit | 一帧结束 |

整体过程：

```text
SOF
→ Arbitration
→ Control
→ Data
→ CRC
→ ACK
→ EOF
```

---

### 14.3 SOF

SOF：

**Start of Frame**

表示：

> CAN 一帧开始。

今天特别区分了：

```text
CAN SOF
→ CAN 标准协议中的控制位

0x0A5A
→ 本作业自己设计的 Header
```

两者不能直接看成同一个结构。

---

### 14.4 ID

ID：

**Identifier**

标准 CAN 中为：

```text
11 bit
```

今天的重要纠正之一：

#### 一开始容易理解成

> ID 决定“发送给谁”。

#### 后来修正为

> ID 更接近“这是什么消息”的标识符，同时参与总线仲裁。

CAN 帧发送后：

```text
一个节点发送
↓
总线上的多个节点都可以看到
↓
各节点根据 ID 判断是否处理
```

所以：

```text
ID
≠ 简单的目的地址
```

---

### 14.5 仲裁 Arbitration

CAN 允许多个节点共用总线。

当多个节点同时发送时，需要进行仲裁。

今天先掌握简化规律：

> **数值更小的 ID 通常有更高的仲裁优先级。**

因此机器人中：

```text
急停
严重故障
保护信息
```

可以设计成较高优先级。

## 15. CRC 与 checksum

### 15.1 CRC

CRC：

**Cyclic Redundancy Check**

中文：

**循环冗余校验**

Classic CAN 中：

```text
CRC Sequence = 15 bit
CRC Delimiter = 1 bit
```

---

### 15.2 CRC 的基本流程

发送端：

```text
数据
→ CRC 运算
→ 得到 CRC
→ 一起发送
```

接收端：

```text
收到数据
→ 再计算 CRC
→ 比较
```

---

### 15.3 CRC 与 checksum 的共同点

都是：

> 错误检测机制。

都体现：

```text
发送端计算
→ 接收端重新计算
→ 比较
```

---

### 15.4 CRC 与本题 checksum 的区别

本题：

```text
checksum
→ 简单加法取低 8 bit
→ 实现容易
→ 检错能力相对弱
```

CAN：

```text
CRC
→ 按固定多项式规则计算
→ 更复杂
→ 检错能力更强
```

---

### 15.5 CRC 的重要误区

容易产生：

> CRC 一样就说明数据一定 100% 正确。

今天修正为：

> CRC 一致只能说明“CRC 没有检测到错误”，不能理解成数学上绝对不存在错误。

## 16. ACK

ACK：

**Acknowledge**

主要包括：

```text

ACK Delimiter
```

今天形成的核心理解：

> ACK 表示至少有接收节点正确接收到该 CAN 帧。

但它不等于：

> 电机已经完成动作。

这是通信层与应用层的区别：

```text
ACK
→ 通信层确认

电机执行成功
→ 应用层状态
```

如果需要确认电机是否执行，应另外发送：

```text
位置反馈
状态反馈
故障反馈
执行结果
```

## 22. FSM 有限状态机

FSM：

**Finite State Machine**

中文：

**有限状态机**

今天开始把它理解为：

> 一个系统在有限个状态之间运行和切换。

本题三个状态：

```text
STATE_IDLE
STATE_RUNNING
STATE_ALARM
```

---

### 22.1 `current_state`

```c
static state_t current_state = STATE_IDLE;
```

含义：

> 当前系统正处于哪个状态。

自己一开始总结：

> 状态机指在几个状态中进行切换运作的机器；`current_state` 表示现在所处的模式。

基本正确。

---

### 22.2 状态转移

State Transition：

**状态转移**

例如：

```c
current_state = STATE_RUNNING;
```

表示：

```text
当前状态
→ RUNNING
```

本题要求：

> 状态切换在运行函数内部完成。

也就是：

```c
static void state_idle(void)
{
    ...
    current_state = STATE_RUNNING;
}
```

---

### 22.3 对状态转移理解的第一次修正

自己一开始说：

> “运行过程中不断检测 current_state 的值，只要它的值变化，状态就会改变。”

后来进一步修正为：

```text
状态函数运行
↓
状态函数主动修改 current_state
↓
本次函数继续执行并结束
↓
下一次进入 while
↓
根据新的 current_state 查表
↓
调用新状态函数
```

这里关键是：

> `current_state` 的变化是由状态函数主动产生的，而不是系统“检测到变化后自动跳转”。

---

### 22.4 修改 `current_state` 不会立即结束函数

这个概念今天专门纠正过一次。

例如：

```c
for (uint8_t i = 0; i < 4; i++)
{
    current_state = STATE_ALARM;
}
```

即使第一次循环已经修改：

```text
current_state = STATE_ALARM
```

当前 `for` 循环仍会继续。

原因：

> `current_state` 只是一个普通变量，改变变量值不会自动改变当前程序计数器的执行位置。

真正提前改变流程，需要：

```c
break;
return;
```

等控制语句。

自己最终复述：

> 不会立即切换，因为当前函数还没有结束、还没有进入下一次 `while` 循环。

---

## 23. 为什么函数表比 `switch` 更模块化

普通状态机可以：

```c
switch (current_state)
{
    case STATE_IDLE:
        state_idle();
        break;

    case STATE_RUNNING:
        state_running();
        break;

    case STATE_ALARM:
        state_alarm();
        break;
}
```

但状态越来越多时：

```text
switch
→ 越来越长
→ main 了解越来越多状态细节
```

函数指针表：

```c
state_table[current_state]();
```

主函数只需要：

```text
读取 current_state
→ 查表
→ 调用函数
```

自己总结：

> 这是一种模块化的方式，可以避免 `switch` 结构过长；主函数只需要通过 `current_state` 的值调用对应数组下标里的函数，而函数实现在各自函数体内。

这个总结准确。

## 40. 核心概念

### 40.1 数据与内存

- 指针保存地址；
- `&` 取地址；
- `*` 解引用；
- 结构体指针使用 `->`；
- 输出参数可以让函数写回多个结果；
- `const` 可以限制通过指针修改数据。

### 40.2 环形队列

- `head`：下一个读取位置；
- `tail`：下一个写入位置；
- `count`：当前元素数量；
- `%` 用于从数组末尾重新回到开头。

### 40.3 位运算

- `&`：掩码保留；
- `|`：组合字段；
- `<<`：向高位移动；
- `>>`：向低位提取；
- bit0 位于最右侧。

### 40.4 协议

- Header 用于识别数据；
- cmd 可以把多个小字段压缩进一个 Byte；
- checksum 用于简单错误检测；
- pack 和 unpack 应互为逆过程。

### 40.5 CAN

- CAN 是共享总线通信；
- ID 是消息标识，也参与仲裁；
- DLC 字段本身 4 bit；
- Classic CAN Data 最大 8 Byte；
- CRC 比简单 checksum 检错能力强；
- ACK 是通信接收确认，不是应用执行确认。

### 40.6 函数指针与 FSM

- 函数也有入口地址；
- 函数指针保存函数地址；
- `typedef` 可以给函数指针类型起名字；
- 函数表把“状态编号”映射到“状态函数”；
- FSM 核心是当前状态、状态行为和状态转移；
- 修改 `current_state` 不会自动终止当前函数；
- 文件级 `static` 用于隐藏模块内部实现；
- `const` 防止函数表运行时被修改。
