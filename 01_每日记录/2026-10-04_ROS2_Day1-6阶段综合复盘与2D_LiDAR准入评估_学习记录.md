# 3. 阶段 A：核心概念压缩测试

## 3.1 Workspace / Package / Executable / Node

测试场景：

```text
ros2_ws
hello_ros2
lidar_pub
/front_lidar
```

判断：

```text
ros2_ws      → Workspace
hello_ros2   → Package
lidar_pub    → Executable
/front_lidar → Node
```

关键认识：

```text
Executable ≠ Node
```

`ros2 run hello_ros2 lidar_pub` 启动的是 executable。

程序运行后：

```cpp
Node("front_lidar")
```

创建的才是 ROS Graph 中的 Node。

因此：

> Executable 名和 Node 名可以相同，但机制上不是同一个概念。

---

## 3.2 `create_publisher()` 与 `publish()`

代码：

```cpp
publisher_ =
    this->create_publisher<sensor_msgs::msg::LaserScan>(
        "/scan", 10);
```

理解：

```text
create_publisher()
→ 创建 Publisher 通信实体

publisher_->publish(msg)
→ 真正发布一条消息
```

这里的：

```text
10
```

不是：

```text
10 Hz
```

而是：

```text
Depth = 10
```

通常对应：

```text
History = KEEP_LAST
Depth   = 10
```

需要继续保持：

```text
Depth
≠
发布频率
```

---

## 3.3 Topic、Message type、QoS

### Topic

表示：

> 数据走在哪个命名的通信通道中。

例如：

```text
/scan
```

### Message type

表示：

> 数据结构是什么。

例如：

```text
sensor_msgs/msg/LaserScan
```

如果：

```text
Publisher:
Topic = /scan
Type  = LaserScan
```

而 Subscriber：

```text
Topic = /scan
Type  = String
```

则不能因为 Topic 名相同就通信。

### QoS

表示：

> 数据希望怎样传输。

因此三者关系可以压缩为：

```text
Topic
→ 在哪里通信

Message type
→ 通信的数据长什么样

QoS
→ 数据怎样传
```

---

## 3.4 QoS Compatibility

测试场景：

```text
Publisher = BEST_EFFORT
Subscriber A = BEST_EFFORT
Subscriber B = RELIABLE
```

判断：

```text
Publisher BEST_EFFORT
→ Subscriber BEST_EFFORT
→ 可兼容

Publisher BEST_EFFORT
→ Subscriber RELIABLE
→ 不兼容
```

核心模型：

```text
Publisher 提供 Offered QoS
Subscriber 提出 Requested QoS
```

只有 Publisher 能满足 Subscriber 的要求，才能建立有效通信。

同时：

```text
Publisher = RELIABLE
Subscriber = BEST_EFFORT
```

通常可以兼容。

# 4. Depth 与 Frequency

测试代码：

```cpp
publisher_ =
    this->create_publisher<sensor_msgs::msg::LaserScan>(
        "/scan", 20);

timer_ =
    this->create_wall_timer(
        500ms,
        ...);
```

判断：

```text
Depth = 20
```

只描述队列深度。

而：

```text
Timer = 500 ms
```

意味着理论周期：

\[
T = 0.5\text{s}
\]

因此理论频率：

\[
f=\frac{1}{T}=2\text{Hz}
\]

即：

```text
500 ms Timer
→ 约 2 Hz
```

# 5. `header.stamp` 与 callback 执行时间

测试场景：

```text
header.stamp = 10:03:15.200

Subscriber callback 实际开始执行：
10:03:15.235
```

正确理解：

```text
header.stamp
→ 这帧传感器数据对应的测量 / 采集时间

callback 执行时间
→ Subscriber 实际被 Executor 调度并开始处理该消息的时间
```

运行过程可以抽象为：

```text
传感器测量
↓
Driver 生成 Message
↓
ROS2 传输
↓
Subscriber 收到
↓
callback ready
↓
Executor 调度
↓
callback 执行
```

因此：

```text
measurement time
≠
callback execution time
```

工程注意：

真实 LiDAR 的 `header.stamp` 究竟对应：

- 扫描开始；
- 扫描结束；
- 设备硬件时间；
- Driver 定义的其他采样时刻；

需要查看真实 Driver 的文档或源码。

# 6. `frame_id`、Node、Topic 的区别

测试场景：

```text
Node:
/front_lidar

Topic:
/front_scan

LaserScan.header.frame_id:
laser
```

正确理解：

```text
/front_lidar
→ Node 名

/front_scan
→ Topic 名

laser
→ 坐标系名称
```

因此：

```text
frame_id
```

回答的是：

> 这一帧数据是在什么坐标系下表达的？

而不是：

> 消息由哪个 Node 发布？

也不是：

> 消息走哪个 Topic？

# 7. Parameter 与 C++ 成员变量

测试代码：

```cpp
this->declare_parameter<double>("range_max", 10.0);

range_max_ =
    this->get_parameter("range_max").as_double();
```

之后程序一直使用：

```cpp
range_max_
```

运行中：

```bash
ros2 param set /fake_lidar range_max 5.0
```

此时可能出现：

```text
ROS2 Parameter range_max = 5.0

C++ 成员变量 range_max_ = 10.0
```

原因：

```text
Parameter
≠
C++ 成员变量
```

更准确理解：

```text
ROS2 Parameter
→ ROS2 运行时配置状态

C++ 成员变量
→ 程序内部真正参与计算的数据
```

二者只有在代码主动执行：

```text
get_parameter()
```

或注册参数变化处理逻辑时，才会建立更新关系。

因此：

```text
ros2 param set 成功
≠
程序实际行为一定立即改变
```

# 8. Parameter / YAML / Remapping / Launch Argument / Launch

这是 Day 6 的核心配置系统。

## Parameter

作用：

> 配置一个 Node 怎么工作。

例如 LiDAR：

```text
serial_port
baud_rate
frame_id
scan_frequency
```

---

## YAML

作用：

> 把一组 Parameter 集中保存到外部配置文件。

例如：

```text
config/lidar.yaml
```

优点：

- 参数不写死在 C++；
- 不写死在 Launch；
- 更容易复用和修改；
- 更适合实际机器人系统。

---

## Remapping

作用：

> 不修改 C++ 源码，改变 ROS Graph 中实际使用的名称和连接关系。

例如源码：

```text
/scan
```

实际运行：

```text
/scan → /front_scan
```

---

## Launch Argument

作用：

> 给 Launch 文件提供启动时输入。

例如：

```text
scan_topic := /front_scan
```

启动时可以改成：

```text
scan_topic := /rear_scan
```

而不用改源码或配置文件。

---

## Launch

作用：

> 统一组织一个 ROS2 系统。

Launch 可以统一管理：

```text
Node
Parameter
YAML
Remapping
Launch Argument
```

从而做到：

```text
一条命令
→ 启动完整系统
```

# 10. callback readiness 与真实发布频率

测试代码：

```cpp
scan_callback(...)
timer_callback()
```

理解：

```text
scan_callback
→ Subscription 收到可处理消息
→ callback ready

timer_callback
→ Timer 到期
→ callback ready
```

然后都由：

```text
Executor
```

进行调度。

---

## 10.1 本次出现的一个重要误判

代码：

```cpp
timer_ =
    this->create_wall_timer(
        1s,
        ...);
```

最开始看到 `1s Timer` 后，产生了：

> `/filtered_scan` 可能受 1 Hz Timer 影响。

这个判断不准确。

必须看：

```cpp
publish()
```

到底写在哪个 callback 中。

实际：

```cpp
scan_callback(...)
{
    ...
    scan_pub_->publish(output);
}
```

而：

```cpp
timer_callback()
{
    RCLCPP_INFO(...);
}
```

因此：

```text
/scan 来一条消息
→ scan_callback
→ /filtered_scan 发布一条消息
```

而：

```text
1 s Timer
→ timer_callback
→ 只打印日志
```

如果：

```text
/scan = 20 Hz
```

稳定运行 5 秒，则大约：

```text
scan_callback     = 100 次
timer_callback    = 5 次
/filtered_scan    = 100 条
received_count_   = 100
```

本次形成的重要代码阅读原则：

> 不要看到 Timer 就自动推断它控制发布频率，必须确认 `publish()` 真正位于哪个 callback。

# 11. 不根据变量名 / Node 名 / Topic 名猜功能

测试代码：

```cpp
auto output = *msg;

output.range_max = range_limit_;

scan_pub_->publish(output);
```

假设：

```text
ranges = [2.0, 5.0, 9.5, 11.0]
range_limit_ = 8.0
```

最初判断：

> 程序已经把大于 8 m 的数据过滤掉。

这个判断是错误的。

代码实际上只执行：

```text
复制原 Message
↓
把 output.range_max 改成 8.0
↓
发布
```

它没有：

```text
遍历 ranges[]
```

也没有：

```text
删除 / 替换 / 裁剪 > 8 m 的元素
```

因此可能得到：

```text
ranges = [2.0, 5.0, 9.5, 11.0]
range_max = 8.0
```

这暴露出当前代码阅读中最值得强化的一点：

```text
不要因为：
ScanRelay
filtered_scan
range_limit
```

这些名字看起来像“过滤器”，就推断代码真的完成了过滤。

正确方式应是：

```text
看具体语句
↓
确认状态如何变化
↓
确认 Message 哪些字段被修改
↓
确认哪里真正 publish
↓
再判断程序功能
```

## 12.1 Topic 存在、Publisher/Subscriber 都有，但没有消息

现象：

```text
/scan 存在

Publisher count: 1
Subscription count: 1
```

但：

```bash
ros2 topic echo /scan
```

没有任何数据。

正确排查意识：

```text
Topic 是否正确
↓
Message type 是否正确
↓
QoS 是否兼容
↓
Publisher 是否真的在 publish()
↓
上游 Timer / callback / sensor source 是否正常
↓
Subscriber 是否真正收到
```

重要认识：

```text
Graph 上存在端点
≠
Publisher 正在实际产生数据
≠
Subscriber 一定已经得到有效消息
```

---

## 12.2 Parameter 显示 5 Hz，但 Topic 只有 2 Hz

现象：

```text
publish_rate_hz = 5.0
```

但：

```text
ros2 topic hz /scan
→ 2 Hz
```

本次自己的原始判断：

> 可能是程序代码里面运用 / 处理这个数据的阶段出了问题。

这一思路是正确的。

更准确可表达为：

```text
Parameter 已经存在且值正确
↓
检查程序有没有读取这个 Parameter
↓
检查是否真正用于 Timer 周期
↓
检查 Parameter 改变后 Timer 是否更新
```

例如：

```cpp
declare_parameter("publish_rate_hz", 5.0);
```

但如果仍然：

```cpp
create_wall_timer(500ms, ...)
```

则实际仍约为：

```text
2 Hz
```

因此：

```text
Parameter 值正确
≠
程序行为自动正确
```

# 22. 今日最重要的几个结论

### 结论 1

```text
ROS2 Graph 中“有 Publisher / Subscriber”
≠
数据一定在正常流动
```

---

### 结论 2

```text
Parameter 的值发生变化
≠
程序内部成员变量和实际行为自动变化
```

---

### 结论 3

```text
Timer 存在
≠
这个 Timer 一定控制 Publisher 的发布频率
```

必须看：

```text
publish()
```

到底位于哪个 callback。

---

### 结论 4

```text
Node / Topic / Parameter 的名字看起来像某种功能
≠
代码真的实现了这个功能
```

必须以实际执行语句为准。

---

### 结论 5

```text
frame_id
```

描述的是：

> 数据属于哪个坐标系。

不是 Node 名，也不是 Topic 名。

---

### 结论 6

ROS2 Day 1～Day 6 已经形成了足够完整的公共前置能力。

当前最合理的学习方式已经从：

```text
继续补 ROS2 基础
```

切换为：

```text
真实硬件接入
→ 遇到实际问题
→ 按需学习新的 ROS2 / TF2 / Driver / 定位建图知识
```
