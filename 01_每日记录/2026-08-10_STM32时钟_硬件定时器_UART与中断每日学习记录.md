## 4. STM32 时钟系统

本工程主要时钟关系：

```text
SYSCLK = 550 MHz
   ↓ AHB /2
HCLK = 275 MHz
   ↓ APB1 /2
PCLK1 = 137.5 MHz
   ↓ 当前 Timer 时钟配置
APB1 Timer Clock = 275 MHz
```

因此 TIM6 的 PSC / ARR 计算使用：

```text
TIM6 Clock = 275 MHz
```

重要结论：

> **PCLK 和 Timer Clock 不一定相同，实际配置 Timer 前应确认真正输入定时器的时钟。**

---

## 5. PSC、CNT、ARR

`PSC = Prescaler`，预分频器：

```text
CNT Clock = TIM Clock / (PSC + 1)
```

`CNT = Counter`，计数器，按照 CNT Clock 自动计数。

`ARR = Auto-Reload Register`，自动重装载寄存器。简单向上计数时：

```text
CNT：0 → 1 → ... → ARR
```

一轮实际计数：

```text
ARR + 1
```

---

## 6. TIM6 500 ms 参数计算

最终参数：

```text
TIM6 Clock = 275 MHz
PSC = 27499
```

因此：

```text
CNT Clock = 10 kHz
单个 tick = 0.1 ms
```

再设置：

```text
ARR = 4999
```

得到：

```text
周期 = (4999 + 1) × 0.1 ms = 500 ms
```

即：

> TIM6 每 500 ms 产生一次周期事件。

---

## 7. Timer 参数选择时的错误与修正

开始考虑：

```text
PSC = 274
CNT Clock = 1 MHz
```

如果要 500 ms：

```text
ARR = 499999
```

但 TIM6 的 ARR 无法容纳这个值。

于是改为：

```text
PSC = 27499
CNT Clock = 10 kHz
ARR = 4999
```

最终满足 500 ms。

这一步形成的认识：

> **Timer 配置不仅要会算，还要考虑寄存器位宽和外设实际限制。**

## 8. Update Event、IRQ、NVIC、ISR

CNT 完成一轮计数后产生：

```text
Update Event
```

它只是 Timer 内部事件，不等于中断。

更准确：

```text
CNT 到周期
↓
Update Event
↓
对应中断已使能
↓
IRQ
↓
NVIC
↓
ISR
```

术语：

- `IRQ = Interrupt Request`：中断请求
- `NVIC = Nested Vectored Interrupt Controller`：管理中断使能、优先级、Pending 与抢占
- `ISR = Interrupt Service Routine`：CPU 响应中断后进入的服务程序

TIM6 的 ISR：

```c
void TIM6_DAC_IRQHandler(void)
{
    HAL_TIM_IRQHandler(&htim6);
}
```

---

## 9. HAL Handler 与 Callback：第一次理解

Timer 阶段看到的实际调用链：

```text
TIM6 Update Event
↓
IRQ
↓
NVIC
↓
TIM6_DAC_IRQHandler()
↓
HAL_TIM_IRQHandler(&htim6)
↓
HAL_TIM_PeriodElapsedCallback()
↓
LED 逻辑
```

当时这个模型足够完成 Timer 实操，但后面的 UART 学习让这里得到进一步修正：

> `IRQ / ISR / HAL Handler` 属于中断处理主链；Callback 是 HAL 在特定高层事件或任务条件满足时提供给用户的接口，不能简单理解成所有中断都必经的一步。

## 13. Timer Callback 与 LED

代码：

```c

{
    if (htim->Instance == TIM6)
    {
        HAL_GPIO_TogglePin(GPIOB, GPIO_PIN_3);

```

其中：

```c
htim->Instance == TIM6
```

用于确认当前是 TIM6 的事件。

LED1 为 PB3。

`HAL_GPIO_TogglePin()` 每调用一次翻转一次 GPIO 输出，所以：

```text

```

# UART 学习部分

## 17. UART 基础概念

`UART = Universal Asynchronous Receiver/Transmitter`

中文：

> 通用异步收发器。

最初容易理解成：

> CPU 数据 → 电信号。

后来修正：

> UART 更准确的作用是按照 UART 的时序和帧格式把数据串行发送，并把接收到的串行 bit 重新组成数据。

---

## 18. TX、RX、GND

- `TX = Transmit`：发送
- `RX = Receive`：接收

典型连接：

```text
设备 A TX → 设备 B RX
设备 A RX ← 设备 B TX
GND       ↔ GND
```

共地的真正作用：

> 给双方建立共同电压参考，使接收端能够可靠识别 HIGH / LOW。

---

## 19. UART 与 GPIO Alternate Function

TX / RX 不应理解为芯片上永远固定的一对脚。

更准确：

```text
USART/UART 外设信号
↓
GPIO Alternate Function
↓
映射到支持的 GPIO
```

因此后续实物时必须根据 MCU、CubeMX 和板上可用引脚确定具体 USART 与 TX / RX。

---

## 20. 串行、异步、Baud Rate

串行：

> 一个数据拆成若干 bit，一位一位传输。

UART 通常：

```text
LSB First
```

即：

```text
bit0 → bit1 → ... → bit7
```

异步：

> 双方没有共享一根时钟线，而是提前约定相同的通信速率，各自依据自己的时钟发送和采样。

普通 UART 中：

```text
115200 Baud ≈ 115200 bit/s
```

一个 bit 约：

```text
8.68 μs
```

---

## 21. UART 帧与 115200 8N1

典型帧：

```text
Idle
→ Start Bit
→ Data Bits
→ Parity（可选）
→ Stop Bit
```

常见状态：

```text
Idle = 1
Start = 0
Stop = 1
```

Parity：

- Even
- Odd
- None

None 表示没有校验位，不是“校验位为 0”。

`115200 8N1`：

```text
115200 → Baud Rate
8      → 8 Data Bits
N      → No Parity
1      → 1 Stop Bit
```

一帧在线路上共：

```text
1 Start + 8 Data + 1 Stop = 10 bit
```

---

## 22. UART 与 PC 的连接

PC USB 与 STM32 UART 不是同一种协议。

常见链路：

```text
STM32 UART
TX / RX / GND
↓
USB-TTL / USB-UART
↓
USB
↓
Windows COM
↓
串口助手
```

当前使用的 Telesky ST-LINK/V2 只有 SWD / 供电相关引脚，没有 TX / RX，也没有可用 ST-Link Virtual COM Port。

因此：

> 当前 ST-Link 可继续负责 SWD 下载 / 调试，但不能直接作为 UART ↔ PC 的串口桥。

## 24. 阻塞式 UART 接收

典型：

```c
HAL_UART_Receive(&huartX, pData, Size, Timeout);
```

含义：

```text
当前 main 执行流
↓
进入 Receive
↓
等待数据
↓
完成 / 超时
↓
返回
```

重要修正：

> 阻塞的是当前正常执行流，不等于整个 CPU 所有中断都停止。

因此 main 阻塞等待 UART 时，只要 Timer 中断正常开启，Timer IRQ 仍可打断 main。

---

## 25. 阻塞式 UART 发送

典型：

```c
HAL_UART_Transmit(&huartX, msg, Size, Timeout);
```

当前执行流会在函数内等待发送过程推进，直到完成或超时。

因此：

```c
HAL_UART_Transmit(...);
task_B();
```

表示：

```text
发送完成 / 超时
↓
task_B 才继续
```

---

## 26. `HAL_UART_Receive_IT()` 的本质

典型：

```c
HAL_UART_Receive_IT(&huartX, &rx_data, 1);
```

今天专门确认：

> UART 数据接收不是全部在这个函数内部完成。

这个函数主要负责：

```text
检查状态
↓
记录接收缓冲区地址
↓
记录目标长度
↓
修改 HAL 接收状态
↓
开启相关中断机制
↓
快速返回
```

真正的 bit 接收由 UART 硬件完成。

---

## 27. 函数调用结束 ≠ 异步任务结束

这是今天最重要的概念之一。

```text
HAL_UART_Receive_IT()
↓
函数返回
```

只说明：

> “启动任务”这个动作结束了。

真正任务：

```text
硬件等待
↓
数据未来到来
↓
UART 接收
↓
中断
↓
HAL 处理
↓
任务最终完成
```

因此需要区分：

```text
函数调用边界
```

和：

```text
异步任务生命周期
```

---

## 28. Start Bit 与 CPU 的误解

错误模型：

```text
Start Bit 到来
↓
CPU 立刻进 ISR
↓
CPU 在 ISR 里等后面的 bit
```

正确模型：

```text
Start Bit
↓
UART 硬件识别
↓
UART 硬件按 Baud Rate 继续采样
↓
完整数据准备好
↓
通过 IRQ 通知 CPU
```

所以：

> CPU 不会为了等 UART 后续 bit 一直停在 ISR 中。

---

## 29. UART 中断接收基本流程

简化模型：

```text
UART 硬件收到完整数据
↓
UART IRQ
↓
NVIC
↓
USARTx_IRQHandler()
↓
HAL_UART_IRQHandler()
↓
HAL 读取接收数据
↓
写入用户缓冲区
↓
更新当前接收任务状态
↓
判断任务是否完成
```

如果任务完成：

```text
↓
HAL_UART_RxCpltCallback()
```

## 30. `Receive_IT(...,8)` 的正确理解

例如：

```c
HAL_UART_Receive_IT(&huartX, rx_buf, 8);
```

不是：

```text
内部调用 8 次 Receive_IT(...,1)
```

而是：

> 一个目标长度为 8 的接收任务。

概念过程：

```text
第 1 字节 → 写入 buffer → 剩余 7
第 2 字节 → 写入 buffer → 剩余 6
...
第 8 字节 → 剩余 0
↓
整个任务完成
↓
RxCpltCallback
```

所以：

> 一次 API 调用可以跨越多次中断处理。

---

## 31. Callback 概念的关键修正

这是今天最有价值的讨论之一。

Timer 阶段容易形成：

```text
IRQ → ISR → Handler → Callback
```

于是误以为：

> Callback 是中断机制必经组成。

UART 学习后重新区分：

```text
硬件中断主链：
事件
→ IRQ
→ NVIC
→ ISR
→ HAL Handler
```

和：

```text
用户接口层：
HAL Handler
→ 判断具体高层事件 / 任务条件
→ 对应 Callback
→ 用户业务
```

最终确认：

> **Callback 不是中断本身，但它把“中断发生后的用户业务逻辑”和底层中断处理解耦了。**

---

## 32. 为什么 Timer 看起来每次中断都 Callback

Timer Update Event 本身就代表：

```text
一个周期完成
```

因此：

```text
相关中断被处理
↓
Period Elapsed 条件成立
↓
PeriodElapsedCallback()
```

在当前 Timer 示例中几乎一一对应。

但不能推出：

> 所有外设每次 IRQ 都一定执行用户 Callback。

---

## 33. UART 如何说明 Callback 不是硬件必需环节

例如：

```c
HAL_UART_Receive_IT(..., 8);
```

前几个字节：

```text
UART IRQ
↓
HAL Handler
↓
数据已经写入 buffer
↓
任务未完成
↓
不执行 RxCpltCallback
```

直到第 8 字节：

```text
任务完成
↓
RxCpltCallback
```

所以：

```text
发生中断 ≠ 必然执行某个用户 Callback
```

最终理解：

> **用户 Callback 可以很好地融入整个中断流程，借助中断机制执行用户逻辑；但 Callback 本身不是硬件中断机制的必需组成。**

---

## 34. `huart` 参数

形式：

```c
void HAL_UART_RxCpltCallback(UART_HandleTypeDef *huart)
```

`huart` 用于：

> 告诉 Callback 到底是哪一个 UART / USART 完成了接收任务。

例如：

```c
if (huart->Instance == USART1)
{
    ...
}
```

可以记：

```text
huart   → 谁完成了接收
rx_data → 收到了什么
```

---

## 35. `rx_data` 在什么时候被写入

例如：

```c
uint8_t rx_data;
HAL_UART_Receive_IT(&huartX, &rx_data, 1);
```

`&rx_data` 表示：

> 接收数据应该写入的内存地址。

真正流程：

```text
UART 硬件接收
↓
IRQ
↓
HAL Handler
↓
写入 rx_data
↓
任务完成
↓
Callback
```

因此：

> **`rx_data` 在 Callback 执行之前就已经被写好。**

这也进一步印证：

> Callback 不是完成底层数据接收和搬运的必要步骤。

---

## 36. 作用域与生命周期

重新区分：

```text
作用域 Scope
→ 哪里可以通过变量名访问

生命周期 Lifetime
→ 变量对应内存还有效多久
```

例如：

```c
void start_receive(void)
{
    uint8_t rx_data;
    HAL_UART_Receive_IT(&huart1, &rx_data, 1);
}
```

函数返回后：

```text
普通局部变量生命周期结束
```

即使那个 RAM 地址物理上还存在，也可能被栈重新使用。

因此异步接收要求：

> 接收任务完成之前，用户提供的缓冲区地址必须一直有效。

---

## 37. 为什么简单示例常用全局 `rx_data`

```c
uint8_t rx_data;
```

同时满足：

```text
生命周期长
+
Callback 可直接访问
```

但要明确：

> 异步 UART 并不是“必须用全局变量”，真正要求是任务存活期间内存地址持续有效。

---

## 38. `Receive_IT(...,1)` 不是永久监听

```c
HAL_UART_Receive_IT(..., 1);
```

只表示：

> 创建一次“接收 1 个数据”的任务。

收到一个字节并完成后，这项任务就结束。

不会自动产生下一项任务。

---

## 39. 持续接收

第一次：

```c
HAL_UART_Receive_IT(&huartX, &rx_data, 1);
```

在 main 中启动。

Callback 中：

```c
HAL_UART_Receive_IT(huart, &rx_data, 1);
```

重新启动下一项任务。

形成：

```text
任务 1
→ Callback
→ 任务 2
→ Callback
→ 任务 3
→ ...
```

所以可以记：

> **main 启动第一次，Callback 续上下一次。**

```text
→ 真正执行

```

## 42. Timer + UART 中断共存

硬件层：

```text
Timer 自己计数
UART 自己接收
```

可以并行。

CPU 软件层：

```text
ISR / Handler / Callback
```

仍然需要按优先级逐个执行。

如果高优先级中断到来：

```text
低优先级 ISR
↓
高优先级 IRQ
↓
抢占
↓
高优先级 ISR
↓
返回原 ISR
```

如果不能抢占：

```text
保持 pending
↓
等待当前 ISR 完成
↓
再处理
```

## 43. 为什么 Callback 应尽量短

Callback 通常运行在中断上下文中。

如果其中做很耗时的操作：

```text
当前中断上下文长期占用 CPU
↓
main 延迟
↓
不能抢占当前中断的其他 IRQ 也要等待
```

因此原则：

> **中断 / Callback 尽量短、尽量快。**

简单状态更新、GPIO 操作、重新挂接接收可以直接做；复杂业务更适合放到 main。

## 44. “中断记录状态，main 执行业务”

常见结构：

```text
UART Callback
→ 记录“发生了什么”
→ 快速退出

main
→ 读取记录
→ 真正执行
```

这与 8.9 非阻塞状态机的思想相通：

> 不让一个函数长期霸占 CPU，而是保存状态，让主循环继续推进。

## 45. `volatile` 的位置

当：

```text

main 读
```

同一个变量时，会涉及 `volatile`。

这个知识之前已经学过，今天只做唤醒。

> `volatile` 主要防止编译器把一个可能被“当前代码流之外”修改的变量错误优化成稳定不变。

同时：

> `volatile` 不等于自动解决所有并发、原子性和竞争条件问题。

## 46. 单个状态变量为什么不够

假设 UART 快速收到：

```text
A → B → C
```

如果每次只：

```c
command = rx_data;
```

那么：

```text
A 被 B 覆盖
B 又被 C 覆盖
```

main 最后可能只看到：

```text
C
```

因此单个变量适合：

> 保存“最新状态”。

## 47. 环形队列与 UART

如果需要保存每一个命令：

```text
UART Callback
→ push(A)
→ push(B)
→ push(C)
```

队列：

```text
[A][B][C]
```

main：

```text
pop A → 处理
pop B → 处理
pop C → 处理
```

所以环形队列的作用：

> **在 UART 接收端和主循环处理端之间暂存尚未处理的数据，并保持顺序。**

## 48. UART + 环形队列 + main 的代码结构

```c
uint8_t rx_data;

int main(void)
{
    // 初始化 UART
    // 初始化环形队列

    HAL_UART_Receive_IT(&huartX, &rx_data, 1);

    while (1)
    {
        uint8_t command;

        if (ring_buffer_pop(&cmd_queue, &command))
        {
            // 解析并执行 command
        }
    }
}

void HAL_UART_RxCpltCallback(UART_HandleTypeDef *huart)
{
    if (huart->Instance == USARTx)
    {
        ring_buffer_push(&cmd_queue, rx_data);
        HAL_UART_Receive_IT(huart, &rx_data, 1);
    }
}
```

职责：

```text
Callback
→ 收
→ 存
→ 重新挂接
→ 快速退出

main
→ 取
→ 解析
→ 执行业务
```

## 50. 今天较有价值的“讨论—修正—形成新模型”过程

### 50.1 Callback 模型的修正

Timer 阶段：

```text
IRQ → ISR → Handler → Callback
```

看起来很自然，因此容易把 Callback 当成中断机制的必经步骤。

UART 学习发现：

```text
一个 8 字节 Receive_IT 任务
```

可能经历多次中断，而 `RxCpltCallback()` 只在整个任务完成时执行。

最终重新建立：

```text
中断主链：
硬件事件 → IRQ → NVIC → ISR → HAL Handler

用户接口：
满足具体高层事件条件
→ Callback
→ 用户业务
```

最重要结论：

> **Callback 不是中断本身，但它把“中断发生后的用户业务逻辑”和底层中断处理解耦了。**

### 50.2 从“函数执行”到“任务生命周期”

通过 `HAL_UART_Receive_IT()` 明确：

```text
函数返回
≠
任务完成
```

函数只是启动任务，真正任务跨越未来的硬件接收和中断处理。

### 50.3 从“变量名”到“内存地址有效性”

学习 `rx_data` 时进一步理解：

```text
作用域
```

和：

```text
生命周期
```

是两个问题。

UART 异步 API 保存的是地址，因此比普通同步函数更需要关注缓冲区是否长期有效。

### 50.4 从“实时状态”到“事件缓冲”

单个变量：

```text
只保留最新值
```

环形队列：

```text
保存尚未处理的一系列数据
```

这让之前独立学习的环形队列真正进入 UART 通信场景。
