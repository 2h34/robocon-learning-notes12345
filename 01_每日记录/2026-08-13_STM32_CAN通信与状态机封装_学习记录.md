### 3.1 CAN 物理层与总线基本机制

今天首先学习了 CAN（Controller Area Network，控制器局域网络）的基本物理层。

CAN 使用两根差分信号线：

```text
CAN_H
CAN_L
```

总线主要依靠两线之间的差分电压表示逻辑状态。

当前建立的简化模型：

```text
显性位 Dominant = 0
隐性位 Recessive = 1
```

当不同节点同时发送时，显性 `0` 可以覆盖隐性 `1`。

CAN 使用差分信号的主要意义之一是抗共模干扰：

```text
外界干扰同时作用于 CAN_H 和 CAN_L
→ 两根线一起变化
→ 两者差值变化较小
→ 接收端仍能较可靠识别逻辑状态
```

总线物理两端通常需要各连接一个 `120 Ω` 终端电阻，用于抑制反射、保证高速通信下的信号完整性。

### 3.2 CAN 仲裁机制

CAN 是多节点总线，没有“某一个固定主机负责决定谁发送”。

多个节点同时发送时会根据 ID 逐位仲裁。

基本规律：

```text
发送 0，同时读到 0
→ 继续发送

发送 1，却读到 0
→ 说明其他节点发送了显性位
→ 当前节点失去仲裁
→ 停止本次发送，等待以后重新发送
```

因此：

> 数值更小的 CAN ID 具有更高的仲裁优先级。

需要注意：

- 仲裁失败不是通信错误；
- 不会因为正常失去仲裁而直接进入错误帧或 Bus-Off；
- ACK 与仲裁是两个不同阶段。

### 3.3 标准 ID 与扩展 ID

CAN 常见两种标识符：

```text
Standard ID：11 bit
最大值：0x7FF

Extended ID：29 bit
最大值：0x1FFFFFFF
```

本次老师作业中的命令 ID：

```text
0x01020101
0x01020201
```

都已经超过 `0x7FF`，因此必须使用 Extended ID。

HAL 构造扩展帧时主要需要：

```c
tx_header.ExtId = ...;
tx_header.IDE = CAN_ID_EXT;
```

而不是使用 `StdId`。

### 3.4 CAN 位时序与 1 Mbps 配置

今天继续巩固了 CAN Bit Timing。

本工程 APB1 时钟为：

```text
42 MHz
```

CAN Prescaler：

```text
3
```

BS1：

```text
9 Tq
```

BS2：

```text
4 Tq
```

因此一个 CAN Bit 包含：

```text
1 Tq（Sync Segment）
+ 9 Tq（BS1）
+ 4 Tq（BS2）
= 14 Tq
```

CAN 时间量子时钟：

```text
42 MHz / 3 = 14 MHz
```

最终波特率：

```text
14 MHz / 14 = 1 Mbps
```

采样点约为：

```text
(1 + 9) / 14 ≈ 71.4%
```

SJW（Synchronization Jump Width，同步跳转宽度）用于重新同步时进行相位补偿，不直接决定名义波特率。

### 3.5 bxCAN Filter：List Mode 与 Mask Mode

今天重点学习了 bxCAN 硬件过滤器。

需要区分：

```text
FilterBank
→ 过滤器资源编号

FilterMode
→ List / Mask

FilterScale
→ 16 bit / 32 bit
```

当前 STM32F405 的 bxCAN 有共享 Filter Bank。

本工程使用：

```c
filter.FilterBank = 0;
filter.SlaveStartFilterBank = 14;
```

表示 Bank 0 分配给 CAN1 使用。

本次作业只需要精确接收两个固定扩展 ID：

```text
0x01020101
0x01020201
```

因此选择：

```c
CAN_FILTERMODE_IDLIST
CAN_FILTERSCALE_32BIT
```

32-bit List Mode 一个 Filter Bank 可以保存两个 32-bit 匹配项，正好适合本题。

### 3.6 扩展帧 32-bit Filter 编码

bxCAN 过滤扩展帧时，29-bit ID 不能直接原样写进 Filter 寄存器。

本次使用：

```c
filter_id = (ExtId << 3) | 0x04U;
```

其中：

```text
bits 31:3 → ExtId[28:0]
bit 2     → IDE
bit 1     → RTR
bit 0     → 保留
```

`0x04U` 即设置 IDE 位，表示匹配扩展帧数据帧。

两个作业 ID：

```text
0x01020101 → 0x0810080C
0x01020201 → 0x0810100C
```

再分别拆成高 16 bit 和低 16 bit：

```c
filter.FilterIdHigh = (filter_id1 >> 16) & 0xFFFFU;
filter.FilterIdLow  = filter_id1 & 0xFFFFU;

filter.FilterMaskIdHigh = (filter_id2 >> 16) & 0xFFFFU;
filter.FilterMaskIdLow  = filter_id2 & 0xFFFFU;
```

这里需要特别注意：

> 在 32-bit List Mode 下，`FilterMaskIdHigh / Low` 这两个名字虽然带有 `Mask`，但实际用于保存第二个 List ID，而不是掩码。

### 3.7 CAN 初始化流程

根据当前模块化原则，将 CubeMX 自动生成的底层 CAN 初始化保留在：

```text
can.c / can.h
```

应用层 Filter、启动和通知配置放到：

```text
can_app.c / can_app.h
```

`can_app_init()` 中主要执行：

```c
HAL_CAN_ConfigFilter(&hcan1, &filter);
HAL_CAN_Start(&hcan1);
HAL_CAN_ActivateNotification(
    &hcan1,
    CAN_IT_RX_FIFO0_MSG_PENDING
);
```

理解：

```text
HAL_CAN_Init()
→ 初始化 CAN 外设参数

HAL_CAN_ConfigFilter()
→ 配置硬件过滤器

HAL_CAN_Start()
→ 让 CAN 外设真正进入工作状态

HAL_CAN_ActivateNotification()
→ 打开指定 CAN 中断源
```

最终在 `main.c` 初始化阶段调用：

```c
MX_CAN1_Init();
can_app_init();
```

### 3.8 CAN FIFO、IRQ、ISR、HAL Callback

今天进一步理清了 CAN 接收链路：

```text
CAN 总线收到完整帧
→ bxCAN 硬件判断帧是否合法
→ Filter 判断是否接收
→ 接收帧进入硬件 FIFO0
→ FIFO0 pending 条件触发
→ CAN1_RX0_IRQn
→ CAN1_RX0_IRQHandler()
→ HAL_CAN_IRQHandler(&hcan1)
→ HAL_CAN_RxFifo0MsgPendingCallback()
```

需要特别区分：

- FIFO 是 bxCAN 硬件内部接收队列；
- ISR 是硬件中断入口；
- `HAL_CAN_IRQHandler()` 是 HAL 对中断状态的统一处理；
- `HAL_CAN_RxFifo0MsgPendingCallback()` 是 HAL 提供给用户的回调接口；
- Callback 不是 CAN 硬件中断机制本身必需的一部分。

本工程 ISR 入口由 CubeMX 保留在：

```text
stm32f4xx_it.c
```

用户业务逻辑放在：

```text
can_app.c
```

### 3.9 `HAL_CAN_GetRxMessage()`

收到 FIFO0 pending 回调后，通过：

```c
HAL_CAN_GetRxMessage(
    hcan,
    CAN_RX_FIFO0,
    &can_rx_header,
    can_rx_data
);
```

将一帧 CAN 数据从硬件 FIFO 取出到用户变量中。

接收头：

```c
CAN_RxHeaderTypeDef can_rx_header;
```

数据缓冲区：

```c
uint8_t can_rx_data[8];
```

其中可以读取：

```text
IDE
RTR
DLC
ExtId / StdId
```

因此应用层先检查：

```c
IDE == CAN_ID_EXT
RTR == CAN_RTR_DATA
DLC == 1U
```

再根据 `ExtId` 识别具体命令。

beep_count = can_rx_data[0];

can_app_process(current_tick);

```c
BEEP_Trigger(current_tick, beep_count);
```

蜂鸣器模块内部继续使用之前完成的非阻塞状态机：

```text
IDLE
→ ON

→ ...

```

使用：

```c
beep_is_work()
```

判断任务是否真正结束。

只有：

```text
beep_workmode == 1
并且

```

才构造并提交回复帧。

这样满足：

> “蜂鸣器全部响完之后再回复。”

### 3.11 CAN 发送与 Tx Mailbox

CAN 发送使用：

```c
HAL_CAN_AddTxMessage(
    &hcan1,
    &tx_header,
    can_tx_data,
    &tx_mailbox
);
```

发送头：

```c
CAN_TxHeaderTypeDef tx_header = {0};
```

需要填写：

```c
tx_header.ExtId = ...;
tx_header.IDE = CAN_ID_EXT;
tx_header.RTR = CAN_RTR_DATA;
tx_header.DLC = ...;
tx_header.TransmitGlobalTime = DISABLE;
```

数据：

```c
can_tx_data[0] = 'O';
can_tx_data[1] = 'K';
```

这里虽然数组类型是：

```c
uint8_t
```

仍然可以直接保存字符 `'O'`、`'K'`，因为 CAN 数据本质上就是字节。

bxCAN 有 3 个发送 Mailbox。

```c
uint32_t tx_mailbox;
```

用于让 HAL 返回本次实际使用的发送邮箱。

需要注意：

> `HAL_CAN_AddTxMessage()` 返回 `HAL_OK`，表示帧已经成功提交到发送邮箱，并不代表该帧此刻已经完成物理总线发送和 ACK。

这再次体现：

```text
函数调用结束
≠
函数启动的硬件任务已经完成
```

### 3.13 LED 状态机封装优化

最初流水灯逻辑分散在：

```text
can_app.c
main.c
led.c
```

导致：

- CAN 模块保存 LED 当前状态；
- `main.c` 直接判断 LED 状态；
- LED 模块本身反而不能独立管理状态。

经过重构，将状态定义放回：

```text
led.h
```

例如：

```c
typedef enum
{
    STATE_OFF = 0,
    STATE_FLOW
} led_state_t;
```

当前状态由：

```text
led.c
```

负责维护。

对外主要通过：

```c
LED_Setmode(new_state, current_tick);
LED_Process(current_tick);
```

控制。

状态逻辑：

```text
STATE_OFF
进入动作：
→ 关闭 LED

持续动作：
→ 基本无持续任务

STATE_FLOW
进入动作：
→ LED1 ON
→ LED2 OFF
→ 初始化 flow_led_index
→ 保存当前 tick

持续动作：
→ 每 300 ms 切换 LED
```

### 3.14 `current_tick` 的处理

重构状态机时一度出现：

> `LED_Setmode()` 需要 `current_tick`，时间应该从哪里来？

最终采用参数逐层传递：

```text
TIM2
→ tick_2ms_count

main.c
→ can_app_process(tick_2ms_count)

can_app.c
→ LED_Setmode(STATE_FLOW, current_tick)

led.c
→ 记录 flow_last_switch_tick
```

CAN Callback 不保存任务开始时间。

因为：

> 真正开始执行任务的时刻是在主循环调用 `LED_Setmode()` / `BEEP_Trigger()` 时，而不是 Callback 收到命令时。

因此形成统一模式：

```text
中断 / Callback
→ 告诉系统“要做什么”

主循环
→ 决定“现在开始做”

业务模块
→ 记录“真正开始做的时间”
```

### 3.15 `main.c` 的模块化收敛

优化后主循环主要为：

```c
while (1)
{
    BEEP_Process(tick_2ms_count);
    can_app_process(tick_2ms_count);
    LED_Process(tick_2ms_count);
}
```

相比最开始：

```text
main.c 自己判断 LED 状态
main.c 自己执行具体 LED 行为
```

现在职责更清楚：

```text
main.c
→ 初始化 + 调度

can_app.c
→ CAN 应用协议、命令解析、请求产生、回复

beep.c
→ 蜂鸣器非阻塞状态机

led.c
→ LED 状态机与具体行为

can.c / stm32f4xx_it.c
→ CubeMX/HAL 底层 CAN 初始化与 ISR
```

## 4. 核心概念

### CAN

- 全称：Controller Area Network，控制器局域网络。
- 是什么：一种面向多节点、基于消息 ID 仲裁的串行总线通信协议。
- 当前用途：CANable 与 STM32 之间发送控制命令和状态回复。

### Dominant / Recessive

- Dominant：显性位，逻辑 `0`。
- Recessive：隐性位，逻辑 `1`。
- 仲裁中显性位可以覆盖隐性位。
- 当前作用：实现无破坏总线仲裁。

### CAN Arbitration

- 是什么：多个节点同时发送时，根据 ID 位逐位比较决定谁继续发送。
- 规律：数值更小的 ID 优先级更高。
- 注意事项：失去仲裁不是通信错误。

### Extended ID

- 是什么：29-bit CAN 标识符。
- 最大值：`0x1FFFFFFF`。
- 当前用途：老师作业中的 `0x01020101`、`0x01020201` 等 ID。

### Filter Bank

- 是什么：bxCAN 硬件过滤器资源。
- 当前用途：只允许老师指定的两个控制 ID 进入 FIFO0。
- 注意事项：Filter Bank 编号与 List/Mask 模式是不同概念。

### List Mode

- 是什么：按多个固定 ID 精确匹配。
- 当前用途：一个 32-bit Filter Bank 精确匹配两个扩展帧 ID。

### Mask Mode

- 是什么：通过 ID + Mask 对一类 ID 进行范围/位模式匹配。
- 当前作业：没有采用。

### FIFO

- 全称：First In First Out，先进先出队列。
- 当前用途：bxCAN 将通过 Filter 的接收帧暂存在硬件 FIFO0。
- 注意事项：CAN 帧不是直接进入 Callback，也不是直接进入用户数组。

### `HAL_CAN_RxFifo0MsgPendingCallback()`

- 是什么：HAL 提供的 FIFO0 接收消息待处理回调接口。
- 当前用途：从 FIFO0 取出帧并记录应用层请求。
- 注意事项：它属于 HAL 封装层，不是硬件 ISR 本身。

### `HAL_CAN_GetRxMessage()`

- 是什么：从指定 CAN 接收 FIFO 中读取一帧数据。
- 当前用途：把硬件 FIFO 中的 Header 和 Data 搬到用户变量。

### `HAL_CAN_AddTxMessage()`

- 是什么：将一帧 CAN 数据装入可用发送 Mailbox，并请求硬件发送。
- 当前用途：发送 `'O','K'` 和流水灯状态回复。
- 注意事项：返回 `HAL_OK` 只代表成功提交到发送邮箱，不代表物理发送已经完成。

### Entry Action 与 State Process

状态机中需要区分：

```text
Entry Action
→ 刚进入某个状态时只执行一次

State Process
→ 保持在该状态期间反复执行
```

例如：

```text
进入 STATE_FLOW
→ 初始化流水灯

保持 STATE_FLOW
→ 每 300 ms 切换 LED
```

这一区分是今天状态机封装优化的关键。

| 问题现象 | 原因 | 优化 / 解决过程 | 当前状态 |
|---|---|---|---|
| 一开始把 Filter Bank 理解成“只能过滤一个 ID” | 没区分 Bank、List Mode、Mask Mode | 明确 32-bit List Mode 一个 Bank 可保存两个 32-bit ID，正好匹配本题两个扩展 ID | 已理解 |

| 不清楚扩展帧 ID 为什么要左移 3 bit | 没有理解 bxCAN Filter 寄存器布局 | 学习 ExtId、IDE、RTR 在 32-bit Filter 中的位布局，并使用 `(ExtId << 3) \| 0x04U` | 已解决 |
| 一度把 Callback 当成 CAN 中断流程必然组成 | 没区分硬件 ISR、HAL Handler、HAL Callback | 重新划分“硬件 → HAL → 用户代码”三个层级 | 已理解 |
| 一开始 `can_app_init()` 没有在 `main.c` 调用 | 只写了应用层初始化函数但没有接入系统初始化流程 | 在 `MX_CAN1_Init()` 后调用 `can_app_init()` | 已解决 |
| 流水灯 Callback 的花括号存在逻辑风险 | `if` 嵌套范围不清晰 | 将 `ExtId == 0x01020201` 下的 `Data[0] == 0/1` 判断完整包裹 | 已解决 |
| 收到流水灯关闭命令后仍调用 `LED_FlowEnter()` | 开/关请求没有分流 | 在 `can_app_process()` 根据 `flow_target_state` 调用不同 LED 状态 | 已解决 |
| LED 当前状态放在 `can_app.c`，main 也直接使用 | 模块职责混乱 | 将 LED 状态归还 `led.c / led.h` 管理，CAN 只保存目标请求 | 已优化 |
| `main.c` 直接判断 LED 状态并控制行为 | main 承担过多具体业务 | 增加 `LED_Process()`，main 只做周期调度 | 已优化 |
| 不知道 `LED_Setmode()` 的 `current_tick` 从哪里获得 | 状态切换与时间记录的调用边界不清晰 | 将 tick 从 main → can_app → LED 模块逐层传递，在真正进入状态时记录时间 | 已解决 |

## 7. 今日总结

今天主要完成了 CAN 通信基础、bxCAN 过滤器、FIFO 接收、中断处理和 HAL 收发接口的学习，并将课堂知识落实到 STM32F405 的实际工程中。

在作业部分，实现了两个扩展帧命令：一个用于控制蜂鸣器按指定次数鸣叫，并在任务全部结束后回复 `'O','K'`；另一个用于控制流水灯开启/关闭并回复当前模式。

相比单纯写出 CAN 收发代码，今天更重要的进步是继续整理软件结构。最初 CAN、LED、main 之间的状态管理比较混乱，后续通过把 LED 状态归还 LED 模块、让 CAN 只保存请求、让 `main.c` 只负责调度，逐渐形成了更清晰的模块边界。

今天对状态机也有了更实际的认识：

```text
状态属于哪个模块
→ 由该模块自己保存

外部事件到来
→ 只提出状态切换请求

进入状态
→ 执行一次 Entry Action

停留在状态
→ 周期执行 State Process
```

当前软件已经达到 Keil：

```text
0 Error(s), 0 Warning(s)
```

但还没有完成 CANable 实物验证，因此当前属于“软件实现与编译完成，硬件验证待回收”的阶段。
