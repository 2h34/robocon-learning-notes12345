## 4. STM32 和 ZDrive 的职责边界

### STM32 负责

- 保存上层目标：valSetNow；
- 保存上一次已经发送的目标：valSetPre；
- 管理目标模式和反馈模式：mode、modeRead；
- 判断是否需要切换模式；
- 把上层单位转换为 ZDrive 协议单位；
- 根据 Node ID 和 CMD ID 生成 CAN 标准帧 ID；
- 打包 4 字节普通帧或 8 字节 PVT/心跳数据；
- 解析 ZDrive 反馈并更新软件变量。

### ZDrive 负责

- 接收 STM32 发送的模式和目标；
- 内部电流控制、速度控制和位置控制；
- 读取电机编码器；
- 进行驱动器内部保护和错误判断；
- 返回位置、速度、电流、模式和错误反馈。

和 DJI + C610 的区别：

    DJI：STM32 通常通过 C610 发送电流目标，C610 完成内部控制
    ZDrive：STM32 可以直接发送速度、位置或 PVT 目标，
            速度环、位置环和更底层电流控制由 ZDrive 完成

## 5. Zmotor 数据结构

位置：ZDrive.h，约 158-171 行。

| 变量 | 含义 |
|---|---|
| mode | STM32 希望 ZDrive 进入的目标模式 |
| modeRead | ZDrive 反馈回来的实际模式 |
| valSetNow | 当前希望发送的目标值 |
| valSetPre | 上一次已经发送的目标值 |
| valReal | ZDrive 反馈的实际位置、速度、电流 |
| statusFlag.err | 当前错误状态 |
| pvtparam.PVTflag | 是否使用 PVT 位置控制 |
| Begin | 是否允许该电机进入 ZdriveFunc 控制流程 |
| param.ReductionRatio | 代码中的减速比换算参数 |

必须区分：

    valSetNow = 想让电机达到什么状态
    valSetPre = 上次已经发过什么目标
    valReal   = 电机实际反馈是什么状态

## 6. 初始化和主循环

### 初始化调用链

位置：main.c，约 124-135 行。

    MX_CAN1_Init()
        ↓
    can_app_init()
        ↓
    DJI_motor_init()
        ↓
    ZdriveInit()

ZdriveInit() 将每个电机初始化为：

    mode = Zdrive_Disable
    modeRead = Zdrive_Disable
    Begin = false
    ReductionRatio = 1.0f

### 主循环调用频率

位置：main.c，约 152-164 行；tim.c 中为 TIM2 配置。

TIM2 周期为 2 ms，主循环每累计 50 次调用一次：

    50 × 2 ms = 100 ms
    ZdriveFunc() ≈ 10 Hz

这适合当前单次速度或位置目标测试，不适合高频 PVT 轨迹控制。

## 7. ZdriveFunc() 的完整逻辑

位置：ZDrive.c，约 489-519 行。

    遍历4个电机
        ↓
    Begin 是否为 true？
        ├─ false：跳过该电机
        └─ true：继续
                 ↓
            错误处理
                 ↓
            modeRead == mode？
            ├─ 否：Zdrive_SwitchMachine()
            └─ 是：Zdrive_RunMachine()
                 ↓
            广播查询 Pur 和 Vel

当前 ZdriveFunc() 末尾无论是否有活动电机，都会发送：

    ZdriveAsk(0, Pur)
    ZdriveAsk(0, Vel)

因此当前程序上电后并非完全没有 CAN 发送，但由于 Begin=false，不会发送电机运行目标。

## 8. 模式切换：Zdrive_SwitchMachine()

位置：ZDrive.c，约 409-430 行。

执行条件：

    motor->modeRead != motor->mode

### 速度模式切换

当前代码会执行：

    motor->valSetNow.speed_rpm = 0.f
    motor->valSetPre.speed_rpm = 0.f

这是一种安全设计：切换到速度模式时先清零速度目标。

实际影响是：如果上位机在模式确认前就写入速度目标，目标可能被清零。因此当前 Debug 测试时，应先等待：

    modeRead == Zdrive_Speed

再设置速度目标。

### 位置模式切换

当前代码会执行：

    motor->valSetNow.pos_deg = motor->valReal.pos_deg
    motor->valSetPre.pos_deg = motor->valReal.pos_deg

含义是进入位置模式时先用当前位置作为初始目标，避免电机突然跳到远处。

如果 Debug 提前写入 10°，而当前反馈位置是 2°，模式切换时目标会被改成 2°。

实际测试顺序应为：

    设置 Position 模式
        ↓
    等待 modeRead == Zdrive_Postion
        ↓
    再设置 valSetNow.pos_deg

模式准备好后，函数会发送：

    ZdriveSet((float)motor->mode, id, Mode)
    ZdriveAsk(id, Mode)

也就是：

    发送模式设置帧
        ↓
    发送模式查询帧
        ↓
    等待 ZDrive 反馈 modeRead

## 9. Zdrive_RunMachine() 的逻辑

位置：ZDrive.c，约 433-476 行。

### 速度模式

    if (fabs(speed_now - speed_pre) > 0.1f)

差值大于 0.1 rpm 才发送新目标。

差值小于等于 0.1 rpm 时：

    不重复发送
    不退出速度模式
    仍然保持速度模式

### 普通位置模式

当 PVTflag == false 时：

    if (fabs(pos_now - pos_pre) > 0.01f)

位置目标差值超过 0.01°，发送一次 PosIn。

### PVT 位置模式

当 PVTflag == true 时：

    ZdriveSetPVT(speed_rpm, pos_deg, id)

每次 ZdriveFunc() 都会发送 PVT 帧。当前调用频率约为 10 Hz，适合低频测试，不适合作为高频轨迹控制周期。

### 电流模式

当前分支只有注释：

    // ZdriveSet(motor->valSetNow.current_A, id, CurIn)

所以当前示例代码的电流模式尚未实现。

## 10. 发送链

    上层或 Debug 修改 Zmotor[i].valSetNow
        ↓
    ZdriveFunc()
        ↓
    Zdrive_SwitchMachine()
    或 Zdrive_RunMachine()
        ↓
    ZdriveSet()
    或 ZdriveSetPVT()
    或 ZdriveAsk()
        ↓
    生成 CAN ID 和 Data
        ↓
    Zdrive_SendDirect()
        ↓
    HAL_CAN_AddTxMessage(&hcan1, ...)
        ↓
    CAN1 发送到 ZDrive

### CAN ID 生成

代码使用：

    CAN_ID = NodeID | (CMD_ID << 4)

例如节点1的位置目标：

    PosIn = 0x24
    CAN ID = 1 | (0x24 << 4)
           = 0x241

### 普通4字节数据

官方指南的 can_write() 是：

    标准帧
    DLC = 4
    Data = float

当前 ZdriveSet() 与此一致。

当前上层接口单位和 ZDrive 协议单位的转换：

    速度：rpm → rps
    位置：deg → 圈

### 查询帧

官方指南的 can_read() 使用 DLC=0。当前 ZdriveAsk() 也使用 DLC=0。

### PVT 帧

官方指南要求：

    CMD ID = 0x39
    Byte0~3 = 速度归一化 uint32
    Byte4~7 = 位置归一化 uint32

当前 ZdriveSetPVT() 的顺序和打包方式一致。

## 12. ZdriveReceive() 如何解析反馈

位置：ZDrive.c，约 150-266 行。

### 解析 CAN ID

    control_id = StdId & 0x0F
    operation_id = StdId >> 4

例如：

    StdId = 0x241
    control_id = 1
    operation_id = 0x24

因此识别为节点1的 PosIn 数据。

### DLC=4

当前按 float 解析：

| CMD | 更新变量 | 代码中的换算 |
|---|---|---|
| Pur | valReal.pos_deg | 归一化圈 → deg |
| Vel | valReal.speed_rpm | rps → rpm |
| Cur_M | valReal.current_A | 直接使用 float |
| Mode | modeRead | float → 枚举 |
| Err | statusFlag.err | float → 枚举 |
| PosIn | valReal.posIn_deg | 归一化圈 → deg |

### DLC=8 心跳帧

官方指南的接收示例使用：

    位置：uint32_t
    速度：uint16_t
    电流：uint16_t

当前变量声明已经与指南一致：

    uint32_t tmp_pos
    uint16_t tmp_vel
    uint16_t tmp_cur

为什么速度和电流原始值是无符号：

    CAN原始编码范围：0~65535
    实际负号由换算公式产生

例如速度原始值：

    0x0000 → -Velocity_Limit
    0x8000 → 约0
    0xFFFF → +Velocity_Limit

所以不能把原始 0x8000 先解释成 int16_t=-32768。

## 13. 今天纠正的几个重要误区

### 误区1：差值小于0.1就退出速度模式

错误。它只是不重复发送速度目标，模式不会退出。

### 误区2：DLC=8的前4字节一定是 float

官方指南明确区分：

    DLC=4参数反馈：float
    DLC=8心跳反馈：uint32_t + uint16_t + uint16_t

### 误区3：负速度必须使用 int16_t 原始数据

错误。心跳帧原始值是无符号归一化编码，换算后才得到负速度或负电流。

### 误区4：上位机同时给模式和目标，就必须同一 CAN 帧发送

错误。上位机可以一次给出“模式+目标”，但 CAN 协议中 Mode、VelIn、PosIn 是不同 CMD，需要按顺序发送不同帧。

### 误区5：队列是 ZDrive 发送的必要条件

当前基础速度和普通位置控制可以采用直接发送。队列只涉及特定响应模式和轨迹执行方式，本项目暂时不采用队列。

## 15. 当前仍未完成或需要后续确认的内容

### 已确认的代码缺口

- Zdrive_Current 分支没有实际发送电流目标；
- Zdrive_ErrHandle() 仍是 TODO；
- Zdrive_SendDirect() 发送失败后没有记录、重试或报警；
- ZdriveSetPID() 当前使用 DLC=8 和归一化 uint32，与指南普通参数4字节 float 写入不一致；
- Answer_Mode 没有在当前程序中配置；
- 上位机模式和目标的一体化指令接口尚未编写；
- Zdrive_SwitchMachine() 目前会清零或覆盖速度/位置目标。

### 需要实际硬件确认的内容

- ZDrive 的 CAN 波特率是否确实为 1 Mbps；
- Node ID 是否和代码中的 i+1 对应；
- ZDrive 是否完成电机校准且无错误；
- ReductionRatio 是否符合实际机械传动关系；
- POU/POD、速度限制和电流限制是否与代码常量一致；
- 反馈帧实际是否按照指南格式返回；
- 单电机空载测试时，方向和位置正负号是否正确。

## 16. 上位机接入的推荐逻辑

上位机可以发送一个逻辑命令：

    node = 1
    mode = Position
    target = 10 deg

STM32收到后保存：

    mode = Position
    valSetNow = 10 deg
    Begin = true

之后由 ZdriveFunc() 自动完成：

    发现 modeRead != mode
        ↓
    发送 Mode 帧
        ↓
    收到 Mode 反馈
        ↓
    发现 modeRead == mode
        ↓
    发送 PosIn 目标帧

当前代码如果不修改，目标需要在模式确认后再写入。后续正式适配时，应修改模式切换逻辑，使其保留上位机目标，并在模式确认后强制发送一次目标。这个修改不需要引入发送队列。

## 19. 今日学习结论

当前 ZDrive 代码的核心不是“STM32重新实现一套 PID”，而是：

    STM32 管理目标和状态
        ↓
    按照 ZDrive 协议发送模式、速度、位置或 PVT 命令
        ↓
    ZDrive 完成内部电机控制
        ↓
    STM32 接收并保存反馈

当前程序已经具备基础速度和普通位置控制的代码链路，但仍属于“示例代码适配阶段”，还不是完整的上位机控制版本。后续修改重点应放在：

    上位机命令接口
    模式切换时保留目标
    直接发送失败处理
    错误处理
    PID参数协议修正
    实物反馈验证
