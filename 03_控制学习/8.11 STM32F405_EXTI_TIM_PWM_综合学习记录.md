## 三、STM32F405 工程基础配置

### 3.1 HAL Timebase

HAL 内部维护毫秒 Tick，例如 `uwTick`。`HAL_GetTick()` 本质上是读取 HAL 已维护的 Tick，而不是直接读取某个 Timer 的 CNT。

当前工程使用 TIM1 作为 HAL Timebase，典型链路：

```text
TIM1 每 1 ms 到期
→ TIM1 IRQ
→ HAL_TIM_IRQHandler()
→ HAL_TIM_PeriodElapsedCallback()
→ HAL_IncTick()
→ uwTick + 1
→ HAL_GetTick()
```

关键理解：

- `HAL_GetTick()` 不等于读取 TIM1 CNT。
- HAL Tick 的硬件来源可以是 SysTick，也可以是 TIM1。
- Timebase 解决的是“谁负责推进 HAL 的 1 ms 时间”。

### 3.2 HSE + PLL → 168 MHz

当前工程：

```text
HSE = 25 MHz
PLLM = 25
PLLN = 336
PLLP = 2
```

计算：

```text
25 MHz / 25 = 1 MHz
1 MHz × 336 = 336 MHz
336 MHz / 2 = 168 MHz
```

因此：

```text
SYSCLK = 168 MHz
```

继续经过总线分频：

```text
SYSCLK = 168 MHz
↓ AHB /1
HCLK = 168 MHz

APB1 /4
→ PCLK1 = 42 MHz
→ APB1 Timer Clock = 84 MHz

APB2 /2
→ PCLK2 = 84 MHz
→ APB2 Timer Clock = 168 MHz
```

F405 Timer Clock 规则：

```text
APB Prescaler = 1
→ Timer Clock = PCLK

APB Prescaler > 1
→ Timer Clock = 2 × PCLK
```

### 3.3 CubeMX 基本配置顺序

```text
① 选择 MCU
↓
② SYS / RCC
↓
③ Clock Configuration
↓
④ GPIO / TIM / UART / CAN 等外设
↓
⑤ NVIC / DMA
↓
⑥ Generate Code
↓
⑦ 检查生成代码
↓
⑧ 编写用户模块
↓
⑨ 编译
↓
⑩ 下载 / 实物验证
```

核心因果关系：

```text
时钟决定外设计时基础
↓
外设配置决定硬件行为
↓
NVIC决定CPU是否响应中断
↓
HAL封装底层流程
↓
用户代码完成业务逻辑
```

### 3.4 USER CODE 与模块化边界

CubeMX 自动生成区域可能在重新 Generate Code 时被覆盖，因此用户补充代码应放进 `USER CODE BEGIN/END` 区域。

但 USER CODE 只是“防覆盖区域”，并不代表所有业务逻辑都应写进 `main.c`。

后续继续采用：

```text
main.c
→ 初始化 + 调度

led.c / led.h
→ LED功能

beep.c / beep.h
→ 蜂鸣器

key.c / key.h
→ 按键

state_machine.c / state_machine.h
→ 状态机
```

CubeMX 自动生成的 ISR 入口，如 `TIM2_IRQHandler()`、`EXTI15_10_IRQHandler()`，仍保留在 `stm32f4xx_it.c` 等生成文件中。

## 四、EXTI 外部中断

EXTI = External Interrupt/Event Controller，外部中断/事件控制器。

GPIO 负责当前电平：

```text
HIGH / LOW
```

EXTI 负责检测：

```text
LOW → HIGH：上升沿
HIGH → LOW：下降沿
```

### 4.1 EXTI Line、Pending、IRQ、ISR

```text
EXTI Line
→ 负责监视哪一路边沿

Pending Flag
→ 记录某条 EXTI 已触发、等待处理

IRQ
→ 向 NVIC 提交的中断请求

ISR
→ CPU 实际进入执行的中断服务函数
```

PC11 的完整链路：

```text
PC11 电平变化
↓
EXTI11 检测有效边沿
↓
EXTI11 Pending = 1
↓
产生 EXTI15_10_IRQn
↓
NVIC 判断是否响应
↓
CPU进入 EXTI15_10_IRQHandler()
↓
HAL_GPIO_EXTI_IRQHandler()
↓
HAL 清 Pending
↓
HAL_GPIO_EXTI_Callback()
↓
用户按键逻辑
```

### 4.2 Pending Flag

Pending 表示“这条中断线有一个尚待处理的事件”。

它与 GPIO 当前电平不同。

例如：

```text
GPIO = HIGH
Pending = 0
```

完全可能。

经典 STM32F4 HAL 流程中：

```text
Pending = 1
↓
进入 HAL Handler
↓
HAL 清 Pending：1 → 0
↓
再调用 Callback
```

因此用户 Callback 执行时，对应 Pending 通常已经被 HAL 清除。

### 4.3 EXTI11 与 EXTI15_10_IRQn

GPIO 外部中断线通常按 Pin 编号对应：

```text
Px11 → EXTI11
```

PA11、PB11、PC11 都对应 EXTI11，因此会竞争同一条 EXTI Line。

STM32F405 中：

```text
EXTI0~4 → 各自独立 IRQ
EXTI5~9 → 共用 EXTI9_5_IRQn
EXTI10~15 → 共用 EXTI15_10_IRQn
```

因此 PC11 最终进入 `EXTI15_10_IRQHandler()`。

## 五、NVIC 与中断优先级

NVIC = Nested Vectored Interrupt Controller，嵌套向量中断控制器。

负责：

- IRQ 是否启用
- 中断优先级
- 多个中断同时出现时谁先执行
- 是否允许更高优先级中断抢占当前 ISR

规则：

```text
数字越小
→ 优先级越高
```

例如：

```text
EXTI = 0
TIM2 = 5
TIM1 = 15
```

则优先级：

```text
EXTI > TIM2 > TIM1
```

### 5.1 抢占优先级与子优先级

```text
Preempt Priority
→ 决定能不能抢占

Sub Priority
→ 抢占优先级相同时决定谁先被服务
```

### 5.2 ISR 中避免长时间阻塞

如果 EXTI 优先级高于 TIM1，而 TIM1 又负责 HAL Tick，那么在 EXTI Callback 中调用 `HAL_Delay()` 可能导致 HAL Tick 无法推进。

因此 ISR 应尽量只做：

```text
读取必要状态
记录数据
设置事件/标志
快速退出
```

业务逻辑放到主循环或模块任务中。

## 六、双边沿 EXTI 与按键识别

经典 STM32F4 HAL Callback：

```c
void HAL_GPIO_EXTI_Callback(uint16_t GPIO_Pin)
```

参数只告诉用户“哪个 Pin 触发”，不会直接告诉用户是上升沿还是下降沿。

因此双边沿模式下，使用：

```c
HAL_GPIO_ReadPin(...)
```

读取当前电平，再结合按键电气定义推断。

当前按键：

```text
默认 LOW
按下 HIGH
```

因此正常情况下：

```text
Callback 中读到 HIGH
→ 推断按下 / 上升沿

读到 LOW
→ 推断松开 / 下降沿
```

注意：`HAL_GPIO_ReadPin()` 读的是“当前电平”，不是“边沿类型”。

## 七、短按 / 长按与消抖

### 7.1 当前作业方案

按下：

```c
press_time = now;
```

松开：

```c
if (now - press_time >= LONG_PRESS_MS)
    key_event = KEY_LONG;
else
    key_event = KEY_SHORT;
```

因此当前实现准确描述为：

> 松开时，根据按压持续时间分类短按或长按。

### 7.2 达到阈值立即触发长按

如果以后要求：

```text
按住满 1000 ms
→ 立即 KEY_LONG
```

则需要记录本轮按压是否已经产生过长按事件，例如 `long_triggered`。

因为：

```text
now - press_time >= 1000
```

是一个会持续成立的条件，而 `KEY_LONG` 应是一次性事件。

### 7.3 消抖

当前使用：

```c
if (now - last_edge_time < KEY_DEBOUNCE_MS)
{
    return;
}
```

本质：

> 接受一个边沿后，在一定时间窗口内拒绝其它边沿。

这是边沿时间过滤，并不等于“连续稳定 20 ms 后才确认状态”。

## 八、`__weak` 与 HAL Callback

HAL 常提供：

```c
__weak void HAL_GPIO_EXTI_Callback(uint16_t GPIO_Pin)
{
}
```

用户再写一个同名非 weak 函数：

```c
void HAL_GPIO_EXTI_Callback(uint16_t GPIO_Pin)
{
    // 用户代码
}
```

链接阶段优先采用用户的强定义。

关键边界：

```text
__weak
→ 决定最终选择哪个实现

HAL内部的函数调用
→ 决定这个 Callback 什么时候被调用
```

## 九、`##` Token Pasting

例如：

```c
#define LED_ON(x)     HAL_GPIO_WritePin(LED##x##_GPIO_Port,                       LED##x##_Pin,                       GPIO_PIN_SET)
```

调用：

```c
LED_ON(1);
```

预处理器会把：

```text
LED ## 1 ## _GPIO_Port
```

拼成：

```c
LED1_GPIO_Port
```

`##` 是 Token Pasting Operator，记号粘贴运算符。

它只负责预处理阶段拼接 token，不理解 GPIO、PWM 等硬件语义。

## 十、TIM2 周期 Tick

作业中：

```c
static volatile uint32_t tick_2ms_count = 0;
```

TIM2 每 2 ms：

```c
tick_2ms_count++;
```

### 10.1 flag 与 counter

`bool flag` 只能表示：

```text
至少发生过一次
```

不能保留次数信息。

计数器可以保留：

```text
时间推进了多少
```

但：

```text
counter保住时间信息
≠
业务任务没有漏执行
```

### 10.2 硬件 Tick 准确 ≠ 业务绝对准时

TIM2 可以严格每 2 ms Tick 一次，但主循环可能由于其它任务延迟。

因此：

```text
硬件时间基准准确
≠
业务一定在目标时刻零延迟执行
```

### 10.3 `last_tick = current_tick` 与 `+= interval`

```c
last_tick = current_tick;
```

表示从本次实际执行时间重新计时。

```c
last_tick += interval;
```

表示尽量保持原计划时间轴。

流水灯这种视觉任务使用 `last_tick = current_tick` 完全合理。

### 10.4 实时任务不能简单补执行

如果电机控制要求每 2 ms 采样一次，但阻塞 20 ms 后再连续补算 10 次，并不等价于过去每 2 ms 正常计算一次。

原因：

- 时间点不同
- 输入数据不同
- 历史状态无法恢复

### 10.5 `uint32_t` Tick 回绕

2 ms Tick 使用 `uint32_t`，约 99 天会回绕：

```text
0xFFFFFFFF → 0
```

但采用：

```c
current_tick - last_tick >= interval
```

这种无符号时间差判断可以正确应对正常回绕。

## 十一、PWM 工程应用

### 11.1 初始化、启动、修改、停止

初始化：

```c
MX_TIM3_Init();
```

启动：

```c
HAL_TIM_PWM_Start(&htim3, TIM_CHANNEL_1);
```

修改 CCR：

```c
__HAL_TIM_SET_COMPARE(&htim3, TIM_CHANNEL_1, value);
```

停止：

```c
HAL_TIM_PWM_Stop(&htim3, TIM_CHANNEL_1);
```

### 11.2 PWM 是硬件持续生成的

`HAL_TIM_PWM_Start()` 返回之后，TIM3 仍然继续由硬件：

```text
CNT持续计数
↓
CNT与CCR比较
↓
自动控制PWM输出
```

因此：

> 函数调用结束，不代表它启动的硬件任务结束。

### 11.3 `CCR=0` 不等于 PWM Stop

```c
__HAL_TIM_SET_COMPARE(..., 0);
```

表示 PWM 通道仍运行，只是占空比变为 0%。

真正停止需要 `HAL_TIM_PWM_Stop()`。

### 11.4 PWM 载波频率与 CCR 更新频率

作业 TIM3：

```text
Timer Clock = 84 MHz
PSC = 83
ARR = 999
```

得到：

```text
CNT Clock = 1 MHz
PWM周期 = 1 ms
PWM频率 = 1 kHz
```

呼吸灯约每 2 ms 更新一次 CCR，所以：

```text
PWM载波频率 = 1 kHz
CCR更新频率 ≈ 500 Hz
```

两者不是一个概念。

### 11.5 PSC / ARR / CCR

```text
fPWM = TimerClock / ((PSC + 1)(ARR + 1))
```

其中：

```text
PSC
→ 决定 CNT Clock

ARR
→ 决定一个周期的计数范围

CCR
→ 决定比较位置 / 占空比
```

同样 1 kHz PWM：

```text
PSC=83，ARR=999
PSC=41，ARR=1999
```

都可以实现，但后者 ARR 更大，可调 CCR 档位更多，占空比分辨率更高。

## 十二、综合作业：按键状态机

作业要求：

- 初始四灯全灭
- 长按进入流水灯
- 短按进入呼吸灯
- 状态切换加入蜂鸣器
- 按键默认低电平，按下高电平
- 输入使用 RX 功能对应引脚

实际使用：

```text
PC11
→ RX 功能引脚
→ 配置为 GPIO_EXTI11
```

### 12.1 状态与事件

```c
typedef enum
{
    STATE_OFF = 0,
    STATE_FLOW,
    STATE_BREATH
} led_state_t;

typedef enum
{
    KEY_NONE = 0,
    KEY_SHORT,
    KEY_LONG
} key_event_t;
```

状态规则：

```text
SHORT → BREATH
LONG  → FLOW
```

重复进入同一状态时不重新触发蜂鸣器。

### 12.2 中断与业务解耦

```text
EXTI Callback
→ 记录按键时间
→ 生成 KEY_SHORT / KEY_LONG
→ 快速退出

main
→ 消费 key_event
→ 状态机切换
→ LED / BEEP 模块执行
```

### 12.3 流水灯

LED1、LED2 为普通 GPIO，约每 300 ms 交替亮灭。

TIM2 2 ms Tick：

```text
150 tick = 300 ms
```

进入流水灯时还需要清理 TIM3 PWM 输出效果。

### 12.4 呼吸灯

LED3 / LED4 使用 TIM3 CH1 / CH2：

```c
CCR1 = breath_value;
CCR2 = 999U - breath_value;
```

实现反向呼吸。

### 12.5 蜂鸣器

状态真正变化时触发蜂鸣器。

不使用 `HAL_Delay()`，而是：

```text
记录开始 Tick
↓
主循环 BEEP_Process()
↓
到时间后关闭
```

实现非阻塞控制。

## 十三、学习过程中出现的问题与纠正

### 13.1 Timer Clock ×2 规则不熟

最终明确：

```text
APB Prescaler = 1
→ Timer Clock = PCLK

APB Prescaler > 1
→ Timer Clock = 2 × PCLK
```

### 13.2 Timer 周期单位判断错误

1 MHz CNT：

```text
1 tick = 1 μs
1000 tick = 1 ms
```

### 13.3 按键高低电平判断写反

当前硬件：

```text
默认 LOW
按下 HIGH
```

因此：

```text
GPIO_PIN_SET → 按下
GPIO_PIN_RESET → 松开
```

### 13.4 呼吸灯 CH2 初始逻辑错误

两路都写 `breath_value` 会同步变化。

正确：

```c
CCR1 = breath_value;
CCR2 = 999U - breath_value;
```

### 13.5 停止调用函数 ≠ PWM 停止

不再调用 `LED_BreathProcess()` 只意味着 CPU 不再修改 CCR，不意味着 TIM3 硬件停止。

这是本次很重要的“软件函数边界 vs 硬件任务边界”理解。

### 13.6 `tick_flag` 与计数器

明确：

```text
flag
→ 只记录是否发生

counter
→ 记录时间推进量
```

同时明确：

```text
时间信息没丢
≠
周期业务不会漏执行
```

## 十五、本次最值得记住的工程经验

1. 硬件机制、HAL 封装、用户代码、业务逻辑要分层理解。
2. Callback 是 HAL 的用户扩展接口，不是硬件中断机制的必需组成。
3. ISR 应尽量短，不要在高优先级 ISR 中做长阻塞。
4. 硬件 Timer 准时，不代表主循环业务绝对准时。
5. 函数返回，不代表该函数启动或配置的硬件任务已经结束。
6. 状态条件和一次性事件不是同一个概念。
7. `current_tick - last_tick` 是常用的无符号计时方式，可正确处理正常计数回绕。
8. PWM 频率与占空比更新频率是两个不同概念。
9. 同频率 PWM 下，ARR 更大通常意味着更高的占空比分辨率。
10. `main.c` 尽量保持初始化与调度，具体功能按模块封装。
