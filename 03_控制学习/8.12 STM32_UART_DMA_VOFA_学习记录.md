## 3. UART 接收方式复习

今天重点比较了几种 HAL UART 接收方式：

```c
HAL_UART_Receive_IT()
HAL_UARTEx_ReceiveToIdle_IT()
HAL_UART_Receive_DMA()
HAL_UARTEx_ReceiveToIdle_DMA()
```

| 接收方式 | 长度特点 | 数据搬运 | 是否利用 IDLE |
|---|---|---|---|
| `HAL_UART_Receive_IT()` | 固定长度 | CPU/HAL 中断路径 | 否 |
| `HAL_UARTEx_ReceiveToIdle_IT()` | 可提前结束当前批次 | CPU/HAL 中断路径 | 是 |
| `HAL_UART_Receive_DMA()` | 固定长度 | DMA | 否 |
| `HAL_UARTEx_ReceiveToIdle_DMA()` | 适合不定长批次 | DMA | 是 |

今天实际使用：

```c
HAL_UARTEx_ReceiveToIdle_DMA()
```

因为它同时具备：

- DMA 自动搬运数据；
- UART IDLE 可以帮助判断“这一批数据暂时收完”；
- 比固定长度接收更适合上位机发送不定长字符串。

## 4. DMA 的核心理解

### 4.1 DMA 是什么

DMA：

```text
Direct Memory Access
直接存储器访问
```

它的作用不是让 UART 线路本身传输得更快，而是让 DMA 控制器代替 CPU 完成外设寄存器与 RAM 之间的大量数据搬运。

UART RX 的简化数据链：

```text
外部串口数据
    ↓
UART 硬件接收
    ↓
USART 数据寄存器
    ↓
UART 产生 DMA 请求
    ↓
DMA 读取 UART 数据寄存器
    ↓
DMA 写入 RAM 中的 rx_buffer
```

因此：

- UART 负责“收”；
- DMA 负责“搬”；
- CPU 负责配置、事件处理和业务逻辑。

### 4.2 “启动 DMA 接收”与“DMA 自动搬运”

CubeMX 中配置 DMA，并不等于程序已经开始接收。

真正启动一次接收任务的是：

```c
HAL_UARTEx_ReceiveToIdle_DMA(&huart1, rx_buffer, sizeof(rx_buffer));
```

调用之后：

```text
CPU 配置好这一轮任务
    ↓
函数返回
    ↓
UART + DMA 在硬件层继续工作
```

非常重要：

> HAL 函数调用结束，不等于它启动的异步接收任务已经结束。

这是今天对“函数任务边界”的一个重要理解。

## 5. UART IDLE 事件

### 5.1 IDLE 是什么

UART IDLE 是 UART 硬件检测到接收线空闲的一种事件。

可以简单理解为：

```text
收到若干字节
    ↓
之后一段时间没有继续收到新的字节
    ↓
UART 检测到 IDLE
```

但是必须注意：

> IDLE 不是协议里的“包尾”。

UART 硬件并不知道“这一批数据是不是完整协议包”，它只知道“接收线现在空闲了”。所以 IDLE 是一种硬件事件，不是业务协议边界。

### 5.2 ReceiveToIdle 中的 `Size`

调用：

```c
HAL_UARTEx_ReceiveToIdle_DMA(...)
```

后，DMA 会不断向 `rx_buffer` 中写入数据。

当出现接收事件时，HAL 可以进入：

```c
HAL_UARTEx_RxEventCallback(UART_HandleTypeDef *huart, uint16_t Size)
```

对于今天这种 Normal DMA、从缓冲区头开始接收的简单场景，可以把 `Size` 理解为本批有效数据长度/有效数据位置。

例如发送：

```text
1011
```

常见情况下：

```text
Size = 4
```

主循环只需要处理：

```c
rx_buffer[0] ~ rx_buffer[3]
```

而不是遍历整个 64 Byte 缓冲区。

## 6. Callback 的层级理解

今天进一步明确了 IRQ、ISR、HAL Handler、Callback 之间的层级关系。

简化流程：

```text
硬件事件
    ↓
IRQ（Interrupt Request，中断请求）
    ↓
NVIC
    ↓
ISR（Interrupt Service Routine，中断服务程序入口）
    ↓
HAL_UART_IRQHandler()
    ↓
HAL 内部判断具体事件
    ↓
HAL_UARTEx_RxEventCallback()
    ↓
用户代码
```

因此：

> Callback 可以很好地融入中断流程，但 Callback 本身不是硬件中断机制必需的一部分。

用户 Callback 是 HAL 提供给业务代码的接口。


这样：

```text

```

整体结构更清晰。

### 7.2 ASCII `'1'` 与数值 `1`

本题代码统计的是：

```c
if (rx_buffer[i] == '1')
{
    count++;
}
```

这里 `'1'` 表示 ASCII 字符 `'1'`，其字节值是：

```text
0x31
```

它和数值：

```text
0x01
```

不是同一个东西。

如果上位机发送字符串：

```text
1011
```

实际 UART 字节是：

```text
31 30 31 31
```

代码可以正确统计 `'1'`。

如果上位机使用 Hex 模式发送：

```text
01 00 01 01
```

则当前代码不会把 `0x01` 当成字符 `'1'`。

## 8. 非阻塞蜂鸣器多次鸣叫

最初如果直接写：

```c
for (...)
{
    BEEP_ON();
    HAL_Delay(...);
    BEEP_OFF();
    HAL_Delay(...);
}
```

虽然容易实现，但会阻塞整个 `main` 主循环，会影响 UART 处理、LED 状态机和其他实时任务。

因此今天沿用了之前的非阻塞思路，把蜂鸣器设计成状态机。

核心状态：

```c
typedef enum
{
    BEEP_STATE_IDLE = 0,
    BEEP_STATE_ON,
    BEEP_STATE_OFF
} beep_state_t;
```

核心状态数据：

```text
当前状态 beep_state
剩余响声次数 beep_remain
当前阶段开始时间 beep_start_tick
```

运行逻辑：

```text
BEEP_Trigger(count)
    ↓
开始第一次 ON

BEEP_Process()
    ↓
ON 时间到
    ↓
关闭蜂鸣器
    ↓
剩余次数 -1
    ↓
进入 OFF

OFF 时间到
    ↓
如果还有剩余次数
    ↓
再次 ON

全部完成
    ↓
IDLE
```

关键理解：

> `beep_remain` 表示“还剩多少次完整鸣叫任务”，应该在一次 ON 阶段真正完成后再减少。

## 9. 作业 1 中遇到的问题

### 9.1 不应该重复调用 `BEEP_Trigger()`

一开始如果统计出 `count` 后再写：

```c
for (uint16_t i = 0; i < count; i++)
{
    BEEP_Trigger(current_tick, count);
}
```

实际上是在重复覆盖启动同一个蜂鸣任务。

正确思路是：

```c
BEEP_Trigger(current_tick, count);
```

只启动一次，因为多次鸣叫已经由蜂鸣器内部状态机负责完成。

这里体现了模块化原则：

> 调用者只告诉模块“我要响几次”，具体怎样分阶段完成由蜂鸣器模块内部负责。

### 9.2 `main` 很快，为什么还会讨论 buffer 覆盖

当前主循环很简单，处理速度非常快。

USART1 为 115200 baud，8N1 时：

```text
1 Byte ≈ 10 bit
10 / 115200 ≈ 86.8 μs
```

因此发送几个字符本身就需要几百微秒，而 STM32F405 主循环处理几个字节通常远小于这个时间。

对于今天这种：

```text
人工点击发送
→ 等待蜂鸣
→ 再发送下一条
```

的测试方式，buffer 被下一批数据覆盖的实际风险很低。

但是从机制上仍然存在竞争：

```text
Callback 重新启动 DMA
    ↓
DMA 已经可以再次写 rx_buffer

同时：

main 可能正在读取 rx_buffer
```

因此：

> “当前 main 足够快，实际很难出问题”不等于“程序结构从机制上保证不会出现竞争”。

今天只需要知道这个问题存在，不要求立即使用双缓冲或队列。

## 11. VOFA+ RawData 与 JustFloat

### 11.1 RawData

RawData 可以理解为：

> VOFA+ 不主动把收到的字节解释成浮点采样数据，而是把它当普通原始数据流使用。

适合：

- 串口助手；
- 手动发送字符串；
- 查看原始收发数据；
- 作业 1 中发送 `1011`。

作业 1 的方向：

```text
VOFA+
    ↓ 发送字符串
STM32
    ↓ 接收并处理
```

### 11.2 JustFloat

JustFloat 用于：

> 把一帧中的二进制 `float` 数据解析为采样通道，用于波形显示。

作业 2 的方向正好相反：

```text
STM32
    ↓ 发送 float 数据
VOFA+
    ↓ JustFloat 解析
    ↓ 波形显示
```

因此 RawData 和 JustFloat不是两种 UART。底层仍然是同一个 USART1，区别在于 VOFA+ 如何解释收到的字节。

## 12. `float` 与字符串的区别

今天作业 2 的一个核心知识是：

```c
float value = 0.5f;
```

和：

```c
char str[] = "0.5";
```

完全不是同一种数据。

字符串 `"0.5"` 在内存中是字符：

```text
'0' '.' '5' '\0'
```

而 `float value = 0.5f;` 在 STM32F405 中通常占 4 Byte，并按照二进制浮点格式存储。

JustFloat 要的是：

> `float` 的原始 4 Byte 二进制内容，而不是字符串 `"0.5"`。

## 13. `memcpy()`

### 13.1 基本语法

```c
memcpy(目标地址, 源地址, 复制字节数);
```

例如：

```c
memcpy(tx_buffer, &value, sizeof(float));
```

表示：

```text
从 value 的内存地址开始
    ↓
读取 sizeof(float) Byte
    ↓
原样复制到 tx_buffer
```

这里没有进行字符串转换、数值转换或浮点转整数，只是纯粹复制内存字节。

今天已经确认：

```text
memcpy() = 原始字节复制
```

## 14. JustFloat 数据帧拼接

今天使用单通道，只发送一个 `float`。

因此：

```text
float 数据：4 Byte
JustFloat 包尾：4 Byte
总计：8 Byte
```

发送 buffer：

```c
uint8_t tx_buffer[8];
```

结构：

```text
tx_buffer

[0] [1] [2] [3] | [4] [5] [6] [7]
 └─ float 4Byte ─┘   └─ 包尾 4Byte ─┘
```

JustFloat 使用的 4 Byte 包尾：

```c
uint8_t tail[4] = {
    0x00,
    0x00,
    0x80,
    0x7F
};
```

拼接：

```c
memcpy(&tx_buffer[0], &value, sizeof(float));
memcpy(&tx_buffer[4], tail, 4);
```

第二次从 `tx_buffer[4]` 开始，是因为 `tx_buffer[0] ~ tx_buffer[3]` 已经被前面的 float 占用了。

## 15. 正弦波如何产生

VOFA+ 并不是自己生成正弦波。

真正的数据由 STM32 产生：

```c
value = sinf(x);
```

然后：

```c
x += 0.1f;
```

每调用一次函数就得到一个新的正弦采样点。

例如：

```text
x = 0.0 → sin(x) ≈ 0
x = 0.1 → sin(x) ≈ 0.0998
x = 0.2 → sin(x) ≈ 0.1987
...
```

这些值不断发送给 VOFA+，VOFA+ 把它们按接收顺序显示为连续采样点，最终看到正弦波。

为了避免 `x` 无限增大：

```c
if (x >= 6.2831853f)
{
    x -= 6.2831853f;
}
```

也就是让相位在大约 `0 ~ 2π` 范围内循环。

## 16. 最终 `vofa_app` 模块

今天新建：

```text
vofa_app.c
vofa_app.h
```

`vofa_app.h` 对外只暴露：

```c
void vofa_app_process(void);
```

`vofa_app.c` 的核心实现：

```c
#include "vofa_app.h"
#include "usart.h"
#include <stdint.h>
#include <string.h>
#include <math.h>

void vofa_app_process(void)
{
    static float x = 0.0f;

    float value = sinf(x);

    x += 0.1f;

    if (x >= 6.2831853f)
    {
        x -= 6.2831853f;
    }

    uint8_t tx_buffer[8];
    uint8_t tail[4] = {0x00, 0x00, 0x80, 0x7F};

    memcpy(&tx_buffer[0], &value, sizeof(float));
    memcpy(&tx_buffer[4], tail, 4);

    HAL_UART_Transmit(&huart1, tx_buffer, sizeof(tx_buffer), 10);
}
```

当前版本使用：

```c
HAL_UART_Transmit()
```

也就是阻塞式发送。

本次只发送 8 Byte，115200 baud 下发送时间很短，因此为了老师作业的最小复现，当前实现可以接受。

后续如果用于高频采样、多通道数据、电机控制、PID 或复杂机器人主循环，再考虑 `HAL_UART_Transmit_DMA()` 并进一步处理 TX buffer 生命周期问题。

## 17. VOFA+ 波形显示

STM32 发送的只有：

```c
value = sinf(x);
```

并没有把内部变量：

```c
x
```

发送出去。

因此 VOFA+ 中 `i0` 对应当前唯一的 float 数据 `sin(x)`。

波形图设置：

```text
Y 轴：i0
X 轴：保持默认
```

这里 X 轴可以理解为采样点到达的先后顺序，不是 STM32 内部的变量 `x`。

最终 Y 值大约在：

```text
-1 ~ +1
```

之间周期性变化。

## 19. 今天遇到的主要问题与修正

### 问题 1：对 DMA buffer 覆盖风险理解过度复杂

一开始讨论了：

```text
Callback 重新启动 DMA 后
DMA 可能重新写 rx_buffer
main 同时读取 rx_buffer
```

这从工程机制上确实存在风险。

但是今天实际：

- buffer 只有 64 Byte；
- 上位机人工发送；
- 每次只有几个字符；
- STM32 主循环非常快；
- 两次人工发送间隔远远大于主循环处理时间。

因此当前作业中实际风险很低。

最终处理：

```text
当前方案保持不变
后续高速连续通信再解决
```

### 问题 2：Half Transfer 被过早拿来作为代码问题

前面只简单提到 HT、TC、IDLE，但是没有真正系统学习，后面检查代码时又突然把 HT 当作“需要处理的问题”，导致学习节奏不一致。

最终重新分类：

```text
HT / TC
→ 已知道存在
→ 尚未系统学习
→ 当前作业不要求处理
→ 后续 DMA 进阶阶段学习
```

### 问题 3：误以为 VOFA 勾选变量后自己产生正弦波

## 23. 今日工程经验

### 经验 1：不要把“当前能工作”和“机制上绝对安全”混为一谈

今天简单人工发送时 `main` 足够快，所以单 buffer 实际工作正常。

但以后连续高速数据时：

```text
DMA 写
+
CPU 读
```

可能同时发生。工程上需要根据实际数据速率和任务复杂度选择方案。

### 经验 2：Callback 中尽量不要堆复杂业务

今天采用：

```text
Callback
→ 记录 Size / 设置 flag

main
→ 真正处理数据
```

更利于后续扩展。

### 经验 3：模块对外提供“业务接口”，内部细节由模块自己完成

例如蜂鸣器：

```c
BEEP_Trigger(current_tick, count);
```

调用者只告诉模块需要响 `count` 次，而不是自己在外面循环控制 ON/OFF，这能降低模块之间的耦合。

### 经验 4：源资料优先，避免给简单作业过度设计

老师本次 VOFA 作业的目标主要是：

```text
学会 float 字节拼接
学会 JustFloat
完成正弦波显示
```

因此不需要为了“更工程化”提前加入过多采样与 DMA TX 机制。

正确做法是：

```text
先满足老师要求
↓
完成验证
↓
再在后续学习工程化改进
```
