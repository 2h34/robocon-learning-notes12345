## 二、学习路线与知识点

### 1. UART 基础概念

UART（Universal Asynchronous Receiver/Transmitter，通用异步收发器）是 STM32 内部用于串行通信的硬件外设。

更准确地理解：

- CPU 把待发送的数据交给 UART；
- UART 按规定的帧格式和时序将数据串行输出到 TX；
- UART 从 RX 接收串行电平变化，并重新恢复成数据；
- UART 负责“通信”，用户程序再决定收到的数据代表什么业务含义。

UART 不是简单的“把数据变成电信号”，因为 CPU 内部的数据本身也是电信号。UART 真正做的是：

> 将数据按照 UART 协议串行化发送，并将接收到的串行 bit 重新组成数据。

### 2. TX、RX、GND

- TX（Transmit）：发送信号；
- RX（Receive）：接收信号；
- GND：提供双方共同的电压参考。

两个 UART 设备通常采用交叉连接：

```text
设备 A TX → 设备 B RX
设备 A RX ← 设备 B TX
GND       ↔ GND
```

TX/RX 在 STM32 中不是固定的“专用脚”，而是 UART/USART 外设信号通过 GPIO Alternate Function 映射到支持的物理引脚。

共地的作用是：

> 给发送端和接收端建立共同的电压参考，使接收端能够可靠判断 TX/RX 上的 HIGH/LOW，从而正确识别 0 和 1。

共地保证的是物理电平识别基础，不代表数据语义一定正确。

### 3. 串行通信

UART 使用串行通信，可以理解为：

> 一个数据先拆成若干 bit，再按时间顺序一位一位发送。

UART 通常按 LSB First（最低有效位优先）发送：

```text
bit0 → bit1 → bit2 → ... → bit7
```

### 4. 异步通信

UART 是异步通信，通信双方没有额外共享的时钟线。

发送端和接收端提前约定相同的通信速率，各自使用内部时钟完成发送和采样。

### 5. Baud Rate（波特率）

对于当前普通二进制 UART，可以近似理解：

```text
115200 Baud ≈ 115200 bit/s
```

一个 bit 的时间约为：

```text
1 / 115200 ≈ 8.68 μs
```

如果发送端和接收端波特率不一致，接收端会在错误的时间点采样，从而产生乱码或接收失败。

### 6. UART 帧结构

UART 一帧通常包括：

```text
Idle → Start Bit → Data Bits → Parity Bit（可选）→ Stop Bit
```

- Idle：空闲状态通常为逻辑 1；
- Start Bit：通常为逻辑 0，表示新的一帧开始；
- Data Bits：实际数据，常用 8 bit，通常 LSB First；
- Parity：可选奇偶校验；
- Stop Bit：通常为逻辑 1，表示当前帧结束并回到空闲状态。

None parity 表示没有校验位，不是“校验位等于 0”。

### 7. 115200 8N1

```text
115200 8N1
```

含义：

- 115200：波特率；
- 8：8 个数据位；
- N：None，无奇偶校验；
- 1：1 个停止位。

因此一个 8N1 数据帧在线路上实际占：

```text
1 Start + 8 Data + 0 Parity + 1 Stop = 10 bit
```

## 四、阻塞式 UART

### 1. 阻塞式接收

典型 HAL 接口：

```c
HAL_UART_Receive(&huartX, pData, Size, Timeout);
```

阻塞式接收的核心特点：

> 当前正常执行流会停留在这个函数里等待接收数据，直到任务完成或超时。

需要特别区分：

> 阻塞 main 不等于关闭整个 CPU。

如果 Timer 中断已经开启，UART 阻塞期间 Timer IRQ 仍然可以抢占当前正常执行流。

### 2. 阻塞式发送

典型接口：

```c
uint8_t msg[] = "Hello STM32\r\n";
HAL_UART_Transmit(&huartX, msg, sizeof(msg) - 1, 1000);
```

可以理解为：

```text
&huartX  → 使用哪个 UART
msg      → 待发送数据所在内存
Size     → 发送多少数据
Timeout  → 最长等待时间
```

阻塞发送时，当前执行流会留在 `HAL_UART_Transmit()` 中等待发送过程完成或超时，然后才继续执行后续代码。

## 五、UART 中断接收

### 1. `HAL_UART_Receive_IT()` 的本质

典型接口：

```c
HAL_UART_Receive_IT(&huartX, &rx_data, 1);
```

它主要负责：

```text
检查 UART 是否可以开始接收
↓
记录接收缓冲区地址
↓
记录目标接收数量
↓
修改 HAL 接收状态
↓
开启 UART 接收相关中断
↓
函数很快返回
```

因此：

> `HAL_UART_Receive_IT()` 是“启动一个 UART 中断接收任务”，不是“函数内部等待并完成整个接收过程”。

真正的数据接收由 UART 硬件在之后完成。

### 2. 函数调用结束 ≠ 接收任务结束

这是今天非常重要的一点：

```text
HAL_UART_Receive_IT()
↓
函数很快返回
↓
main 继续运行
↓
过一段时间数据到来
↓
UART 硬件接收
↓
中断
↓
HAL 处理
↓
达到要求的接收数量
↓
任务完成
```

所以：

> 一个函数可以只负责“启动任务”，函数本身已经结束，而它启动的异步任务仍然继续存在。

## 六、UART 接收中断的准确流程

以普通概念模型理解：

```text
外部开始发送 UART 数据
↓
UART 硬件检测 Start Bit
↓
UART 硬件根据波特率完成数据 bit 采样
↓
完整数据准备好
↓
产生 UART 接收 IRQ
↓
NVIC 响应
↓
USARTx_IRQHandler()        ← ISR
↓
HAL_UART_IRQHandler()
↓
HAL 读取 UART 接收数据
↓
写入用户缓冲区
↓
更新剩余接收数量
↓
如果整个接收任务完成
↓
HAL_UART_RxCpltCallback()
```

### 学习中纠正的一个误解

错误模型：

```text
检测 Start Bit
↓
CPU 马上进入中断
↓
CPU 在 ISR 里等后面的 bit
```

正确模型：

> Start Bit 主要由 UART 硬件检测，UART 硬件完成后续 bit 的采样和接收；CPU 不会为了等待后面的 bit 一直停留在 ISR 中。

## 七、`HAL_UART_Receive_IT(..., 8)` 的真正含义

例如：

```c
HAL_UART_Receive_IT(&huartX, rx_buf, 8);
```

它表示：

> 创建一个“目标长度为 8 个数据单元”的接收任务。

不是内部自动执行 8 次 `HAL_UART_Receive_IT(...,1)`。

概念上：

```text
启动一个 8 字节任务
↓
第 1 字节中断 → 写入 rx_buf[0] → 剩余 7
↓
第 2 字节中断 → 写入 rx_buf[1] → 剩余 6
↓
...
↓
第 8 字节中断 → 写入 rx_buf[7] → 剩余 0
↓
整个 8 字节接收任务完成
↓
RxCpltCallback()
```

因此：

> 一次 API 调用可以对应多个后续中断处理过程。

## 八、Callback 的准确理解

这是今天讨论最深入、也最值得记录的一部分。

### 1. 最初容易产生的误解

之前学习 Timer 时容易把流程简单理解成：

```text
事件 → IRQ → NVIC → ISR → HAL Handler → Callback
```

这容易让人误以为：

> Callback 是硬件中断机制本身不可缺少的一环。

### 2. 更准确的中断模型

硬件中断主链：

```text
硬件事件
↓
IRQ
↓
NVIC
↓
ISR
↓
HAL Handler
```

HAL / 用户业务层：

```text
HAL Handler
↓
判断某个高层事件或任务是否完成
↓
如果成立
↓
Callback
↓
用户业务逻辑
```

因此最终形成的准确表达是：

> **Callback 不是中断本身，但它把“中断发生后的用户业务逻辑”和底层中断处理解耦了。**

### 3. Timer 为什么容易造成误解

Timer 示例中：

```text
每次 Update Event
↓
刚好代表一个周期完成
↓
PeriodElapsed 事件成立
↓
HAL_TIM_PeriodElapsedCallback()
```

所以表现出来常常是：

```text
每次 Timer 中断 → 每次 Callback
```

但这只是因为 Timer 的这类中断事件恰好每次都满足对应高层 Callback 的条件。

并不代表：

```text
所有中断都必然对应一次用户 Callback
```

### 4. UART 更能说明 Callback 不是中断必需组成

例如：

```c
HAL_UART_Receive_IT(&huartX, rx_buf, 8);
```

可能发生：

```text
第 1 字节中断
→ HAL Handler
→ 数据写入缓冲区
→ 任务未完成
→ 不执行 RxCpltCallback

...

第 8 字节中断
→ HAL Handler
→ 数据写入缓冲区
→ 任务完成
→ RxCpltCallback
```

因此：

```text
发生中断 ≠ 必然执行某个用户 Callback
```

最终理解：

> Callback 可以很好地融入中断整个流程，借助中断机制在合适的时机执行用户业务逻辑；但 Callback 本身不是硬件中断机制的必需组成。

## 九、`HAL_UART_RxCpltCallback()` 参数

典型形式：

```c
void HAL_UART_RxCpltCallback(UART_HandleTypeDef *huart)
```

`huart` 用于告诉用户：

> 到底是哪一个 UART/USART 完成了这次接收任务。

例如：

```c
if (huart->Instance == USART1)
{
    // USART1 对应的业务逻辑
}
```

可以简单记：

```text
huart   → 告诉用户“是谁”
rx_data → 告诉用户“收到了什么”
```

## 十、接收缓冲区 `rx_data`

例如：

```c
uint8_t rx_data;
HAL_UART_Receive_IT(&huartX, &rx_data, 1);
```

这里传入的是 `rx_data` 的地址。

数据真正到来时：

```text
UART 硬件完成接收
↓
中断
↓
HAL Handler
↓
从 UART 硬件取出数据
↓
写入之前指定的 &rx_data
↓
接收任务完成
↓
Callback
```

所以：

> `rx_data` 在 Callback 执行前就已经被写好了。

这也进一步说明：

> Callback 不是“接收并搬运数据”的必要步骤，它主要负责在接收任务完成后给用户提供处理入口。

## 十一、变量作用域与生命周期

今天重新明确了两个概念：

```text
作用域 Scope
→ 在哪里能通过变量名访问它

生命周期 Lifetime
→ 变量对应的内存存在多久、地址什么时候仍然有效
```

例如：

```c
void StartReceive(void)
{
    uint8_t rx_data;
    HAL_UART_Receive_IT(&huart1, &rx_data, 1);
}
```

问题是：

```text
Receive_IT 保存了 &rx_data
↓
函数很快返回
↓
局部变量生命周期结束
↓
这块内存可能被栈上的其他内容重新使用
↓
HAL 以后再使用旧地址就不安全
```

因此异步接收真正要求的是：

> 从启动接收任务开始，到任务完成之前，接收缓冲区对应的内存必须一直有效。

这不是简单的“必须使用全局变量”。

---

## 十二、持续接收为什么需要再次调用 `Receive_IT`

例如：

```c
HAL_UART_Receive_IT(&huartX, &rx_data, 1);
```

含义是：

> 接收接下来的 1 个数据单元。

它不是“永久监听”。

第一次任务：

```text
Receive_IT
↓
收到 1 字节
↓
任务完成
↓
Callback
```

如果 Callback 中不再调用：

```c
HAL_UART_Receive_IT(...)
```

那么当前这一项 HAL 中断接收任务结束后，不会自动生成下一项任务。

所以持续接收通常写：

```c
void HAL_UART_RxCpltCallback(UART_HandleTypeDef *huart)
{
    // 处理数据
    HAL_UART_Receive_IT(huart, &rx_data, 1);
}
```

最终形成的理解：

> main 负责“启动第一次”，Callback 负责“续上下一次”。

## 十三、串口命令控制硬件

最简单的单字节命令：

```c
if (rx_data == '1')
{
    // 任务 A
}
else if (rx_data == '0')
{
    // 任务 B
}
```

注意：

```c
'1'
```

是字符 `'1'`，ASCII 编码值为 49。

而：

```c
1
```

是数值 1。

因此串口助手输入字符 `1` 时，通常代码应该判断：

```c
rx_data == '1'
```

而不是：

```c
rx_data == 1
```

## 十四、UART、GPIO 和业务逻辑的层级

整个程序可以分成：


UART 只负责“收到什么数据”，数据具体代表什么由用户业务代码定义。

## 十五、Timer + UART 中断共存

Timer 和 UART 硬件可以同时工作：

```text
Timer 硬件 → 自己计数
UART 硬件  → 自己接收 bit
```

在硬件层，两者可以并行。

但是 CPU 软件处理中：

```text
ISR
Handler
Callback
```

CPU 仍然需要按顺序执行。

NVIC 负责管理中断优先级。

例如 UART ISR 正在执行时，高优先级 Timer IRQ 到来：

```text
UART ISR
↓
Timer 高优先级 IRQ
↓
Timer 抢占
↓
Timer ISR
↓
返回 UART ISR
↓
继续执行
```

如果另一个中断不能抢占当前中断，则会保持 pending，等待当前 ISR 完成。

因此：

> 多个外设可以并行工作，但 CPU 在软件层面通过中断优先级进行快速切换和顺序处理。

## 十六、为什么 Callback 应尽量短

Callback 通常运行在中断上下文中。

如果 Callback 中做大量耗时任务：

```text
UART Callback 占用 CPU
↓
其他不能抢占它的中断只能等待
↓
main 也不能继续
```

因此工程上通常：

> 中断负责快速响应、记录事件；主循环负责较重的业务处理。

简单 GPIO 操作、修改状态、重新挂接接收等短操作可以放在 Callback 中。

复杂运算、长时间等待等不适合塞进 Callback。

## 十七、“中断只记录状态，main 再处理”

一种常见结构：

```c
volatile uint8_t command;

void HAL_UART_RxCpltCallback(UART_HandleTypeDef *huart)
{
    command = rx_data;
}

while (1)
{
    if (command == '1')
    {
        // 真正执行业务
    }
}
```

它的核心思想是：

```text
中断
→ 只记录“发生了什么”
→ 快速退出

main
→ 根据记录
→ 真正处理
```

`volatile` 今天只是唤醒旧知识，没有重新展开学习。

## 十八、为什么单个状态变量不够

如果 UART 很快连续收到：

```text
'A' → 'B' → 'C'
```

但 Callback 只写：

```c
command = rx_data;
```

那么后来的数据会覆盖前面的数据。

所以：

> 单个状态变量适合保存“当前最新状态”，不适合可靠保存多个按顺序到来的事件。

## 十九、环形队列与 UART 的结合

环形队列可以作为：

> UART 接收端和 main 处理端之间的临时缓冲区。

Callback：

```text
收到 A → push(A)
收到 B → push(B)
收到 C → push(C)
```

main：

```text
pop A → 处理
pop B → 处理
pop C → 处理
```

基本结构：

```c
uint8_t rx_data;

int main(void)
{
    // 初始化环形队列
    HAL_UART_Receive_IT(&huartX, &rx_data, 1);

    while (1)
    {
        uint8_t command;

        if (ring_buffer_pop(&cmd_queue, &command))
        {
            // 解析并执行 command
        }
    }
}
```

Callback：

```c
void HAL_UART_RxCpltCallback(UART_HandleTypeDef *huart)
{
    if (huart->Instance == USARTx)
    {
        ring_buffer_push(&cmd_queue, rx_data);
        HAL_UART_Receive_IT(huart, &rx_data, 1);
    }
}
```

职责：

```text
Callback
→ 收到数据
→ 存入队列
→ 重新启动接收
→ 快速退出

main
→ 从队列取数据
→ 解析
→ 执行业务
```

## 二十、今日遇到的主要问题、误解与修正

### 问题 1：把 UART 理解成简单“信号转换”

最初理解：

> CPU 数据 → 电信号。

修正：

> UART 更准确的作用是按 UART 的时序和帧结构将数据串行发送，并把接收到的串行 bit 恢复成数据。

### 问题 2：把 Callback 当成中断必经组成

产生原因：

Timer 示例中“每次周期中断都执行 PeriodElapsedCallback”，容易形成“中断一定会 Callback”的错误模型。

最终修正：

```text
硬件事件 → IRQ → NVIC → ISR → HAL Handler
```

是中断主链。

Callback 是 HAL 在特定高层事件或任务条件满足时提供给用户的业务接口。

最终明确：

> Callback 不是中断本身，但它把“中断发生后的用户业务逻辑”和底层中断处理解耦了。

### 问题 3：误以为 Start Bit 后 CPU 会一直待在 ISR

修正：

> UART 硬件先完成 bit 接收，完整数据准备好后再通过中断通知 CPU。

### 问题 4：误以为 `Receive_IT(...,8)` 是内部执行 8 次 `Receive_IT(...,1)`

修正：

> `Receive_IT(...,8)` 是一个长度为 8 的接收任务，HAL 通过缓冲区指针、剩余计数和多次接收中断完成它。

### 问题 5：误以为函数返回就代表接收任务结束

修正：

> 函数调用结束 ≠ 函数启动的异步任务结束。

### 问题 6：没有区分变量作用域和内存生命周期

最终明确：

```text
作用域 → 能不能通过变量名访问
生命周期 → 变量内存是否仍然有效
```

### 问题 7：误以为 `Receive_IT(...,1)` 是永久监听

修正：

> 它只启动一个 1 字节任务，完成后需要再次调用 `Receive_IT()` 才能开始下一项任务。

### 问题 8：单个变量与环形队列用途混淆

最终明确：

```text
单个状态变量 → 记录最新状态
环形队列     → 暂存多个尚未处理的数据，并保持顺序
```

## 二十六、今日最值得记住的几点

1. **UART 接收不是 CPU 一直盯着 RX 引脚，而是 UART 硬件先完成底层 bit 接收，再通过中断通知 CPU。**
2. **`HAL_UART_Receive_IT()` 是启动异步接收任务，而不是在函数执行期间完成全部接收。**
3. **函数调用结束，不等于函数启动的任务结束。**
4. **`rx_data` 在 `HAL_UART_RxCpltCallback()` 执行之前就已经由 HAL 写好。**
5. **Callback 不是中断本身，但它把“中断发生后的用户业务逻辑”和底层中断处理解耦了。**
6. **发生中断不等于一定执行某个用户 Callback；Callback 是否执行取决于相应高层事件或任务完成条件。**
7. **持续的单字节中断接收，本质上是多个有限的一字节任务通过 Callback 不断重新挂接。**
8. **单个变量记录的是“最新状态”；环形队列保存的是“尚未处理的一系列数据”。**
9. **中断适合快速响应和记录，较重的业务逻辑通常交给 main 处理。**
10. **分析 STM32/HAL 代码时，要始终区分硬件机制、HAL 封装、用户 Callback 和业务逻辑四个层级。**
