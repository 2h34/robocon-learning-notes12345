# 二、FreeRTOS 基础知识

## 1. FreeRTOS 是什么

FreeRTOS = **Free Real-Time Operating System，实时操作系统**。

在当前 STM32 工程中，FreeRTOS 主要负责：

```text
多个功能同时存在
↓
由 FreeRTOS Kernel 管理多个 Task
↓
Scheduler 决定当前 CPU 执行哪个 Task
```

FreeRTOS 解决的是：

> **“什么时候让哪个 Task 运行？”**

而具体业务逻辑仍然由用户代码完成。

---

## 2. Task 与普通函数

普通函数：

```text
被调用
↓
完成一次工作
↓
返回
```

例如：

```c
noise_task();
breath_lights();
Led_Breath_GetBrightness();
```

这些函数主要负责：

> **“做什么”**

Task：

```text
系统启动时创建
↓
长期存在
↓
由 Scheduler 调度
↓
通常在 for(;;) 中循环
```

Task 更负责：

> **“什么时候做”**

例如：

```text
Float_Task
→ 决定每10ms执行一次

Led_Breath_GetBrightness
→ 真正取得当前亮度
```

---

## 3. Scheduler 调度器

Scheduler = **调度器**。

作用：

> 在多个 Ready Task 中决定当前哪个 Task 获得 CPU。

STM32F4 是单核 Cortex-M4，因此并不是多个 Task 真正同时执行，而是：

```text
Task A运行
↓
Task A阻塞/被抢占
↓
Task B运行
↓
Task C运行
↓
再回到Task A
```

切换速度快，所以看起来多个功能可以并发运行。

---

## 4. Task 三种重要状态

### Running

当前正在占用 CPU 执行。

### Ready

已经满足运行条件，但正在等待 Scheduler 分配 CPU。

```text
Ready
↓
Scheduler选择
↓
Running
```

### Blocked

Task 正在等待条件。

例如：

```c
osDelay(100);
```

或：

```c
osMessageQueueGet(can_rx_queue, &Msg, 0, osWaitForever);
```

会让当前 Task 进入 Blocked。

条件满足后：

```text
Blocked
↓
Ready
↓
等待Scheduler
↓
Running
```

---

## 5. `osDelay()` 不会停止整个 CPU

```c
osDelay(100);
```

表示：

> 当前 Task 延时约 100ms。

不是：

> 整个 STM32 停止 100ms。

例如：

```text
UARTTask
↓
osDelay(1)
↓
UARTTask Blocked

与此同时：
NoiseTask / CANTask / LEDTask
仍可运行
```

---

## 6. Task Priority 优先级

多个 Task 都 Ready 时：

> 优先级高的 Task 更容易先获得 CPU。

但是：

```text
高优先级 Task 处于 Blocked
→ 仍然不会运行
```

如果高优先级 Task 永远不阻塞，可能导致低优先级 Task 长时间无法执行。

因此需要合理使用：

```c
osDelay()
osDelayUntil()
Queue等待
```

---

## 7. Task Stack

每个 Task 都有自己的 Stack，用于保存：

- 局部变量
- 函数调用信息
- 返回地址
- Task 切换时需要保存的运行上下文

例如：

```c
.stack_size = 128 * 4
```

约等于 512 Byte。

Stack 可以理解为：

> 每个 Task 自己的一块运行工作区。

---

## 8. TCB 与 Handle

TCB = **Task Control Block，任务控制块**。

FreeRTOS 用它记录：

- Task 状态
- Priority
- Stack 信息
- 调度相关信息

可以理解为：

```text
TCB = FreeRTOS 给 Task 建的档案
```

Handle 是程序用来标识 RTOS 对象的句柄，例如：

```c
osThreadId_t UARTTaskHandle;
osMessageQueueId_t can_rx_queue;
```

Handle 不是 Task 函数本身，也不是 TCB 本体。

# 三、Queue 消息队列

## 1. Queue 的作用

Queue 是 FreeRTOS 中用于 Task / Callback 之间传递数据的 RTOS 对象。

```text
Producer
↓
osMessageQueuePut()
↓
Queue
↓
osMessageQueueGet()
↓
Consumer
```

当前 CAN 接收链：

```text
CAN Callback
↓
can_rx_queue
↓
CAN_Task
```

---

## 2. Queue 创建

例如：

```c
can_rx_queue = osMessageQueueNew(
    16,
    sizeof(CanMsg_t),
    NULL
);
```

含义：

```text
16
→ 最多16条消息

sizeof(CanMsg_t)
→ 每条消息大小

NULL
→ 默认属性
```

VOFA 的 float Queue：

```c
vofa_tx_queue = osMessageQueueNew(
    8,
    sizeof(float),
    NULL
);
```

表示最多保存 8 个 float。

---

## 3. `osMessageQueuePut()`

```c
osMessageQueuePut(
    vofa_tx_queue,
    &brightness,
    0,
    0
);
```

Queue 保存的是 `brightness` 的数据副本，不是局部变量地址本身。

---

## 4. `osMessageQueueGet()`

```c
osMessageQueueGet(
    can_rx_queue,
    &Msg,
    0,
    osWaitForever
);
```

表示从 Queue 取一条数据复制到 `Msg`。

如果 Queue 为空，`osWaitForever` 会让 Task 进入 Blocked。

---

## 5. Queue 与 Task 状态

完整过程：

```text
can_rx_queue为空
↓
CAN_Task调用Get(osWaitForever)
↓
CAN_Task → Blocked
↓
CPU运行其他Task

CAN收到数据
↓
Callback Put进Queue
↓
CAN_Task：Blocked → Ready
↓
Scheduler调度
↓
CAN_Task再次Running
```

这把：

```text
Queue
+
Blocked
+
Ready
+
Scheduler
```

真正串了起来。

# 四、ISR / Callback / Task 的职责边界

当前理解：

```text
IRQ
↓
ISR
↓
HAL Handler
↓
HAL Callback
↓
Queue
↓
Task
```

其中：

- IRQ：硬件中断请求
- ISR：中断服务入口
- HAL Handler：HAL 底层中断封装
- Callback：HAL 给用户的回调接口
- Task：FreeRTOS 管理的执行单元

Callback 不是硬件中断机制本身必需的组成部分。

工程上更合理的是：

```text
Callback
→ 快速保存/入队
→ 尽快退出

Task
→ 做复杂业务逻辑
```

# 五、`osDelayUntil()` 与周期任务

通过 NoiseTask 和 FloatTask 学习了：

```c
uint32_t last = osKernelGetTickCount();

for (;;)
{
    last += 10;
    osDelayUntil(last);
}
```

当前 FreeRTOS Tick：

```text
1000Hz
→ 1 Tick ≈ 1ms
```

`osDelayUntil()` 等待的是绝对 Tick：

```text
1010
1020
1030
1040
...
```

因此更适合固定周期任务。

相比：

```c
osDelay(10);
```

`osDelayUntil()` 不容易把每轮代码执行时间累计进周期。

适合：

- 500Hz NoiseTask
- 100Hz FloatTask
- 固定周期控制任务

从板：

```c

);
```

今天明确：

# 九、brightness 与 duty

呼吸灯内部：

```c
static uint32_t duty;
```

范围约：

```text
0 ~ 1999
```

协议中的 brightness：

```text
0.0 ~ 1.0
```

因此：

```c
brightness = (float)duty / 1999.0f;
```

为了模块封装，增加：

```c
float Led_Breath_GetBrightness(void);
```

实现：

```c
float Led_Breath_GetBrightness(void)
{
    if (!breath_on)
    {
        return 0.0f;
    }

    return (float)duty / 1999.0f;
}
```

# 十、从板 100Hz float 反馈

题目要求：

```text
从板100Hz向主板反馈一个变化的float
```

100Hz 对应：

```text
10ms周期
```

因此设计 `FloatTask`：

```c
uint32_t last = osKernelGetTickCount();

for (;;)
{
    last += 10;
    osDelayUntil(last);

    brightness = Led_Breath_GetBrightness();

    memcpy(
        TxData,
        &brightness,
        sizeof(float)
    );

    HAL_CAN_AddTxMessage(
        &hcan1,
        &TxHeader,
        TxData,
        &TxMailbox
    );
}
```

CAN Header：

```c
TxHeader.StdId = FLOAT_ID;
TxHeader.IDE = CAN_ID_STD;
TxHeader.RTR = CAN_RTR_DATA;
TxHeader.DLC = 4;
```

# 十四、VOFA 控制命令解析

协议：

```text
A5 | on_off | period_H | period_L | 5A
```

合法帧判断：

```c
if ((rx_status == osOK) &&
    (frame[0] == 0xA5 && frame[4] == 0x5A))
```

解析：

```c
cmd.on_off = frame[1];

cmd.period_ms =
    (frame[2] << 8) |
    frame[3];
```

例如：

```text
A5 01 07 D0 5A
```

表示：

```text
打开呼吸灯
周期2000ms
```

## 3. Queue 被重复 Get

错误写法：

```c

{
    osMessageQueueGet(...);
}
```

第一次已经取出数据，第二次会多取一条甚至阻塞。

正确做法：

```text

↓

```

# 二十、今日最值得记住的一点

今天最重要的认识：

> **FreeRTOS 不是把所有功能都变成 Task，而是把需要独立调度、等待或固定周期执行的部分交给 Task，具体功能仍由模块函数完成。**

例如：

```text
FloatTask
→ 负责每10ms运行一次

Led_Breath_GetBrightness()
→ 负责取得brightness

HAL_CAN_AddTxMessage()
→ 负责交给CAN外设发送
```

同时，一个功能是否真正完成，要看完整数据链，而不是只看某个函数能否编译。

VOFA 波形完整链：

```text
duty
→ brightness
→ FloatTask
→ CAN
→ Callback
→ Queue
→ CAN_Task
→ Queue
→ UART_Task
→ FireWater
→ VOFA
```

少任何一环，都不能算真正闭环。
