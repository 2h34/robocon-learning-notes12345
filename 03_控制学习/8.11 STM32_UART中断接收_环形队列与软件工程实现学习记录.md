# 4. UART 中断配置

在 CubeMX 开启：

```text
USART1 global interrupt
```

当前 USART1 与 TIM6 都配置为同一中断优先级。

简化理解：

- 两个中断都可以响应
- 同优先级情况下，一个 ISR 正在运行时，另一个不会直接抢占
- 新到中断先 pending
- 当前 ISR 退出后再继续处理

# 5. UART 中断接收的层级模型

本轮进一步明确了 UART 中断接收不能简单理解成“开 UART 就能中断接收”。

应分为三个层级。

## 第一层：UART 外设准备

例如：

```text
Asynchronous
115200
8N1
TX / RX
```

作用：

> 让 USART1 具备正常收发数据的硬件条件。

---

## 第二层：中断通道准备

例如：

```text
USART1 global interrupt
NVIC Enable
```

作用：

> 当 USART1 产生 IRQ 时，允许 CPU 响应。

---

## 第三层：软件接收任务

由用户代码启动：

```c
HAL_UART_Receive_IT(&huart1, &rx_data, 1);
```

它表示：

> 启动一次“通过中断方式接收 1 个字节”的异步任务。

任务完成后，HAL 才会进一步进入对应的接收完成 Callback。

所以更准确的结构是：

```text
UART 外设配置
→ 中断通道配置
→ HAL_UART_Receive_IT() 启动任务
→ 任务完成
→ HAL_UART_RxCpltCallback()
```

不是：

```text
第三层 = Callback
```

```text
USART1 产生 IRQ
↓

↓
```

> **Callback 不是中断本身，但它把“中断发生后的用户业务逻辑”和底层中断处理解耦了。**

# 7. 设计 UART 接收缓冲变量 `rx_data`

使用：

```c
HAL_UART_Receive_IT(&huart1, &rx_data, 1);
```

需要保证 `rx_data`：

- 生命周期足够长
- 接收期间地址持续有效
- Callback 能访问

最终使用：

```c
uint8_t rx_data;
```

定义为全局变量。

原因：

1. `HAL_UART_Receive_IT()` 是异步任务，函数返回不代表任务完成。
2. 接收任务完成前，`&rx_data` 必须一直有效。
3. Callback 需要读取该数据。

需要明确：

> 全局变量不是 HAL 强制要求。

真正要求的是：

> 生命周期和可访问性满足异步任务需要。

---

# 8. 第一次 `HAL_UART_Receive_IT()` 放在哪里

最终选择：

```text
USART1 初始化完成之后
while(1) 之前
```

原因：

- UART 必须先初始化
- `Receive_IT()` 是一次有限异步任务
- 不应该放在 `while(1)` 中无条件反复调用
- 前一次任务还没完成时再次调用可能得到 `HAL_BUSY`

后来进一步发现：

> Callback 后面要向队列 push，所以队列必须先初始化。

因此最终顺序为：

```text
USART1 初始化
↓
系统初始化
↓
byte_queue_init()
↓
HAL_UART_Receive_IT()
↓
while(1)
```

---

# 9. 为什么需要环形队列

最开始考虑 Callback 时，只想到：

```text
接收完成
→ 再次 Receive_IT
```

但这样会漏掉一个关键动作：

> 当前收到的 `rx_data` 必须先保存。

因为下一次接收仍然使用同一个：

```c
rx_data
```

如果不缓存，下一次数据可能覆盖上一次结果。

因此建立：

```text
UART Callback
→ push(rx_data)
→ 环形队列
→ main 再 pop
```

形成生产者 / 消费者结构：

```text
UART Callback = 生产者
main()        = 消费者
```

# 12. 字节环形队列结构设计

队列核心成员：

```text
buf
head
tail
count
```

最终结构：

```c
#define BYTE_QUEUE_SIZE 16

typedef struct
{
    uint8_t buf[BYTE_QUEUE_SIZE];
    uint8_t head;
    uint8_t tail;
    uint8_t count;
} byte_queue_t;
```

作用：

- `buf`：实际存数据
- `head`：下一次 pop 的位置
- `tail`：下一次 push 的位置
- `count`：当前有效元素数量

# 13. 一个实际理解错误：`count = 15` 是否满

最初判断：

```text
count = 15 → 满
```

后来纠正：

```text
数组下标：0 ~ 15
元素总数：16
```

所以：

```text
count = 0  → 空
count = 15 → 还有一个位置
count = 16 → 满
```

这是：

> 最大下标 ≠ 元素数量

# 16. 环形队列函数实现

## 16.1 初始化

```c
void byte_queue_init(byte_queue_t *q)
{
    q->head = 0;
    q->tail = 0;
    q->count = 0;
}
```

不需要清空整个 `buf[]`。

原因：

> `count = 0` 已经表示当前没有有效元素。

---

## 16.2 判空

```c
bool byte_queue_is_empty(const byte_queue_t *q)
{
    return q->count == 0;
}
```

---

## 16.3 判满

```c
bool byte_queue_is_full(const byte_queue_t *q)
{
    return q->count == BYTE_QUEUE_SIZE;
}
```

---

## 16.4 push

正确顺序：

```text
判断是否满
↓
buf[tail] = data
↓
tail 后移并回绕
↓
count++
↓
return true
```

实现：

```c
bool byte_queue_push(byte_queue_t *q, uint8_t data)
{
    if (byte_queue_is_full(q))
    {
        return false;
    }

    q->buf[q->tail] = data;
    q->tail = (q->tail + 1) % BYTE_QUEUE_SIZE;
    q->count++;

    return true;
}
```

---

## 16.5 为什么必须回绕

不能只写：

```c
q->tail++;
```

否则：

```text
tail = 15
↓
tail = 16
```

超出：

```text
buf[0] ~ buf[15]
```

所以：

```c
q->tail = (q->tail + 1) % BYTE_QUEUE_SIZE;
```

同理：

```c
q->head = (q->head + 1) % BYTE_QUEUE_SIZE;
```

形成：

```text
0 → 1 → ... → 15 → 0 → 1 ...
```

这就是环形队列的核心。

---

## 16.6 pop

正确顺序：

```text
判断是否为空
↓
读取 buf[head]
↓
head 后移并回绕
↓
count--
↓
return true
```

实现：

```c
bool byte_queue_pop(byte_queue_t *q, uint8_t *data)
{
    if (byte_queue_is_empty(q))
    {
        return false;
    }

    *data = q->buf[q->head];
    q->head = (q->head + 1) % BYTE_QUEUE_SIZE;
    q->count--;

    return true;
}
```

# 19. 队列满时的策略讨论

最初选择：

```text
B：丢掉最旧字节，保留最新字节
```

当时的理由是：

> CPU 可能已经处理过最旧字节。

这个理解被纠正。

如果队列：

```text
count == 16
```

说明 16 个字节都还没有被 main `pop()`。

如果最旧字节已经处理，它就不会继续占位置。

最终改为：

```text
A：队列满时，拒绝新字节
```

即：

```c
byte_queue_push(...)
→ false
```

旧数据保持不变。

但进一步认识到：

> 无论丢新还是丢旧，只要队列已经满，就已经发生数据完整性问题。

后续更完整设计应该加入：

```text
overflow 标志
```

用于通知上层数据曾丢失。

本轮暂未实现。

# 20. 实现 UART Callback

最终 Callback：

```c
void HAL_UART_RxCpltCallback(UART_HandleTypeDef *huart)
{
    if (huart->Instance == USART1)
    {
        byte_queue_push(&rx_queue, rx_data);

        HAL_UART_Receive_IT(huart, &rx_data, 1);
    }
}
```

Callback 只做三件事：

```text
确认 USART1
↓
push 当前 rx_data
↓
重新挂下一次 Receive_IT
↓
快速退出
```

没有在 Callback 中做：

- 命令解析
- LED 控制
- `HAL_Delay()`
- 长循环
- 复杂业务

# 21. 为什么 Callback 里必须再次 `Receive_IT`

第一次：

```c
HAL_UART_Receive_IT(&huart1, &rx_data, 1);
```

只代表：

> 接收 1 个字节的一次性任务。

该字节完成后，本次任务结束。

要连续接收：

```text
第 1 字节完成
↓
Callback
↓
再次 HAL_UART_Receive_IT()
↓
开始第 2 字节
```

所以连续监听依赖：

```text
main 中启动第一次
+
Callback 中不断重新挂下一次
```

# 23. 为什么 `volatile` 不够

例如：

```c
q->count--;
```

在 CPU 层面可能不是不可分割的一步，而是：

```text
读取 count
↓
减 1
↓
写回
```

如果中间 UART 中断进入，又执行：

```c
q->count++;
```

就可能发生竞争。

因此：

> `volatile` 只能影响编译器优化和访问可见性，不能自动保证多步读改写操作的原子性。

# 24. PRIMASK 与临界区

## 24.1 `__get_PRIMASK()`

```c
uint32_t primask = __get_PRIMASK();
```

作用：

> 保存进入临界区前的中断屏蔽状态。

当前简化理解：

```text
PRIMASK = 0
→ 普通可屏蔽中断允许

PRIMASK = 1
→ 普通可屏蔽中断被屏蔽
```

---

## 24.2 `__disable_irq()`

```c
__disable_irq();
```

作用：

> 暂时屏蔽普通可屏蔽中断。

注意：

- 不是关闭 USART1 外设
- UART 硬件本身仍可能继续工作
- 只是 CPU 暂时不响应普通 IRQ

---

## 24.3 `__set_PRIMASK(primask)`

```c
__set_PRIMASK(primask);
```

作用：

> 恢复进入临界区前的中断状态。

它比：

```c
__enable_irq();
```

更严谨。

区别：

```text
__enable_irq()
→ 无条件开启中断

__set_PRIMASK(old_state)
→ 恢复原状态
```

如果中断原本就是关闭的，直接 `__enable_irq()` 会改变原系统状态。

---

# 25. main 中的临界区

最终结构：

```c
uint8_t data;
bool result;
uint32_t primask;

primask = __get_PRIMASK();

__disable_irq();

result = byte_queue_pop(&rx_queue, &data);

__set_PRIMASK(primask);

if (result)
{
    command_process(data);
}
```

只保护：

```c
byte_queue_pop(...)
```

而不保护：

```text
command_process
LED 控制
复杂业务
HAL_Delay
```

原因：

> 临界区必须尽可能短。

另外需要记住：

> `__disable_irq()` 不只影响 USART1，TIM6 等普通中断也会短暂被屏蔽。

当前 pop 很短，因此可以接受。

# 29. CubeMX USER CODE 区域问题

检查 `main.c` 时发现：

```c
#include "byte_queue.h"
```

一开始放在自动生成 Include 区域。

后续调整到：

```c
/* USER CODE BEGIN Includes */
#include "led.h"
#include "buzzer.h"
#include "byte_queue.h"
/* USER CODE END Includes */
```

原因：

> 用户自己写的代码尽量放进 `USER CODE` 区域，避免重新 Generate Code 时被 CubeMX 覆盖。

同样地，自定义变量和函数也应尽量放在对应 `USER CODE` 区域。

# 37. 本轮最值得记住的几点

## 1. 函数返回不等于异步任务结束

```c
HAL_UART_Receive_IT(...)
```

返回后，UART 接收任务仍然继续。

---

## 2. Callback 不是 ISR

```text
IRQ
→ ISR
→ HAL Handler
→ Callback
```

---

## 3. Callback 要短

当前 Callback 只负责：

```text
push
→ 重新 Receive_IT
→ 退出
```

---

## 4. 队列用于解耦

```text
UART 快速产生数据
↓
队列缓存
↓
main 稍后处理
```

---

## 5. `volatile` 不能解决所有并发问题

共享数据涉及：

```text
中断 + main
```

还要考虑原子性与临界区。

---

## 6. 临界区越短越好

```text
保存状态
→ 暂时关中断
→ 操作共享数据
→ 恢复状态
```

---
