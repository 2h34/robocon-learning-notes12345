# 二、C 语言前置基础

## 2.1 指针

普通变量：

```c
int x = 10;
```

指针：

```c
int *p = &x;
```

含义：

```text
&x  → 取得 x 的地址
p   → 保存 x 的地址
*p  → 访问 p 指向地址中的数据
```

例如：

```c
*p = 20;
```

就是通过指针修改 `x`。

---

## 2.2 为什么函数参数里使用指针

例如：

```c
void packet_queue_init(packet_queue *q);
```

传入队列地址后，函数内部：

```c
q->head = 0;
q->tail = 0;
q->count = 0;
```

修改的是调用者真正的队列，而不是副本。

---

## 2.3 输出参数

题目 3：

```c
bool command_pack_unpack(
    const command_packet *pkt,
    uint8_t *blink_count,
    uint8_t *led_mask
);
```

这里：

```text
return true / false
→ 返回解包是否成功

*blink_count
→ 输出闪烁次数

*led_mask
→ 输出 LED 掩码
```

C 函数一般只能直接返回一个值，因此可通过指针参数实现多个输出。

---

## 2.4 `.` 与 `->`

普通结构体：

```c
packet_queue q;
q.head = 0;
```

结构体指针：

```c
packet_queue *q;
q->head = 0;
```

记忆：

```text
对象本身 → .
对象指针 → ->
```

并且：

```c
q->head
```

等价于：

```c
(*q).head
```

---

## 2.5 `const` 指针

本次常见：

```c
const command_packet *pkt;
```

表示：

> 不能通过 `pkt` 修改它指向的协议包内容。

常见形式：

```text
const int *p
→ 指向的数据不能通过 p 修改

int * const p
→ p 自己不能改指向

const int * const p
→ 两者都不能改
```

---

## 2.6 数组与指针的联系

数组：

```c
int arr[4];
```

有：

```c
arr[i]
```

可理解为：

```c
*(arr + i)
```

后面的函数指针表同样依赖“数组下标 → 找到元素”的思路。

# 三、bit、Byte、十六进制与整数类型

## 3.1 bit

**bit = binary digit = 二进制位**

只能为：

```text
0
或
1
```

## 3.2 Byte

```text
1 Byte = 8 bit
```

## 3.3 十六进制

一个十六进制位对应：

```text
4 bit
```

因此：

```text
2 个十六进制位 = 8 bit = 1 Byte
```

例如：

```text
0x5A
```

实际数字部分是 `5` 和 `A`：

```text
5 = 0101
A = 1010
```

所以：

```text
0x5A = 0101 1010
```

`0x` 只是十六进制前缀，不算一个十六进制位。

## 3.4 固定宽度整数

```text
uint8_t  = 8 bit  = 1 Byte
uint16_t = 16 bit = 2 Byte
uint32_t = 32 bit = 4 Byte
```

`u` / `unsigned` 表示无符号。

## 3.5 `U` 后缀

例如：

```c
3U
4U
0x0FU
```

`U` 表示无符号整数字面量。

# 四、位运算

本次主要使用：

```text
&
|
<<
>>
```

## 4.1 按位与 `&`

用于保留指定 bit：

```c
led_mask & 0x0F
```

`0x0F = 0000 1111`，因此只保留低 4 位。

## 4.2 按位或 `|`

用于组合字段：

```c
(blink_count << 4) | led_mask
```

## 4.3 左移 `<<`

例如：

```c
1U << n
```

可生成 bit n 的掩码。

注意：

> **bit0 是最右边的一位。**

## 4.4 右移 `>>`

用于把高位字段移动到低位：

```c
pkt->cmd >> 4
```

可以提取 cmd 高 4 位中的闪烁次数。

## 4.5 掩码 Mask

本次逻辑 LED 掩码：

```c
#define LED_MASK_LED1 0x01U
#define LED_MASK_LED2 0x02U
#define LED_MASK_LED3 0x04U
#define LED_MASK_LED4 0x08U
```

对应：

```text
LED1 → bit0
LED2 → bit1
LED3 → bit2
LED4 → bit3
```

组合 LED1 + LED2：

```c
LED_MASK_LED1 | LED_MASK_LED2
```

得到：

```text
0x03
```

# 五、整数提升 Integer Promotion

即使变量是：

```c
uint8_t
```

参与算术、移位等运算时，C 往往会先提升到 `int` 或 `unsigned int` 再计算。

例如：

```c
blink_count << 4
```

最后常显式转换：

```c
(uint8_t)(...)
```

例如：

```c
pkt->cmd =
    (uint8_t)((blink_count << CMD_BLINK_SHIFT)
    | (led_mask & CMD_LED_MASK));
```

含义：

> 先正常完成运算，再明确保存成 8 bit 结果。

# 六、题目 1：环形队列

## 6.1 环形队列思想

把固定数组理解成首尾相接：

```text
0 → 1 → 2 → ... → N-1
↑                 ↓
└─────────────────┘
```

到最后一个位置后再回到 0。

## 6.2 队列结构

```c
typedef struct
{
    command_packet buf[PACKET_QUEUE_SIZE];
    uint8_t head;
    uint8_t tail;
    uint8_t count;
} packet_queue;
```

核心：

```text
head
→ 下一个读取位置

tail
→ 下一个写入位置

count
→ 当前有效元素个数
```

## 6.3 初始化

```c
q->head = 0;
q->tail = 0;
q->count = 0;
```

## 6.4 入队 push

流程：

```text
检查是否已满
↓
写入 q->buf[q->tail]
↓
tail 后移
↓
count++
```

关键：

```c
q->buf[q->tail] = *pkt;
q->tail = (q->tail + 1) % PACKET_QUEUE_SIZE;
q->count++;
```

## 6.5 出队 pop

流程：

```text
检查是否为空
↓
读取 q->buf[q->head]
↓
head 后移
↓
count--
```

关键：

```c
*pkt = q->buf[q->head];
q->head = (q->head + 1) % PACKET_QUEUE_SIZE;
q->count--;
```

## 6.6 `%` 的作用

假设：

```text
PACKET_QUEUE_SIZE = 16
tail = 15
```

则：

```text
(15 + 1) % 16 = 0
```

实现从数组末尾回到开头。

## 6.7 空与满

```c
q->count == 0U
```

表示空。

```c
q->count == PACKET_QUEUE_SIZE
```

表示满。

`count` 可以消除只看 `head == tail` 时“空/满难区分”的问题。

# 七、题目 2：自定义协议包与封包

## 7.1 协议包结构

```c
typedef struct
{
    uint8_t header[2];
    uint8_t cmd;
    uint8_t checksum;
} command_packet;
```

共 4 Byte：

```text
Byte 0 → header[0] = 0x0A
Byte 1 → header[1] = 0x5A
Byte 2 → cmd
Byte 3 → checksum
```

## 7.2 包头

```c
#define HEADER_HIGH_BYTE 0x0AU
#define HEADER_LOW_BYTE  0x5AU
#define HEADER_WORD      0x0A5AU
```

两个字节拼起来：

```text
0x0A5A
```

作用是让接收端识别这是不是本协议的数据。

## 7.3 cmd 位段

一个 Byte：

```text
bit7 bit6 bit5 bit4 | bit3 bit2 bit1 bit0
```

设计：

```text
高 4 位 → blink_count
低 4 位 → led_mask
```

定义：

```c
#define CMD_BLINK_SHIFT 4U
#define CMD_LED_MASK    0x0FU
```

## 7.4 封包公式

```c
pkt->cmd =
    (uint8_t)((blink_count << CMD_BLINK_SHIFT)
    | (led_mask & CMD_LED_MASK));
```

理解：

```text
blink_count << 4
→ 放到高 4 位

led_mask & 0x0F
→ 保留低 4 位

|
→ 合并成一个 Byte
```

## 7.5 实际测试

```text
blink_count = 3
LED1 + LED2
```

LED mask：

```text
0001 | 0010 = 0011 = 0x03
```

blink_count：

```text
3 = 0011
```

左移：

```text
0011 0000
```

组合：

```text
0011 0000
0000 0011
---------
0011 0011 = 0x33
```

所以：

```text
cmd = 0x33
```

# 八、Checksum

本题：

```c
#define PACKET_CHECKSUM(h0, h1, cmd) \
    ((uint8_t)((h0) + (h1) + (cmd)))
```

测试：

```text
0x0A + 0x5A + 0x33 = 0x97
```

所以完整测试包：

```text
{0x0A, 0x5A, 0x33, 0x97}
```

含义：

> LED1、LED2 闪烁 3 次。

强制转换为 `uint8_t` 表示只保留低 8 bit。

# 九、逻辑 LED 掩码与 GPIO 映射

协议中：

```text
bit0~bit3
→ LED1~LED4
```

但实际 LED 在：

```text
PB3~PB6
```

所以协议掩码要转换为 GPIO 引脚掩码：

```c
uint8_t led_pins =
    (uint8_t)((led_mask & CMD_LED_MASK) << 3);
```

例如：

```text
逻辑 0000 0011
```

左移 3：

```text
0001 1000
```

对应 PB3 和 PB4。

这是本次一个很重要的概念：

> **协议层的逻辑编号和硬件层的物理引脚编号不是一回事，需要映射。**

# 十、题目 3：解包与校验

## 10.1 整体流程

```text
收到协议包
↓
检查包头
↓
检查 checksum
↓
提取 blink_count
↓
提取 led_mask
↓
返回 true
```

任一校验失败：

```c
return false;
```

## 10.2 拼接包头

```c
uint16_t header_word =
    ((uint16_t)pkt->header[0] << 8)
    | pkt->header[1];
```

例如：

```text
0x0A → 0x0A00
0x5A → 0x005A
OR   → 0x0A5A
```

然后：

```c
if (header_word != HEADER_WORD)
{
    return false;
}
```

## 10.3 checksum 校验

重新计算：

```c
uint8_t checksum =
    PACKET_CHECKSUM(
        pkt->header[0],
        pkt->header[1],
        pkt->cmd
    );
```

再比较：

```c
if (checksum != pkt->checksum)
{
    return false;
}
```

## 10.4 解出 blink_count

```c
*blink_count =
    (uint8_t)(pkt->cmd >> CMD_BLINK_SHIFT);
```

## 10.5 解出 led_mask

```c
*led_mask =
    (uint8_t)(pkt->cmd & CMD_LED_MASK);
```

## 10.6 完整链条

```text
参数
↓
封包
↓
入队
↓
出队
↓
包头校验
↓
checksum 校验
↓
解包
↓
LED mask 转 GPIO mask
↓
执行
```

这已经是一个简化版的嵌入式通信处理链。

# 十一、题目 4：CAN 2.0

## 11.1 CAN

CAN：

**Controller Area Network**

中文：

**控制器局域网络**

常用于汽车、机器人、电机控制器、工业设备之间的通信。

重要特点：

> CAN 更接近共享总线 / 广播式通信，而不是简单点对点地址通信。

## 11.2 Classic CAN 标准数据帧

本次学习 11 bit 标准 ID 的 Classic CAN 数据帧。

| 字段 | 英文 | 位数 | 主要作用 |
|---|---|---:|---|
| SOF | Start of Frame | 1 bit | 帧开始 |
| ID | Identifier | 11 bit | 消息标识、参与仲裁 |
| RTR | Remote Transmission Request | 1 bit | 数据帧/远程帧 |
| IDE | Identifier Extension | 1 bit | 标准/扩展 ID |
| r0 | Reserved bit | 1 bit | 保留位 |
| DLC | Data Length Code | 4 bit | 数据长度 |
| Data | Data Field | 0~64 bit | 业务数据 |
| CRC Sequence | Cyclic Redundancy Check | 15 bit | CRC 检错 |
| CRC Delimiter | CRC Delimiter | 1 bit | 分隔 |
| ACK Slot | Acknowledge Slot | 1 bit | 接收确认 |
| ACK Delimiter | Acknowledge Delimiter | 1 bit | 分隔 |
| EOF | End of Frame | 7 bit | 帧结束 |

整体：

```text
SOF
→ Arbitration
→ Control
→ Data
→ CRC
→ ACK
→ EOF
```

# 十二、CAN 各字段重点

## 12.1 SOF

SOF：

**Start of Frame**

表示一帧 CAN 开始。

它不等于本题自定义包头 `0x0A5A`。

```text
SOF
→ CAN 标准控制位

0x0A5A
→ 自定义协议字节头
```

## 12.2 ID

ID：

**Identifier**

标准格式 11 bit。

最重要的修正：

### 错误理解

> ID 是“发给谁的地址”。

### 正确理解

```text
一个节点发送
↓
总线上所有节点都能看到
↓
各节点读取 ID
↓
决定自己是否关心
```

因此 ID 更接近：

```text
消息身份
消息类型
功能类别
```

同时还参与仲裁。

## 12.3 仲裁

简化理解：

> **数值更小的 ID 通常有更高优先级。**

所以急停、严重故障等可设计为高优先级消息。

## 12.4 RTR

RTR：

**Remote Transmission Request**

简化：

```text
RTR = 0 → 数据帧
RTR = 1 → 远程帧
```

## 12.5 IDE

IDE：

**Identifier Extension**

```text
IDE = 0 → 11 bit 标准 ID
IDE = 1 → 29 bit 扩展 ID
```

## 12.6 r0

Reserved bit，保留位。

## 12.7 DLC

DLC：

**Data Length Code**

注意区分：

```text
DLC 字段本身
→ 4 bit
```

和：

```text
DLC 的数值
→ 表示 Data 长度
```

例如：

```text
DLC = 4
→ Data = 4 Byte
→ 32 bit
```

不是 Data 只有 4 bit。

# 十三、CRC 与 checksum

CRC：

**Cyclic Redundancy Check**

中文：

**循环冗余校验**

Classic CAN 中 CRC Sequence 为 15 bit。

共同点：

```text
发送端计算
↓
接收端重新计算
↓
比较
```

区别：

```text
本题 checksum
→ 简单加法
→ 实现简单
→ 检错能力较弱

CAN CRC
→ 固定 CRC 规则
→ 更复杂
→ 检错能力更强
```

重要修正：

> CRC 相等只能说“CRC 没有检测到错误”，不能理解成数学上 100% 绝对正确。

---

# 十四、ACK

ACK：

**Acknowledge**

表示至少有节点正确接收到该帧并进行确认。

重要修正：

> **ACK 不等于电机已经执行完成。**

ACK 是通信层确认。

如果想知道电机是否真的执行成功，需要另发：

```text
状态反馈
位置反馈
故障反馈
执行结果
```

# 十六、题目 5：函数指针

普通指针保存数据地址。

函数也有代码入口地址，因此可写：

```c
void (*func)(void);
```

表示：

> `func` 是一个指向“无参、无返回值函数”的函数指针。

赋值：

```c
func = state_idle;
```

调用：

```c
func();
```

重要修正：

不是“访问函数指针的地址”，更准确是：

> **通过函数指针中保存的函数入口地址调用对应函数。**

# 十七、`typedef` 函数指针类型

```c
typedef void (*state_func)(void);
```

含义：

> 定义一种新的类型 `state_func`，它代表“指向无参无返回值函数的函数指针类型”。

```c
state_func func;
```

等价于：

```c
void (*func)(void);
```

注意：

> `typedef` 只是给类型起名字，没有创建函数，也没有创建具体变量。

# 二十一、有限状态机 FSM

FSM：

**Finite State Machine**

中文：

**有限状态机**

核心：

> 系统在有限个状态中运行；当前状态决定执行什么行为；满足条件后进行状态转移。

本题：

```text
STATE_IDLE
STATE_RUNNING
STATE_ALARM
```

当前状态：

```c
static state_t current_state = STATE_IDLE;
```

---

# 二十二、状态机执行流程

```text
读取 current_state
↓
查 state_table
↓
调用对应状态函数
↓
状态函数执行行为
↓
状态函数修改 current_state
↓
函数结束
↓
下一轮 while
↓
根据新的 current_state 调用新状态
```

状态转移：

```c
current_state = STATE_RUNNING;
```

就是从当前状态转到 RUNNING。

---

# 二十三、状态转移中的重要误区

最初容易理解为：

> “程序一直检测 current_state，只要它变了，程序马上跳到新状态函数。”

更准确：

> 状态函数先主动修改 `current_state`；当前函数继续执行；等当前函数结束并进入下一轮 `while` 后，才会按新状态查表。

因此：

> **修改 `current_state` 本身不会自动终止当前函数。**

例如把：

```c
current_state = STATE_ALARM;
```

写进 `for` 循环里，并不会自动跳出 `for`。

真正改变当前控制流需要：

```c
break;
return;
```

等语句。

所以更好的结构是：

```text
完成当前状态任务
↓
再修改 current_state
↓
下一轮进入新状态
```

---

# 二十四、为什么不用长 `switch`

传统写法：

```c
switch (current_state)
{
    case STATE_IDLE:
        state_idle();
        break;

    case STATE_RUNNING:
        state_running();
        break;

    case STATE_ALARM:
        state_alarm();
        break;
}
```

状态越多，`switch` 越长。

函数表：

```c
state_table[current_state]();
```

主循环只负责调度。

模块划分：

```text
main.c
→ 总调度

state_machine_run()
→ 状态机统一入口

state_table
→ 状态和函数的对应关系

state_xxx()
→ 各状态自己的实现
```

---

# 二十五、`state_machine_run()` 的意义

老师并没有强制一定要多设计这一层，但为了封装可以：

```c
void state_machine_run(void)
{
    ...
}
```

于是主循环：

```c
while (1)
{
    state_machine_run();
}
```

`main.c` 不需要知道：

```text
current_state
state_table
state_idle
state_running
state_alarm
```

可以把 `state_machine_run()` 理解成：

> **main 进入状态机模块的统一入口。**

# 二十六、`static`

文件级：

```c
static state_t current_state;
static void state_idle(void);
static const state_func state_table[];
```

这里 `static` 表示：

> 变量或函数只在当前 `.c` 文件内部可见。

作用：

```text
隐藏内部实现
减少外部依赖
避免名字冲突
提高模块封装性
```

注意：函数内部局部变量使用 `static` 还有另一种含义，本次没有深入展开。

---

# 二十七、`const state_table`

```c
static const state_func state_table[STATE_COUNT]
```

拆开：

```text
state_func
→ 元素是函数指针

state_table
→ 函数指针数组

const
→ 数组中的函数指针不能运行时被重新赋值

static
→ 仅本 .c 文件使用
```

因此：

```text
STATE_IDLE → state_idle
```

一旦初始化，不应该运行过程中改成：

```text
STATE_IDLE → state_alarm
```

---

# 二十八、数组越界和 NULL 检查

不能盲目：

```c
state_table[current_state]();
```

最好：

```c
if ((current_state < STATE_COUNT)
    && (state_table[current_state] != NULL))
{
    state_table[current_state]();
}
```

原因：

如果：

```text
STATE_COUNT = 3
```

合法下标只有：

```text
0 1 2
```

若错误出现：

```text
current_state = 5
```

访问：

```c
state_table[5]
```

就是数组越界，会读取数组范围外内存。

同时：

```c
state_table[current_state] != NULL
```

保证对应位置确实有有效函数地址。

# 三十六、本次主要错误与修正总表

## 1. 函数指针调用表述不够准确

错误倾向：

> “访问函数指针的地址调用函数。”

修正：

> 通过函数指针中保存的函数入口地址调用对应函数。

## 2. 混淆 `state_t` 与 `STATE_IDLE`

修正：

```text
state_t → 类型
STATE_IDLE → 枚举常量，值为 0
```

## 3. 认为状态机是“检测 current_state 变化后立即切换”

修正：

> 状态函数主动修改 `current_state`，当前函数完成后，下一轮主循环才按新状态调用新函数。

## 4. 认为修改 `current_state` 会自动中断当前函数

修正：

> 不会。`current_state` 只是普通变量；需要函数结束、`return`、`break` 等才改变当前控制流。

## 5. 认为把状态切换写进 `for` 就会直接导致循环停止

修正：

> 只修改状态变量不会停止 `for`。真正问题是逻辑状态与当前执行行为会不一致。

## 6. 把 CAN ID 过度理解为地址

修正：

> ID 是消息标识，同时参与仲裁；节点根据 ID 决定是否处理。

## 7. 混淆 DLC 字段位数与 DLC 数值

修正：

```text
DLC 字段 = 4 bit
DLC = 4 → Data = 4 Byte
```

## 8. 把 CRC 成功理解成绝对无错误

修正：

> CRC 一致只能说没有检测到错误。

## 9. 把 ACK 理解成电机执行完成

修正：

> ACK 是通信层接收确认，不是应用层执行结果。

## 10. 把 SOF 与自定义包头当成同一类东西

修正：

```text
SOF → CAN 标准控制位
0x0A5A → 本题自定义协议包头
```

## 11. 混淆逻辑 LED mask 与 GPIO pin mask

修正：

```text
协议 bit0~bit3
硬件 PB3~PB6
```

中间需要移位映射。

## 12. 把 VS Code 红线当成 Keil 编译错误

修正：

```text
VS Code includePath
≠
Keil Include Path
```

## 13. 注释掉 `buzzer.h` 却保留 buzzer 调用

修正：

> 使用函数就应包含其声明头文件，或删除调用。

# 三十七、整个 8.10 最核心的 10 个思想

1. **指针是地址工具**：用于修改外部对象、传结构体、实现输出参数。
2. **环形队列循环利用固定数组**：`head` 读、`tail` 写、`count` 判空满。
3. **位运算可在一个 Byte 内组织多个字段**：移位放位置、按位或组合、按位与提取。
4. **协议逻辑和硬件引脚是两层概念**：需要映射。
5. **封包和解包互为逆过程**。
6. **校验是通信可靠性的基础**：checksum 简单，CRC 更强。
7. **CAN ID 是消息标识与仲裁依据，不只是目标地址。**
8. **函数指针让函数可以被“表驱动”选择。**
9. **FSM = 当前状态 + 状态行为 + 状态转移。**
10. **模块化目标是让 main 少知道细节**：main 调统一接口，内部模块自己负责实现。
