## 二、任务五：非阻塞流水灯调度

### 2.1 任务目标

任务五是在前面流水灯模式的基础上，将原本依赖 `HAL_Delay()` 的阻塞式灯效改造成非阻塞调度。

最终支持四种模式：

| `signal` | 模式 | 现象 |
|---|---|---|
| `0` | `FLOW_IDLE` | 所有 LED 熄灭 |
| `1` | `FLOW_SINGLE` | 单灯依次流水 |
| `2` | `FLOW_PAIR` | 相邻双灯依次流水 |
| `3` | `FLOW_ALL` | 四灯同步闪烁 |

要求模式能够在主循环中即时切换，不能因为某个 `HAL_Delay()` 尚未结束而等待旧效果播放完。

### 2.2 为什么要去掉 `HAL_Delay()`

之前的写法本质上是：

```c
led_on(0);
HAL_Delay(250);
led_off(0);
HAL_Delay(250);
```

这种写法简单，但 `HAL_Delay()` 执行期间 CPU 会一直等待。

```text
点亮 LED
→ HAL_Delay(250)
→ CPU 在这 250 ms 内不能继续执行后面的灯效调度逻辑
```

如果此时 `signal` 已经从 `1` 改成 `3`，程序也不能立即响应，只能等 Delay 结束后才能继续。

因此任务五改成：

```text
执行一次动作
→ 记录开始时间
→ 主循环继续运行
→ 每轮检查时间是否到
→ 到期后再执行下一步
```

这就是本次作业中最核心的 **非阻塞（non-blocking）** 思想。

## 三、软件计时器的设计

### 3.1 `timer_t` 结构体

任务五中定义了：

```c
typedef struct
{
    uint32_t start_tick;
    uint32_t duration_ms;
    uint8_t active;
} timer_t;
```

三个成员的作用分别是：

- `start_tick`：记录计时开始时的系统 Tick；
- `duration_ms`：记录本次需要计时多久；
- `active`：表示当前计时器是否有效。

例如：

```c
timer_start(&led_timer, 250U);
```

如果此时 `HAL_GetTick()` 为 `1000`，则计时器中相当于保存：

```text
start_tick  = 1000
duration_ms = 250
active      = 1
```

### 3.2 计时器启动函数

```c
static void timer_start(timer_t *timer, uint32_t duration_ms)
{
    timer->start_tick = HAL_GetTick();
    timer->duration_ms = duration_ms;
    timer->active = 1U;
}
```

这个函数的意义不是“等待 duration_ms”，而是：

> 记录当前时间，并告诉程序“从现在开始，这个计时器有效”。

### 3.3 计时器查询函数

```c
static uint8_t timer_expired(timer_t *timer)
{
    if (timer->active == 0U)
    {
        return 0U;
    }

    if ((HAL_GetTick() - timer->start_tick) >= timer->duration_ms)
    {
        timer->active = 0U;
        return 1U;
    }

    return 0U;
}
```

核心判断是：

```c
HAL_GetTick() - timer->start_tick >= timer->duration_ms
```

例如：

```text
start_tick = 1000
当前 HAL_GetTick() = 1250
duration_ms = 250
```

则：

```text
1250 - 1000 = 250
```

说明时间已经到。

### 3.4 One-shot Timer：单次触发计时器

到期后：

```c
timer->active = 0U;
return 1U;
```

下一轮主循环再次查询时，因为：

```c
active == 0U
```

所以不会再次返回到期。

只有重新执行：

```c
timer_start(...);
```

才能开始下一次计时。

因此本次软件计时器属于 **One-shot Timer（单次触发计时器）**。

这一点也是 `active` 变量存在的主要意义。

## 四、LED 状态机

### 4.1 LED 状态定义

```c
typedef enum
{
    LED_STEP_ON = 0,
    LED_STEP_OFF
} led_step_t;
```

并定义：

```c
static led_step_t current_step = LED_STEP_ON;
```

`current_step` 用来记录 LED 调度当前处在哪个阶段，而不是简单表示某个 GPIO 电平。

### 4.2 SINGLE 模式运行流程

SINGLE 模式可以理解成：

```text
LED0 亮
↓ 250 ms
LED0 灭
↓ 250 ms
LED1 亮
↓ 250 ms
LED1 灭
↓
LED2 ……
```

核心逻辑：

```c
if (timer_expired(&led_timer))
{
    if (current_step == LED_STEP_ON)
    {
        led_off(current_led);
        current_step = LED_STEP_OFF;
        timer_start(&led_timer, 250U);
    }
    else
    {
        current_led++;

        if (current_led >= LED_COUNT)
        {
            current_led = 0U;
        }

        led_on(current_led);
        current_step = LED_STEP_ON;
        timer_start(&led_timer, 250U);
    }
}
```

整个灯效不是在一次 `flow_led()` 中执行完，而是：

```text
主循环每运行一轮
→ 查询一次 timer
→ 时间不到就退出
→ 时间到了才推进一个状态
```

### 4.3 PAIR 模式

PAIR 模式采用相邻双灯滑动：

```text
LED0 + LED1
→ 灭
→ LED1 + LED2
→ 灭
→ LED2 + LED3
→ 灭
→ 回到 LED0 + LED1
```

因为要访问：

```c
current_led + 1U
```

所以 `current_led` 不能走到最后一个 LED，下标边界应判断：

```c
if (current_led >= LED_COUNT - 1U)
{
    current_led = 0U;
}
```

### 4.4 ALL 模式

ALL 模式则是：

```text
四灯全部亮
↓
四灯全部灭
↓
四灯全部亮
↓
……
```

SINGLE、PAIR、ALL 三种模式的底层机制实际上相同：

```text
状态 + 单次计时器
```

不同的只是每个状态里具体操作哪些 LED。

## 五、模式切换逻辑

### 5.1 `flow_mode`

```c
typedef enum
{
    FLOW_IDLE = 0,
    FLOW_SINGLE,
    FLOW_PAIR,
    FLOW_ALL
} flow_mode;
```

模式对应关系：

```text
signal = 0 → FLOW_IDLE
signal = 1 → FLOW_SINGLE
signal = 2 → FLOW_PAIR
signal = 3 → FLOW_ALL
```

### 5.2 `update_mode()`

通过外部全局变量：

```c
extern volatile int signal;
```

判断当前模式。

```c
static void update_mode(void)
{
    if (signal == 0)
    {
        current_mode = FLOW_IDLE;
    }
    else if (signal == 1)
    {
        current_mode = FLOW_SINGLE;
    }
    else if (signal == 2)
    {
        current_mode = FLOW_PAIR;
    }
    else if (signal == 3)
    {
        current_mode = FLOW_ALL;
    }
}
```

### 5.3 为什么能即时切换

每次进入：

```c
flow_led();
```

先保存旧模式：

```c
flow_mode previous_mode = current_mode;
```

然后：

```c
update_mode();
```

再判断：

```c
if (current_mode != previous_mode)
{
    mode_init();
}
```

例如：

```text
原来 signal = 1
current_mode = FLOW_SINGLE

Watch 改成 signal = 3

下一轮 flow_led()
↓
previous_mode = FLOW_SINGLE
↓
update_mode()
↓
current_mode = FLOW_ALL
↓
发现模式发生变化
↓
mode_init()
↓
立即切换到 ALL
```

因此不需要等旧模式当前的 250 ms 周期结束。

## 六、`mode_init()` 的作用

`mode_init()` 的核心职责是：

> 每次进入新模式时，清除旧模式的运行状态，然后建立新模式的初始状态。

LED 部分：

```c
for (uint8_t i = 0U; i < LED_COUNT; i++)
{
    led_off(i);
}

current_led = 0U;
current_step = LED_STEP_ON;
led_timer.active = 0U;
```

含义：

```text
关闭旧模式留下的 LED
→ current_led 回到 0
→ 状态重新从 ON 开始
→ 旧 led_timer 立即作废
```

这一步是“即时切换”能够正确工作的关键。

## 七、任务五中遇到的问题与解决过程

### 7.1 函数声明顺序导致编译错误

加入新的 `static` 函数后，一开始出现过类似：

```text
implicit declaration
static declaration follows non-static declaration
```

原因是 C 编译器从上向下读取代码，在 `flow_led()` 调用这些函数时还没有看到它们的声明。

最终在调用前加入：

```c
static void update_mode(void);
static void timer_start(timer_t *timer, uint32_t duration_ms);
static uint8_t timer_expired(timer_t *timer);
static void mode_init(void);
```

问题解决。

**经验：** 如果函数实现写在调用位置之后，应提前提供函数原型。

### 7.2 对“计时器是否自己运行”的理解

学习过程中进一步明确：

```text
timer_t 本身不会自己执行循环
```

真正不断运行的是：

```c
while (1)
{
    flow_led();
}
```

计时器只保存：

```text
开始时间
持续时间
当前是否有效
```

每轮主循环主动查询它。

### 7.3 为什么 IDLE 不应该不断重启 timer

如果 IDLE 每轮都执行：

```c
timer_start(&led_timer, 250U);
```

那么 `start_tick` 会不断刷新，计时时间几乎永远到不了 250 ms。

因此 IDLE 下应保持计时器无效，而不是不断重新开始计时。

# 八、任务六：模式绑定蜂鸣器

## 8.1 任务目标

在任务五基础上增加蜂鸣器：

| 模式 | LED | 蜂鸣器 |
|---|---|---|
| IDLE | 全灭 | 不响 |
| SINGLE | 单灯流水 | 不响 |
| PAIR | 双灯流水 | 慢鸣 |
| ALL | 全灯闪烁 | 快鸣 |

蜂鸣节奏：

```text
PAIR：200 ms ON / 800 ms OFF
ALL ： 50 ms ON / 100 ms OFF
```

同时要求：

- 继续使用任务五的非阻塞计时机制；
- 效果逻辑中不使用 `HAL_Delay()`；
- 模式切换后蜂鸣器立即跟随；
- 不残留上一模式的蜂鸣节奏；
- GPIO 操作仍通过 `buzzer_on()` / `buzzer_off()` 封装。

---

## 九、蜂鸣器配置结构体

### 9.1 `beep_config`

```c
typedef struct
{
    uint32_t on_ms;
    uint32_t off_ms;
} beep_config;
```

表示一个蜂鸣节奏：

```text
响多久 + 停多久
```

### 9.2 `mode_config`

```c
typedef struct
{
    uint8_t buzzer_enable;
    beep_config beep;
} mode_config;
```

表示：

```text
当前模式是否允许蜂鸣
+
蜂鸣器 ON / OFF 时间配置
```

### 9.3 四种模式配置

```c
static const mode_config idle_config =
{
    0U,
    {0U, 0U}
};

static const mode_config single_config =
{
    0U,
    {0U, 0U}
};

static const mode_config pair_config =
{
    1U,
    {200U, 800U}
};

static const mode_config all_config =
{
    1U,
    {50U, 100U}
};
```

这样将“配置数据”和“执行逻辑”分离。

例如以后修改 PAIR 的蜂鸣节奏，只需改 `pair_config`，不用改 `buzzer_update()`。

---

## 十、`current_config` 指针

定义：

```c
static const mode_config *current_config = &idle_config;
```

作用：

> 始终指向当前模式对应的配置。

例如进入 PAIR：

```c
current_config = &pair_config;
```

那么：

```c
current_config->buzzer_enable
```

得到 `1U`，而：

```c
current_config->beep.on_ms
```

得到 `200U`。

进入 ALL 后，只需：

```c
current_config = &all_config;
```

相同的执行代码自动读取 `50U / 100U`。

### 10.1 `const mode_config *` 的含义

学习过程中重新确认了：

```c
const mode_config *current_config;
```

表示：

```text
指针可以改变指向
但不能通过该指针修改所指向的数据
```

例如：

```c
current_config = &pair_config;
current_config = &all_config;
```

都允许。

但通过 `current_config` 修改配置内容则不允许。

这与：

```c
mode_config * const p;
```

不同，后者表示指针本身不能再指向其他对象。

## 十一、为什么 LED 和蜂鸣器不能共用同一个计时器实例

任务六一开始讨论过是否直接复用：

```c
led_timer
```

最终明确：

> 计时器机制可以复用，但计时器状态不能共用。

因此定义：

```c
static timer_t led_timer;
static timer_t buzzer_timer;
```

原因：PAIR 模式中：

```text
LED：250 ms
蜂鸣器：200 ms ON / 800 ms OFF
```

如果共用同一个 `timer_t`：

```text
LED 启动 250 ms
↓
蜂鸣器启动 200 ms
↓
同一个 timer 的 start_tick / duration_ms 被覆盖
↓
LED 原有计时数据丢失
```

因此：

```text
复用算法 ≠ 复用运行状态
```

这也是本次学习中非常重要的工程理解。

## 十二、蜂鸣器状态机

### 12.1 状态定义

```c
typedef enum
{
    BUZZER_STEP_ON = 0,
    BUZZER_STEP_OFF
} buzzer_step_t;
```

变量：

```c
static buzzer_step_t buzzer_step = BUZZER_STEP_ON;
```

用于记录当前蜂鸣节奏处于 ON 还是 OFF 阶段。

### 12.2 为什么不能复用 LED 的 `current_step`

因为 LED 和蜂鸣器运行周期不同。

例如 PAIR 模式某一时刻可能是：

```text
LED：处于 250 ms ON 阶段
蜂鸣器：处于 800 ms OFF 阶段
```

所以必须分别保存：

```text
current_step → LED 状态
buzzer_step  → 蜂鸣器状态

led_timer    → LED 时间
buzzer_timer → 蜂鸣器时间
```

## 十三、模式切换时蜂鸣器如何清理旧状态

在 `mode_init()` 中先执行：

```c
buzzer_off();
buzzer_step = BUZZER_STEP_ON;
buzzer_timer.active = 0U;
```

作用：

```text
立即关闭上一模式的蜂鸣器
↓
废弃上一模式未完成的计时
↓
把下一次有效蜂鸣预置为 ON 阶段
```

之后通过 `switch` 选择当前配置。

最后统一判断：

```c
if (current_config->buzzer_enable)
{
    buzzer_on();
    timer_start(&buzzer_timer, current_config->beep.on_ms);
}
```

这样 IDLE / SINGLE 不会启动蜂鸣器，而 PAIR / ALL 会根据自己的配置自动启动。

---

## 十四、关于 `buzzer_step = BUZZER_STEP_ON` 的讨论

学习过程中曾讨论：

> 能不能在 `mode_init()` 公共部分直接写 `buzzer_step = BUZZER_STEP_ON`，而不是在 PAIR / ALL 两个 case 中重复写？

最终确认：可以。

这和任务五中的：

```c
current_step = LED_STEP_ON;
```

属于同一种设计思路。

在 IDLE / SINGLE 中，虽然 `buzzer_step` 被预置为 ON，但：

```text
buzzer_timer.active = 0
蜂鸣器没有启动
```

所以它只是“下一次有效调度的初始阶段”，不会造成蜂鸣器误响。

## 十五、`buzzer_update()` 独立函数

最终创建：

```c
static void buzzer_update(void)
{
    if (timer_expired(&buzzer_timer))
    {
        if (buzzer_step == BUZZER_STEP_ON)
        {
            buzzer_off();
            buzzer_step = BUZZER_STEP_OFF;
            timer_start(&buzzer_timer, current_config->beep.off_ms);
        }
        else
        {
            buzzer_on();
            buzzer_step = BUZZER_STEP_ON;
            timer_start(&buzzer_timer, current_config->beep.on_ms);
        }
    }
}
```

它只负责一件事：

> 推进蜂鸣器的 ON / OFF 状态。

### 15.1 PAIR 实际运行流程

进入 PAIR：

```text
current_config = pair_config
↓
buzzer_on()
↓
buzzer_step = ON
↓
启动 200 ms 计时
```

200 ms 到期：

```text
timer_expired() = 1
↓
buzzer_off()
↓
buzzer_step = OFF
↓
启动 800 ms 计时
```

800 ms 到期：

```text
buzzer_on()
↓
buzzer_step = ON
↓
重新启动 200 ms
```

形成：

```text
响 200
→ 停 800
→ 响 200
→ 停 800
→ ……
```

### 15.2 ALL 实际运行流程

执行逻辑完全相同，只是：

```c
current_config = &all_config;
```

于是自动读取：

```text
on_ms  = 50
off_ms = 100
```

形成：

```text
响 50
→ 停 100
→ 响 50
→ 停 100
→ ……
```

因此 PAIR 和 ALL 实际上是：

```text
同一套状态机执行逻辑
+
不同的模式配置参数
```

## 十六、为什么把 `buzzer_update()` 单独封装

一开始讨论过是否直接把蜂鸣器推进逻辑写在 `flow_led()` 末尾。

功能上可以，但蜂鸣器实际上已经具备：

```text
自己的 timer
自己的 step
自己的配置
自己的状态转换
```

它已经是一套独立状态机。

因此最终使用：

```c
buzzer_update();
```

让：

```text
flow_led()
→ 管模式与 LED 调度

buzzer_update()
→ 管蜂鸣器节奏推进
```

程序职责更清楚。

## 十七、`return` 的复习

在讨论是否需要：

```c
if (current_config->buzzer_enable == 0U)
{
    return;
}
```

时，重新复习了 `return`。

### 有返回值函数

```c
int add(int a, int b)
{
    return a + b;
}
```

作用：

```text
结束函数
+
返回结果
```

### `void` 函数

```c
void test(void)
{
    if (...)
    {
        return;
    }
}
```

这里的：

```c
return;
```

只表示：

> 立即结束整个当前函数。

与 `break`、`continue` 的区别：

```text
return   → 退出整个函数
break    → 退出当前循环或 switch
continue → 跳过本轮循环剩余部分
```

最终当前 `buzzer_update()` 没有强制加提前返回，因为 `buzzer_timer.active == 0U` 时，`timer_expired()` 已经会直接返回 `0U`，后续状态不会推进。

## 十八、任务五与任务六的完整程序运行流程

最终主流程可以概括为：

```text
while(1)
   ↓
flow_led()
   ↓
保存 previous_mode
   ↓
update_mode()
   ↓
判断模式是否改变
   ↓
如果改变
   ↓
mode_init()
   ├─ 清除旧 LED 状态
   ├─ 清除旧 led_timer
   ├─ 清除旧蜂鸣器状态
   ├─ 清除旧 buzzer_timer
   ├─ 选择 current_config
   ├─ 初始化新模式 LED
   └─ 如果需要蜂鸣，启动第一次鸣叫
   ↓
switch(current_mode)
   ↓
检查 led_timer
   ↓
到期才推进 LED 状态
   ↓
buzzer_update()
   ↓
检查 buzzer_timer
   ↓
到期才推进蜂鸣器状态
   ↓
flow_led() 返回
   ↓
while(1) 下一轮
```

整个效果运行过程中，没有为了等待 LED 或蜂鸣器而使用 `HAL_Delay()` 阻塞 CPU。

## 二十一、今天遇到的主要问题与解决过程

### 问题 1：不知道如何把阻塞式等待改成非阻塞

最开始的思维接近：

```text

→ 等待
→ 灭
```

后来转换为：

```text
亮

→ 到期后改变状态
```

这是本次学习最大的思维变化之一。

### 问题 2：函数定义顺序导致编译错误

出现 `implicit declaration` 等问题后，通过在调用前增加函数原型解决。

### 问题 3：理解 `active` 和 One-shot Timer

最终明确：

```text
到期一次
→ active 清零
→ 不会重复触发
→ 必须重新 timer_start 才能再次计时
```

### 问题 4：LED 和蜂鸣器是否可以共用一个 timer

最终判断不能，因为它们保存的运行时间不同。

解决：

```c
static timer_t led_timer;
static timer_t buzzer_timer;
```

### 问题 5：为什么要增加 `mode_config`

一开始认为可以直接在 `case FLOW_PAIR` / `case FLOW_ALL` 中写时间参数。

后来理解：

```text
配置参数
和
执行逻辑
```

应该分离。

因此把不同模式的 `buzzer_enable`、`on_ms`、`off_ms` 放进配置结构体。

### 问题 6：`const mode_config *current_config` 的含义

重新复习了 `const` 与指针，最终理解为：

```text
指针可以换目标
目标数据通过该指针只读
```

### 问题 7：`buzzer_step` 应该在哪里初始化

曾考虑是否必须在 PAIR / ALL 中分别设置。

结合任务五的 `current_step` 设计，最终统一在 `mode_init()` 公共区域预置为 `BUZZER_STEP_ON`。

### 问题 8：`buzzer_update()` 是否需要额外判断 `buzzer_enable`

曾考虑：

```c
if (current_config->buzzer_enable == 0U)
{
    return;
}
```

后来发现当前程序已经通过：

```c
buzzer_timer.active == 0U
```

阻止无效模式继续推进，因此这个判断不是必须的。

### 问题 9：忘记 `return` 的作用

重新复习：

```text
return   → 退出整个函数
break    → 退出循环或 switch
continue → 跳过当前循环剩余部分
```

### 问题 10：Debug 中如何暂停并修改 Watch

重新熟悉 Keil Debug 的 Stop、Watch、F5 继续运行流程，并最终完成四模式动态切换验证。

## 二十四、本次学习后最需要记住的几点

### 1. 非阻塞的本质

不是“不计时”，而是：

> 不在一个地方等待时间过去。

### 2. 状态机的本质

程序不需要一次完成整个动作，而是：

```text
记录当前状态
→ 每轮判断
→ 满足条件后推进一个状态
```

### 3. 软件计时器本身不会运行

真正不断运行的是主循环，计时器只是保存状态并被不断查询。

### 4. 复用机制不等于复用状态

LED 和蜂鸣器可以共用：

```c
timer_start()
timer_expired()
```

但不能共用同一个 `timer_t` 实例。

### 5. 配置和执行逻辑分离

PAIR 和 ALL 不需要写两套蜂鸣器执行代码，只需要：

```text
同一套 buzzer_update()
+
不同 mode_config
```

### 6. 模式切换必须清理旧状态

`mode_init()` 不只是程序启动时的初始化函数，它也是：

> 每次模式发生变化时，对旧模式运行状态进行清场并为新模式重新建立初始状态。
