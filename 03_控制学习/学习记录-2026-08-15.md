## 1. 作业要求最终整理

本次作业不是只让一块板完成一个功能，而是让主板、从板、VOFA 和 CANable 通过 UART、CAN 共同工作。

### 1.1 最终通信协议

#### VOFA → 主板：UART 控制帧

固定发送 5 字节：

```text
A5 | 开关 | 周期高字节 | 周期低字节 | 5A
```

- `0xA5`：帧头。
- 开关：`0` 表示关闭呼吸灯，`1` 表示开启呼吸灯。
- 周期：单位为 ms，使用两个字节传递。
- `0x5A`：帧尾。

例如开启呼吸灯、周期为 2000 ms：

```text
A5 01 07 D0 5A
```

因为：

```text
2000(十进制) = 0x07D0
周期高字节 = 0x07
周期低字节 = 0xD0
```

#### 主板 → 从板：呼吸灯命令

| 项目 | 内容 |
|---|---|
| CAN ID | `0x100` 标准帧 |
| DLC | 3 |
| `Data[0]` | 呼吸灯开关 |
| `Data[1]` | 周期高字节 |
| `Data[2]` | 周期低字节 |

#### 从板 → 主板：亮度反馈

| 项目 | 内容 |
|---|---|
| CAN ID | `0x200` 标准帧 |
| 发送频率 | 100 Hz，即每 10 ms 一帧 |
| DLC | 4，即 `sizeof(float)` |
| 数据 | 当前呼吸灯归一化亮度 `0.0f ~ 1.0f` 的原始 4 字节 |

#### CANable → 主板和从板：蜂鸣器命令

| 项目 | 内容 |
|---|---|
| CAN ID | `0x123` 标准帧 |
| DLC | 至少 1 |
| `Data[0]` | 蜂鸣次数 `N` |

主板和从板都放行 `0x123`，所以两块板都会执行蜂鸣器任务。

#### 两块板产生的噪声报文

| 发送方 | ID | 帧类型 | 频率 |
|---|---:|---|---:|
| 主板 | `0x012` | 标准帧 | 500 Hz |
| 从板 | `0x02010101` | 扩展帧 | 500 Hz |

500 Hz 表示：

```text
周期 = 1 / 500 s = 2 ms
```

#### 其它约定

- CAN 波特率：1 Mbps。
- VOFA 输出协议：FireWater，即发送可读数字文本并以换行结束。
- 两颗流水灯用于显示板子正在正常运行。

## 2. 今天首先解决的核心问题：主板和从板怎么组织工程

一开始最容易想到的是创建两个完全独立的工程：一个主板工程，一个从板工程。这样当然可以，但相同代码会复制两份，后续修改协议、任务或驱动时容易漏改其中一份。

本项目采用的方案是：

```text
同一套源码
├─ 主板编译目标：定义 IS_MASTER_BOARD
└─ 从板编译目标：定义 IS_SLAVE_BOARD
```

角色判断集中在 [protocol.h](User/Inc/protocol.h)：

```c
#if defined(IS_MASTER_BOARD)
    /* 主板专用代码 */
#elif defined(IS_SLAVE_BOARD)
    /* 从板专用代码 */
#endif
```

这样做的好处：

1. CAN 消息结构、蜂鸣器、流水灯和呼吸灯等公共代码只维护一份。
2. 主板只编译 UART 和 VOFA 转发逻辑。
3. 从板只创建 100 Hz float 发送任务。
4. 主从板的噪声 ID、帧类型和接收业务 ID 可以通过宏自动切换。

今天建立的一个重要认识是：`#if defined(...)` 是**编译阶段选择代码**，不是程序运行到这里再判断。主板固件里不会包含从板专用分支，反过来也一样。

## 3. FreeRTOS 工程环境的复现

### 3.1 ARM_CM4F 文件问题

在 CubeMX 生成的工程中，FreeRTOS 可移植层可能使用：

```text
Middlewares/Third_Party/FreeRTOS/Source/portable/RVDS/ARM_CM4F
```

而当前编译环境需要的实现来自固件库中的：

```text
Repository/STM32Cube_FW_F4_V1.27.0/
Middlewares/Third_Party/FreeRTOS/Source/portable/GCC/ARM_CM4F
```

今天区分了两种处理范围：

1. 替换当前项目 `RVDS/ARM_CM4F` 中的文件，只修复当前已经生成的工程。
2. 替换 CubeMX 固件仓库模板中的对应文件，让以后重新生成工程时也使用正确文件。

需要记住：以后如果重新生成 CubeMX 代码，要先确认模板是否已经修复；否则生成操作可能重新覆盖项目中的可移植层文件。

### 3.2 CubeMX 自动生成与自己编写代码的边界

CubeMX 主要负责生成：

- 外设句柄和初始化函数；
- GPIO、CAN、UART、TIM 的基本配置；
- FreeRTOS 任务属性、句柄和任务创建语句；
- `main()` 中的初始化顺序。

例如 [freertos.c 第 168 行](Core/Src/freertos.c#L168)：

```c
LEDTaskHandle = osThreadNew(LED_Task, NULL, &LEDTask_attributes);
```

通常任务创建框架由 CubeMX 根据配置生成，而 `LED_Task()` 循环中真正要完成什么，是我们自己实现的业务逻辑。

重新生成代码时，手写内容应尽量放在 `USER CODE BEGIN/END` 区域或独立的 `User` 模块中。

## 4. 程序分层思路

今天把程序拆成了三层理解：

```text
硬件/中断层
    ↓ 把消息快速取出
FreeRTOS 队列
    ↓ 安全地跨中断、跨任务传递
业务任务层
    ↓ 识别协议并调用 LED、蜂鸣器、UART、CAN 功能
```

### 4.1 为什么不把所有逻辑都写在中断回调里

CAN/UART 回调当然可以直接判断 ID、控制蜂鸣器或解析数据，但中断应尽量短：

- 中断执行时会影响普通任务调度。
- `osDelay()` 不能在中断中使用。
- UART 文本格式化、蜂鸣器等待、协议分发都不适合长时间占用中断。
- 业务增加以后，中断函数会越来越难维护。

所以当前结构是：回调负责“接收并入队”，任务负责“取出并处理”。

### 4.2 CAN 硬件 FIFO 和 FreeRTOS 软件队列不是同一个东西

CAN 外设自带 FIFO，用于临时保存已经被硬件过滤器接收的 CAN 报文。

FreeRTOS 消息队列由程序创建，用于把数据安全地传给任务。

数据路径是：

```text
CAN 总线
→ 硬件过滤器
→ CAN FIFO0
→ CAN 接收中断回调
→ can_rx_queue
→ CAN_Task
```

UART 没有与 CAN FIFO 完全相同的报文 FIFO 机制。本项目由 HAL 中断接收缓冲区接收 5 字节，再放入 `uart_rx_queue`。

## 5. 公共协议与数据结构

公共定义位于 [protocol.h](User/Inc/protocol.h)。

### 5.1 三个业务 ID

```c
#define CMD_ID   0x100U
#define FLOAT_ID 0x200U
#define BEEP_ID  0x123U
```

统一定义 ID，可以避免在不同文件中重复写“魔法数字”。协议变化时只需要集中修改。

### 5.2 CAN 队列消息

```c
typedef struct {
    uint32_t id;
    uint8_t data[8];
} CanMsg_t;
```

它表示从 CAN FIFO 取出并准备交给任务的一整帧业务信息。

### 5.3 呼吸灯命令

```c
typedef struct {
    uint8_t  on_off;
    uint16_t period_ms;
} BreathCmd_t;
```

串口帧或 CAN 字节先被解析为这个结构，再交给呼吸灯任务。这样呼吸灯模块不需要知道命令最初来自 UART 还是 CAN。

## 7. 完整数据流复现

### 7.1 VOFA 控制主板和从板呼吸灯

#### 第一步：UART 中断接收

[UART_Start_Receive()](User/Src/UART_IRQHandler.c#L7) 调用：

```c
HAL_UARTEx_ReceiveToIdle_IT(&huart1, rx_buffer, 5);
```

收到数据或出现空闲事件后，HAL 调用 [HAL_UARTEx_RxEventCallback()](User/Src/UART_IRQHandler.c#L12)。回调检查：

- 是否为 USART1；
- 实际长度是否为 5；
- 帧头是否为 `0xA5`；
- 帧尾是否为 `0x5A`。

有效帧被复制进 `uart_rx_queue`，之后立即重新开启下一次接收。

#### 第二步：主板解析 UART 帧

[UART_Task()](Core/Src/freertos.c#L319) 从队列取出一帧，并解析：

```c
cmd.on_off = frame[1];
cmd.period_ms = (frame[2] << 8) | frame[3];
```

为什么高字节要左移 8 位：

```text
高字节原来位于 16 位数字的 bit15~bit8
低字节位于 bit7~bit0
```

例如：

```text
0x07 << 8 = 0x0700
0x0700 | 0xD0 = 0x07D0 = 2000
```

之前讨论过滤器 ID 左移 5 位，是因为标准 CAN ID 在过滤器寄存器中从 bit15 到 bit5 对齐；这里周期左移 8 位则是为了拼接两个普通字节。这是两个不同的位移场景。

#### 第三步：主板自己执行

主板把 `BreathCmd_t` 放进 `breath_cmd_queue`。`Breath_Task` 取出后调用：

```c
Led_Breath_SetCmd(cmd.on_off, cmd.period_ms);
```

#### 第四步：主板转发给从板

主板将命令拆回 CAN 字节：

```c
TxData[0] = cmd.on_off;
TxData[1] = (uint8_t)(cmd.period_ms >> 8);
TxData[2] = (uint8_t)(cmd.period_ms & 0xFF);
```

然后以 `0x100` 标准数据帧发送。实现位置：[freertos.c 第 380—402 行](Core/Src/freertos.c#L380)。

#### 第五步：从板接收并执行

从板过滤器放行 `0x100`。CAN 回调把消息放进 `can_rx_queue`，`CAN_Task` 再拼出 `BreathCmd_t` 并放进 `breath_cmd_queue`，最后仍由 `Breath_Task` 执行。

因此，主从板虽然命令来源不同，但最后共用相同的呼吸灯控制模块。

### 7.2 从板亮度反馈到 VOFA

数据路径：

```text
从板 Breath_Task 更新 duty
→ Float_Task 读取归一化亮度
→ CAN 0x200，每 10 ms 发送
→ 主板 CAN 硬件过滤器
→ CAN 回调
→ can_rx_queue
→ CAN_Task
→ vofa_tx_queue
→ UART_Task
→ "0.xxx\n"
→ VOFA FireWater 曲线
```

#### float 如何装入 CAN

从板 [Float_Task()](Core/Src/freertos.c#L463) 使用：

```c
memcpy(tx_data, &brightness, sizeof(brightness));
```

这不是进行数值换算，而是把 `float` 在内存中的 4 个原始字节复制到 CAN 数据区。

主板收到后反向复制：

```c
memcpy(&brightness, Msg.data, sizeof(float));
```

主板再使用 `snprintf()` 转为 FireWater 需要的文本：

```c
snprintf(tx_buffer, sizeof(tx_buffer), "%.3f\n", brightness);
```

### 7.3 CANable 控制两块板蜂鸣

主板和从板的过滤器都放行 `0x123`。

`CAN_Task` 识别 `BEEP_ID` 后，将 `Data[0]` 放进 `beep_queue`：

```c
osMessageQueuePut(beep_queue, &Msg.data[0], 0, 0);
```

两块板各自都有一个 `buzzer_Task`，所以都会从自己的队列取出次数并调用 `Beep(count)`。

[buzzer_Task()](Core/Src/freertos.c#L229) 还做了两层保护：

- 次数为 0 时不蜂鸣；
- 次数大于 20 时限制为 20，避免长时间占用任务。

### 7.4 500 Hz 噪声

[Noise_Task()](Core/Src/freertos.c#L298) 使用绝对周期延时：

```c
last += 2;
osDelayUntil(last);
noise_task();
```

主板发送 `0x012` 标准帧，从板发送 `0x02010101` 扩展帧，具体组帧位于 [Noise_Task.c](User/Src/Noise_Task.c)。

`osDelayUntil()` 以固定时间点为目标，比“执行一次再 `osDelay(2)`”更不容易因代码执行时间而逐渐漂移。

## 8. CAN 硬件过滤器的复现

过滤器配置位于 [can.c 第 65—90 行](Core/Src/can.c#L65)。

当前使用：

```c
FilterScale = CAN_FILTERSCALE_16BIT;
FilterMode  = CAN_FILTERMODE_IDLIST;
```

16 位列表模式的一个过滤器组可以填写 4 个标准 ID。项目实际只需要两个，因此重复填写：

```c
FilterIdHigh       = RX_BUSINESS_ID;
FilterIdLow        = BEEP_ID;
FilterMaskIdHigh   = RX_BUSINESS_ID;
FilterMaskIdLow    = BEEP_ID;
```

这里虽然字段名中有 `Mask`，但在列表模式下，这四个位置都被当成 ID 槽，不是掩码。

角色宏决定 `RX_BUSINESS_ID`：

- 主板：`FLOAT_ID`，所以只接收 `0x200` 和 `0x123`。
- 从板：`CMD_ID`，所以只接收 `0x100` 和 `0x123`。

调用 `HAL_CAN_ConfigFilter()` 完成配置，再执行：

```c
HAL_CAN_Start(&hcan1);
HAL_CAN_ActivateNotification(&hcan1, CAN_IT_RX_FIFO0_MSG_PENDING);
```

之后过滤器由 CAN 硬件自动工作，不需要任务不断调用“过滤函数”。不匹配的噪声报文不会进入 FIFO0，也不会触发本项目的 FIFO0 消息回调。

### 标准 ID 为什么左移 5 位

标准 CAN ID 是 11 位。STM32 的 16 位过滤器槽需要把这 11 位放在 bit15~bit5，因此：

```c
#define CAN_STD_ID_16BIT(id) ((id) << 5)
```

左移 5 位是寄存器格式要求，不是随意选择。

## 9. 呼吸灯算法复现

实现位于 [Led_Breath.c](User/Src/Led_Breath.c)。

### 9.1 用 100 步表示一个完整周期

```c
step_ms = period_ms / 100;
```

例如周期 2000 ms：

```text
每一步 = 2000 / 100 = 20 ms
```

`Breath_Task` 每经过一个 `step_ms` 调用一次 `breath_lights()`，`phase` 从 0 走到 99，然后重新回到 0。

### 9.2 余弦曲线

```c
duty = (1 - cos(2π × phase / 100)) / 2 × 1999;
```

分段理解：

1. `cos()` 原范围为 `-1 ~ 1`。
2. `1 - cos()` 得到 `0 ~ 2`。
3. 再乘 `0.5` 得到 `0 ~ 1`。
4. 乘 `1999` 得到 PWM 比较值 `0 ~ 1999`。

两路 PWM 分别设置为：

```c
duty
1999 - duty
```

所以两颗呼吸灯呈现一亮一暗的互补效果。

### 9.3 开关和周期保护

[Led_Breath_SetCmd()](User/Src/Led_Breath.c#L7) 将周期限制在 200~10000 ms，避免周期过小造成步长为 0，也避免周期过大导致效果过慢。

关闭命令会立刻把两路比较值清零，不必等到下一次呼吸更新。

### 9.4 第一次循环周期问题

任务启动时还没有收到控制命令，所以 `step_ms` 使用默认值 20 ms。收到第一条有效命令后，才按新周期运行。

当前方案的优点是任务可以立即进入稳定循环；因为默认 `breath_on = 0`，第一次命令到来前不会误亮。若以后要求“收到首条命令前完全不运行更新”，可以让任务先阻塞等待第一条命令，但本作业没有必要。

## 10. 流水灯与蜂鸣器复现

### 10.1 流水灯

[running_lights()](User/Src/Led_Flow.c#L4) 使用静态变量保存上一次状态，每次调用都翻转：

```c
run_led = !run_led;
```

然后让 LED1 和 LED2 保持相反电平。[LED_Task()](Core/Src/freertos.c#L208) 周期调用它。

`GPIO_PIN_SET` 是输出高电平，`GPIO_PIN_RESET` 是输出低电平；它们不是“恢复默认状态”。LED 到底是高电平点亮还是低电平点亮，取决于开发板原理图中的接线方式。

### 10.2 蜂鸣器

[Beep()](User/Src/Beep.c#L4) 循环 `count` 次，每次：

```text
高电平 100 ms
低电平 100 ms
```

它在普通 FreeRTOS 任务中执行，所以可以使用 `osDelay()`。`osDelay()` 只阻塞当前蜂鸣器任务，不会阻塞整个 FreeRTOS，也不会妨碍 CAN、UART 和 LED 任务继续运行。

## 11. 阻塞、非阻塞与队列的认识

### 11.1 `osMessageQueueGet()` 的超时参数

```c
osMessageQueueGet(queue, &message, 0, timeout);
```

- `timeout = 0`：队列空时立即返回，属于非阻塞读取。
- `timeout = osWaitForever`：队列空时挂起当前任务，直到收到消息。

蜂鸣器和 CAN 调度任务没有消息时没有别的事情，因此使用 `osWaitForever` 最合理，不浪费 CPU。

UART 任务同时要处理“接收命令”和“发送 VOFA 波形”两个队列，所以分别用 `timeout = 0` 轮询，并在末尾 `osDelay(1)` 让出 CPU。

### 11.2 队列读取不是复制整个队列

```c
osMessageQueueGet(can_rx_queue, &Msg, 0, osWaitForever);
```

只把队头的一条 `CanMsg_t` 复制到 `Msg`，并把这一条从队列中移除，不会把整个队列复制过来。

### 11.3 CAN 发送邮箱与软件待发送队列

CAN 外设自带发送邮箱，但邮箱只解决硬件短暂排队，不等于无限软件 FIFO。如果连续高速产生多条必须保证发送的业务回复，而邮箱又满了，就需要软件队列保存待发送报文并统一重试。

如果只要求避免“邮箱满就进入死循环”，也可以保存一个 pending 标志并在后续重试；如果每一条命令都不能丢，环形队列/FreeRTOS 队列更可靠。

本次作业正常逐条验收时，当前直接调用 `HAL_CAN_AddTxMessage()` 的方式通常足够，但返回值仍是以后可以继续增强的地方。

## 12. 今天重点澄清的函数知识

### `osThreadNew()`

CMSIS-RTOS2 提供的任务创建函数。它创建并调度任务；传入的 `LED_Task`、`CAN_Task` 等任务入口函数是项目自己实现的。

### `osMessageQueueNew()`

创建软件消息队列，需要提供消息数量和单条消息大小。

### `osMessageQueuePut()`

把一条消息的内容复制进队列。传入的是消息地址，但队列保存的是指定大小的数据副本。

### `osMessageQueueGet()`

从队头复制一条消息到目标变量并移除该条消息。

### `HAL_CAN_GetRxMessage()`

从 CAN 硬件 FIFO 读取一帧的报文头和数据。它负责“从硬件取出”，而 FreeRTOS 队列负责“交给任务”。

### `HAL_CAN_AddTxMessage()`

尝试把一帧报文提交到 CAN 发送邮箱。返回 `HAL_OK` 表示成功装入邮箱，不表示对方业务任务已经处理。

### `HAL_UARTEx_ReceiveToIdle_IT()`

以中断方式接收数据，并允许由空闲事件报告本次实际接收长度。对应回调是 `HAL_UARTEx_RxEventCallback()`。

普通 `HAL_UART_Receive_IT()` 收满指定长度后对应 `HAL_UART_RxCpltCallback()`。

### `(void)函数调用`

例如：

```c
(void)HAL_CAN_AddTxMessage(...);
```

`(void)` 明确表示程序有意忽略返回值。不写通常也能编译，但可能产生“返回值未使用”警告。它不会改变函数是否执行，也不会让调用自动成功。

更稳妥的实现仍然是检查返回值并决定重试、入队或记录错误。

- 两块板的 LED1、LED2 应持续交替闪烁。
- 这说明 RTOS 已启动并且 `LED_Task` 正常调度。

### 13.3 VOFA 控制测试

依次发送：

```text
A5 01 07 D0 5A    开启，周期 2000 ms
A5 01 03 E8 5A    开启，周期 1000 ms
A5 00 07 D0 5A    关闭
```

检查：

- 主板呼吸灯响应；
- 从板呼吸灯同步响应；

### 13.4 蜂鸣器测试

CANable 发送：

```text
ID:   0x123 标准帧
DLC:  1
Data: 03
```

期望主板和从板各蜂鸣 3 次。

注意 CANable 软件中的 `Extended` 不能勾选，否则它发送的是扩展帧，无法匹配标准帧过滤器中的 `0x123`。

### 13.5 频率测试

- 主板 `0x012`：约 500 帧/s。
- 从板 `0x02010101`：约 500 帧/s。
- 从板 `0x200`：约 100 帧/s。

### 13.6 过滤器测试

理想结果：

- 主板接收回调只出现 `0x200`、`0x123`。
- 从板接收回调只出现 `0x100`、`0x123`。
- 两块板都不会因为对方噪声进入业务接收回调。

可以在回调或 `CAN_Task` 设置断点、观察计数器或查看队列内容进行验证。

## 14. 当前实现中值得继续注意的地方

这些不一定妨碍基础验收，但以后完善程序时需要记住。

1. 多处 `osMessageQueuePut()` 使用 `timeout = 0` 且未检查返回值；队列满时消息会被丢弃。
2. 多处 `HAL_CAN_AddTxMessage()` 未检查返回值；邮箱繁忙时无法得知本帧是否成功提交。
3. UART 当前按一次回调恰好得到 5 字节完整帧处理；如果串口数据被拆成多次到达，会丢弃不完整部分，复杂通信中应设计累积解析缓冲区。
4. UART 日志和 FireWater 数值共用 USART1，VOFA 显示时要确认文本格式不会影响曲线解析。
5. 当前 CAN 回调保存 `RxHeader.StdId`，因为业务过滤器只放行标准业务帧，当前够用；如果未来允许扩展业务帧，应根据 `IDE` 选择 `StdId` 或 `ExtId`，并在队列消息中保留帧类型和 DLC。
6. CAN 初始化启用了 FIFO1 通知，但当前过滤器全部分配到 FIFO0，且项目只实现 FIFO0 消息回调；FIFO1 通知目前没有业务作用。
7. `LED_Task` 的周期值当前直接按 tick 增加 100。若 FreeRTOS tick 不再是 1 ms，最好使用 `pdMS_TO_TICKS(100U)` 明确单位。

## 15. 今天形成的总体理解

这次复现最重要的不是记住某一行代码，而是理解下面这条主线：

```text
先规定协议
→ 再决定每块板收什么、发什么
→ 用硬件过滤器挡住无关报文
→ 中断只负责把有效消息搬进队列
→ CAN_Task/UART_Task 负责协议解析和分发
→ 各业务任务只关心自己的功能
```

程序模块化之后，每个任务都可以用一句话解释：

- 中断：快速搬运数据。
- 队列：安全传递数据。
- `CAN_Task`：识别和分流 CAN 消息。
- `UART_Task`：连接 VOFA、主板和 CAN。
- `Breath_Task`：按照参数生成呼吸效果。
- `Float_Task`：定时上报从板亮度。
- `Noise_Task`：按 500 Hz 制造要求中的噪声。
- `buzzer_Task`：按次数执行蜂鸣。
- `LED_Task`：显示系统仍在运行。

能够从“消息从哪里来、经过什么队列、由哪个任务处理、最后控制什么硬件”四个问题追踪一项功能，就已经掌握了这个工程最核心的逻辑。
