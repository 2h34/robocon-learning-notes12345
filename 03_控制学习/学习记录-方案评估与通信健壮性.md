## 1. 当前作业方案的总体评价

### 1.1 总体结论

当前实现的主要功能和架构方向是正确的，基础验收链路已经具备：

```text
VOFA UART 指令
→ 主板解析
→ 主板自己控制呼吸灯
→ CAN 0x100 转发给从板
→ 从板控制呼吸灯

从板当前亮度
→ CAN 0x200，100 Hz
→ 主板
→ UART FireWater
→ VOFA 曲线

CANable 0x123
→ 主板和从板
→ 两块板蜂鸣器分别响应
```

当前方案最大的优点是结构清楚，最大的不足是对异常输入和资源忙碌情况考虑较少。

### 1.2 当前实现的优点

#### 主从板共用一套源码

通过：

```c
IS_MASTER_BOARD
IS_SLAVE_BOARD
```

在编译阶段选择主板或从板代码，公共模块只维护一份，避免两个独立工程逐渐不一致。

#### 中断与业务任务分离

当前基本数据流是：

```text
硬件中断回调
→ 快速取出数据
→ 放入 FreeRTOS 队列
→ 普通任务解析协议并执行功能
```

这样不会把蜂鸣器延时、文本格式化等耗时操作放进中断。

#### CAN 使用硬件过滤器

主板只放行：

```text
0x200、0x123
```

从板只放行：

```text
0x100、0x123
```

噪声报文在硬件层被挡住，不需要进入中断后再由软件丢弃。

#### 功能模块比较清楚

项目已经将流水灯、蜂鸣器、呼吸灯、CAN 回调、UART 回调和噪声发送拆到不同模块，FreeRTOS 任务的职责也基本清楚。

#### 周期任务采用绝对时间延时

500 Hz 噪声和 100 Hz float 反馈使用 `osDelayUntil()`，比每次执行后再简单 `osDelay()` 更不容易累计漂移。

### 1.3 当前实现的主要不足

讨论中总结出的改进点包括：

1. CAN 队列消息没有保存 `DLC`、`IDE`、`RTR`。
2. 业务任务没有检查报文数据长度。
3. 多处没有检查 `osMessageQueuePut()` 返回值。
4. 多处没有处理 `HAL_CAN_AddTxMessage()` 失败。
5. UART 默认一次回调正好收到 5 字节，不适应分包和粘包。
6. UART 使用阻塞发送，数据量大时会暂时阻塞发送任务。
7. FireWater 数值和普通日志共用同一个 UART，可能干扰 VOFA 解析。
8. 部分时间直接使用 tick 数，默认假定 1 tick 等于 1 ms。
9. PWM 最大值 `1999` 写死在呼吸灯模块中。
10. 部分注释和当前代码已经不同步。

最终形成的判断是：这些问题并不都需要在本次作业验收前解决。应先保证基本链路跑通，再按风险和实际现象逐步增强。

## 2. CAN 报文为什么要保存 DLC、IDE 和 RTR

### 2.1 最初疑问

讨论中提出：

> 如果收到了 ID 为 `0x200`、但 DLC 只有 1 的报文，程序仍然会按照 float 读取 4 字节。这个问题是不是只需要在 CAN Callback 里判断一次？

最终结论是：不是简单地只在 Callback 中增加一个业务判断，而是分成两层。

```text
CAN Callback
→ 保存报文的客观信息

CAN_Task
→ 按业务协议检查报文是否合法
```

### 2.2 DLC 的含义

DLC 是 Data Length Code，表示当前 CAN 报文有几个有效数据字节。

经典 CAN 中：

```text
DLC=1 → 只有 Data[0] 有效
DLC=3 → Data[0]~Data[2] 有效
DLC=4 → Data[0]~Data[3] 有效
DLC=8 → Data[0]~Data[7] 有效
```

当前业务协议要求：

| ID | 功能 | 合理 DLC |
|---:|---|---:|
| `0x123` | 蜂鸣次数 | 至少 1，严格协议可要求等于 1 |
| `0x100` | 开关和周期 | 等于 3 |
| `0x200` | 一个 float | 等于 `sizeof(float)`，当前为 4 |

如果 `0x200` 的 DLC 只有 1，却执行：

```c
memcpy(&brightness, Msg.data, sizeof(float));
```

程序会读 4 字节，但后面 3 字节不是这帧报文的有效内容，得到的 float 不可信。

### 2.3 更完整的 CAN 队列消息

原结构只保存 ID 和 8 字节数据。更完善的形式是：

```c
typedef struct
{
    uint32_t id;
    uint8_t  ide;
    uint8_t  rtr;
    uint8_t  dlc;
    uint8_t  data[8];
} CanMsg_t;
```

字段含义：

- `id`：标准或扩展 ID。
- `ide`：标准帧还是扩展帧。
- `rtr`：数据帧还是远程帧。
- `dlc`：本帧有效数据长度。
- `data`：报文数据。

队列创建使用了：

```c
sizeof(CanMsg_t)
```

因此结构体变大后，队列单条消息大小会自动更新。

### 2.4 Callback 的职责

Callback 适合完成：

```text
从 CAN FIFO 读取报文
→ 保存 IDE、RTR、DLC
→ 根据 IDE 选择 StdId 或 ExtId
→ 复制有效数据
→ 放进 can_rx_queue
```

核心思路：

```c
msg.ide = rx_header.IDE;
msg.rtr = rx_header.RTR;
msg.dlc = rx_header.DLC;

if (rx_header.IDE == CAN_ID_STD)
{
    msg.id = rx_header.StdId;
}
else
{
    msg.id = rx_header.ExtId;
}

memset(msg.data, 0, sizeof(msg.data));

if (msg.dlc <= 8)
{
    memcpy(msg.data, rx_data, msg.dlc);
    osMessageQueuePut(can_rx_queue, &msg, 0, 0);
}
```

### 2.5 CAN_Task 的职责

业务合法性放在 `CAN_Task` 中检查。

蜂鸣器：

```c
if (Msg.ide == CAN_ID_STD &&
    Msg.rtr == CAN_RTR_DATA &&
    Msg.id == BEEP_ID &&
    Msg.dlc >= 1)
{
    osMessageQueuePut(beep_queue, &Msg.data[0], 0, 0);
}
```

主板接收 float：

```c
if (Msg.ide == CAN_ID_STD &&
    Msg.rtr == CAN_RTR_DATA &&
    Msg.id == FLOAT_ID &&
    Msg.dlc == sizeof(float))
{
    float brightness;
    memcpy(&brightness, Msg.data, sizeof(brightness));
}
```

从板接收呼吸灯命令：

```c
if (Msg.ide == CAN_ID_STD &&
    Msg.rtr == CAN_RTR_DATA &&
    Msg.id == CMD_ID &&
    Msg.dlc == 3)
{
    cmd.on_off = Msg.data[0];
    cmd.period_ms =
        ((uint16_t)Msg.data[1] << 8) |
        Msg.data[2];
}
```

### 2.6 最终理解

```text
Callback 保存“收到的是什么”
CAN_Task 判断“它是否符合我们的业务协议”
```

虽然也能把所有判断写进 Callback，但这样会让中断越来越复杂，破坏当前模块化结构。

## 3. UART 为什么需要累积解析

### 3.1 最初疑问

当前代码要求：

```c
Size == 5
```

并检查：

```text
A5 ... 5A
```

疑问是：如果 UART 没有一次正好收到完整 5 字节，该怎么办？

### 3.2 UART 是字节流，不认识业务帧

CAN 硬件知道一帧报文的 ID 和 DLC，但 UART 只看到连续字节。

UART 不知道：

- `0xA5` 是帧头；
- `0x5A` 是帧尾；
- 每帧长度为 5 字节。

这些规则属于用户协议。

同一帧可能这样到达：

```text
第一次回调：A5 01
第二次回调：07 D0 5A
```

也可能一次收到两帧：

```text
A5 01 07 D0 5A A5 00 07 D0 5A
```

因此：

> 一次 UART Callback 不一定等于一帧业务数据。

### 3.3 简单累积解析器

对于固定 5 字节协议，可以维护：

```c
static uint8_t frame_buffer[5];
static uint8_t frame_index;
```

处理逻辑：

```text
还没有帧头
→ 丢弃其它字节，等待 0xA5

找到 0xA5
→ 开始累计后续字节

累计到 5 字节
→ 检查最后一个是不是 0x5A

正确
→ 完整帧入队

错误
→ 重新寻找下一帧头
```

UART Callback 每次收到多少字节都可以逐字节交给解析器：

```c
for (uint16_t i = 0; i < Size; i++)
{
    UART_Protocol_PushByte(uart_rx_block[i]);
}
```

### 3.4 环形缓冲区

环形缓冲区适合更连续、更高速或变长的 UART 数据。

```c
#define UART_RING_SIZE 128

typedef struct
{
    uint8_t buffer[UART_RING_SIZE];
    volatile uint16_t head;
    volatile uint16_t tail;
} UartRing_t;
```

- `head`：下一个字节写入位置。
- `tail`：下一个字节读取位置。
- 写到数组结尾后回到索引 0。

典型分工：

```text
UART Callback
→ 快速把字节写入环形缓冲区

UART_Task
→ 从环形缓冲区读取字节
→ 查找 A5
→ 判断第 5 字节是否为 5A
→ 解析完整帧
```

### 3.5 当前作业的取舍

当前协议固定 5 字节、控制频率不高，先学习简单累积解析器更合适。完整环形缓冲区是可选扩展，不是本次验收必做项。

## 4. UART 的主要发送方式

### 4.1 阻塞发送

```c
HAL_UART_Transmit(
    &huart1,
    data,
    length,
    timeout
);
```

调用任务等待发送完成或超时后，函数才返回。

优点：简单，适合短数据和低频发送。  
缺点：发送期间当前任务不能继续执行其它代码。

`timeout=100` 是最大等待 100 ms，不表示每次一定等待 100 ms。正常发送完成会提前返回。

### 4.2 中断发送

```c
HAL_UART_Transmit_IT(
    &huart1,
    data,
    length
);
```

启动发送后函数很快返回，HAL 通过 UART 中断继续提供后续字节。全部发送完成后进入：

```c
HAL_UART_TxCpltCallback()
```

发送缓冲区必须一直有效到完成回调发生，不能使用已经失效或被覆盖的局部数组。

### 4.3 DMA 发送

```c
HAL_UART_Transmit_DMA(
    &huart1,
    data,
    length
);
```

DMA 从内存搬运数据到 UART，CPU 参与更少，适合较长或频繁的数据。它同样需要管理发送忙状态和缓冲区生命周期。

### 4.4 对比

| 方式 | 调用后何时返回 | CPU 参与 | 适合场景 |
|---|---|---:|---|
| 阻塞 | 发送完或超时 | 高 | 短数据、低频、入门调试 |
| 中断 | 启动后很快返回 | 中 | 中等数据、异步发送 |
| DMA | 启动后很快返回 | 低 | 长数据、高频连续发送 |

### 4.5 日志使用另一个 UART 是什么意思

通常确实表示再开启一个硬件串口，例如 USART2：

```text
USART1
├─ 接收 VOFA 命令
└─ 输出 FireWater 数值

USART2
└─ 输出普通调试日志
```

这需要：

- CubeMX 开启另一个 UART/USART；
- 配置 TX 引脚和波特率；
- 生成新的 UART 句柄；
- 需要时增加第二个 USB 转串口模块；
- 两边共地。

当前板子资源不足时，可以不新增串口，而是在画波期间关闭普通日志。

## 5. 当前工程有没有必要建立 UART_TX_Task

### 5.1 最初疑问

讨论了 UART 发送队列以后产生了疑问：

> 当前工程需要 UART 发送的只有主板到 VOFA，还有必要专门创建 UART_TX_Task 吗？

### 5.2 检查当前数据流

当前两个 UART 发送调用都位于同一个 `UART_Task`：

```text
UART_Task
├─ 发送呼吸参数日志
└─ 发送 VOFA 亮度
```

CAN_Task 并不直接调用 `HAL_UART_Transmit()`，而是：

```text
CAN_Task
→ brightness 放入 vofa_tx_queue
→ UART_Task 取出
→ UART_Task 统一发送
```

因此当前已经只有一个 USART1 发送者，不存在多个任务同时争抢 `huart1`。

### 5.3 最终结论

当前作业没有必要额外创建 UART_TX_Task。

如果硬加，会形成：

```text
CAN_Task
→ vofa_tx_queue
→ UART_Task
→ uart_tx_queue
→ UART_TX_Task
→ USART1
```

消息多转发一次，但当前没有明显收益，属于过度设计。

## 6. 什么情况下真正需要 UART 发送队列

假设未来有多个任务直接要求同一个串口发送：

```text
Sensor_Task ─┐
CAN_Task ────┼→ USART1
Fault_Task ──┘
```

如果它们分别调用 `HAL_UART_Transmit()` 或异步发送函数，可能出现：

- UART 正忙，后一次调用返回 `HAL_BUSY`；
- 消息顺序难以统一；
- 多个任务都需要处理发送状态；
- DMA 缓冲区生命周期难以管理。

此时适合改为：

```text
Sensor_Task ─┐
CAN_Task ────┼→ uart_tx_queue → UART_TX_Task → USART1
Fault_Task ──┘
```

### 6.1 发送队列消息结构

```c
#define UART_TX_MAX_LENGTH 64

typedef struct
{
    uint16_t length;
    uint8_t data[UART_TX_MAX_LENGTH];
} UartTxMsg_t;
```

结构体直接保存数组，而不是只保存一个指向局部数组的指针。队列会复制整条消息，因此生产者函数返回后数据仍然有效。

### 6.2 UART_TX_Task

```c
void UART_TX_Task(void *argument)
{
    UartTxMsg_t msg;

    for (;;)
    {
        if (osMessageQueueGet(
                uart_tx_queue,
                &msg,
                0,
                osWaitForever) != osOK)
        {
            continue;
        }

        if (msg.length == 0)
        {
            continue;
        }

        if (HAL_UART_Transmit(
                &huart1,
                msg.data,
                msg.length,
                100) != HAL_OK)
        {
            uart_tx_error_count++;
        }
    }
}
```

它的职责只有：

```text
等待消息
→ 取出一条
→ 发送一条
→ 再等待下一条
```

发送队列只能解决短时并发和统一排序，不能突破 UART 本身的带宽。如果生产速度长期大于发送速度，队列最终仍然会满。

## 7. 当前工程的两个简单发送封装

如果只想让 `UART_Task` 更容易阅读，而不增加新任务，可以封装普通函数。

### 7.1 发送亮度

```c
static HAL_StatusTypeDef VOFA_SendBrightness(float brightness)
{
    char buffer[32];
    int length;

    length = snprintf(
        buffer,
        sizeof(buffer),
        "%.3f\n",
        brightness
    );

    if (length < 0)
    {
        return HAL_ERROR;
    }

    if (length >= (int)sizeof(buffer))
    {
        length = sizeof(buffer) - 1;
    }

    return HAL_UART_Transmit(
        &huart1,
        (uint8_t *)buffer,
        (uint16_t)length,
        100
    );
}
```

### 7.2 发送参数日志

```c
static HAL_StatusTypeDef VOFA_SendLog(
    const BreathCmd_t *cmd)
{
    char buffer[64];
    int length;

    if (cmd == NULL)
    {
        return HAL_ERROR;
    }

    length = snprintf(
        buffer,
        sizeof(buffer),
        "Breath %s period=%ums\n",
        cmd->on_off ? "ON" : "OFF",
        cmd->period_ms
    );

    if (length < 0)
    {
        return HAL_ERROR;
    }

    if (length >= (int)sizeof(buffer))
    {
        length = sizeof(buffer) - 1;
    }

    return HAL_UART_Transmit(
        &huart1,
        (uint8_t *)buffer,
        (uint16_t)length,
        100
    );
}
```

`static` 表示函数只在当前 `.c` 文件中使用。`const BreathCmd_t *cmd` 表示传入结构体地址，函数只读取、不通过这个指针修改命令。

封装后，`UART_Task` 只需要表达业务意图：

```c
VOFA_SendLog(&cmd);
VOFA_SendBrightness(brightness);
```

## 8. UART_TX_Printf 与 C 可变参数

### 8.1 最初困难

为了让多个任务方便地向发送队列写入文本，讨论过：

```c
UART_TX_Printf("ID=0x%lX DLC=%u\n", id, dlc);
```

但它的实现涉及：

```c
va_list
va_start()
vsnprintf()
va_end()
```

这些知识对于当前阶段偏难。

### 8.2 它们分别是什么

函数声明中的：

```c
...
```

表示参数数量不固定。

```c
va_list args;
```

声明一个用于遍历可变参数的状态对象。

```c
va_start(args, format);
```

初始化 `args`，告诉它可变参数位于最后一个固定参数 `format` 后面。

```c
vsnprintf(buffer, size, format, args);
```

按照格式字符串读取 `args` 中的参数，并生成文本。

```c
va_end(args);
```

结束可变参数读取。它必须和 `va_start()` 成对使用。

典型顺序：

```c
va_list args;

va_start(args, format);
result = vsnprintf(buffer, size, format, args);
va_end(args);
```

### 8.3 当前学习结论

`UART_TX_Printf()` 是便利封装，不是使用 UART 发送队列的必要条件。当前阶段不需要为了发送队列强行学习和使用可变参数。

## 9. 不使用可变参数也能正确写入 uart_tx_queue

更适合当前阶段的接口是：

```c
osStatus_t UART_TX_PutData(
    const uint8_t *data,
    uint16_t length)
{
    UartTxMsg_t msg = {0};

    if (data == NULL ||
        length == 0 ||
        length > UART_TX_MAX_LENGTH)
    {
        return osErrorParameter;
    }

    msg.length = length;
    memcpy(msg.data, data, length);

    return osMessageQueuePut(
        uart_tx_queue,
        &msg,
        0,
        0
    );
}
```

然后将“格式化”和“入队”分成两步：

```c
char buffer[32];
int length;

length = snprintf(
    buffer,
    sizeof(buffer),
    "%.3f\n",
    brightness
);

if (length > 0 &&
    length < (int)sizeof(buffer))
{
    UART_TX_PutData(
        (uint8_t *)buffer,
        (uint16_t)length
    );
}
```

数据路径：

```text
snprintf 生成文本
→ UART_TX_PutData 复制到 UartTxMsg_t
→ osMessageQueuePut 再复制到队列
→ UART_TX_Task 取出并发送
```

局部数组 `buffer` 在函数返回后可以失效，因为队列中保存的是数据副本，不是该数组的地址。

## 10. snprintf 的返回值

`snprintf()` 返回 `int`，表示：

> 如果缓冲区足够大，原本需要写入多少个字符，不包含结尾的 `\0`。

例如：

```c
char buffer[32];

int result = snprintf(
    buffer,
    sizeof(buffer),
    "value=%u\n",
    123U
);
```

生成：

```text
value=123\n
```

一共 10 个字符，因此 `result == 10`，结尾的 `\0` 不计入返回值。

### 返回值判断

```c
result < 0
```

表示格式化失败。

```c
0 <= result && result < sizeof(buffer)
```

表示完整文本已经写入，可以发送 `result` 个字节。

```c
result >= sizeof(buffer)
```

表示目标数组太小，文本被截断。注意返回值仍然是“原本需要的长度”，不能直接将它作为当前数组的发送长度，否则可能越界读取。

安全用法：

```c
if (result > 0 &&
    result < (int)sizeof(buffer))
{
    UART_TX_PutData(
        (uint8_t *)buffer,
        (uint16_t)result
    );
}
```

## 11. 这轮讨论后的最终取舍

### 当前作业建议保留

```text
CAN_Task
→ vofa_tx_queue
→ UART_Task
→ HAL_UART_Transmit
→ VOFA
```

原因：

- 当前只有一个任务真正发送 USART1；
- 文本很短，阻塞时间有限；
- 没有多个发送者争抢 UART；
- 新建 UART_TX_Task 会增加不必要的队列和任务复杂度。

### 当前可做的轻量优化

1. 把亮度发送封装为 `VOFA_SendBrightness()`。
2. 把日志发送封装为 `VOFA_SendLog()`。
3. 检查 `snprintf()` 和 `HAL_UART_Transmit()` 返回值。
4. 验收画波时避免向同一串口混入普通日志。
5. 后续增强 CAN 消息结构时保存并检查 DLC、IDE、RTR。

### 暂时不必实现

1. 独立 `UART_TX_Task`。
2. `uart_tx_queue`。
3. `UART_TX_Printf()` 可变参数封装。
4. UART DMA 发送。
5. 完整 UART 环形缓冲区。
6. 第二个日志 UART。

这些不是无用知识，而是在程序规模、发送来源或数据量增加后再使用的工具。

## 12. 本轮形成的核心认识

### 关于“更高级”

DMA、环形缓冲区、独立发送任务和通用 `Printf` 接口并不是越多越好。工程设计需要先判断问题是否真实存在，再选择解决机制。

### 关于中断和任务边界

```text
中断：快速收数据、保存客观信息
任务：检查业务协议、执行耗时操作
```

### 关于队列

队列用于任务之间传递数据副本和吸收短时间并发，但不能提高 UART 或 CAN 的物理带宽。

### 关于封装

封装不一定要写成通用复杂函数。先写两个含义明确的普通函数，往往比一个难以理解的 `UART_TX_Printf()` 更适合当前阶段。

### 关于当前学习状态

已经能够理解和应用：

- 为什么检查 CAN DLC；
- Callback 和 CAN_Task 的职责边界；
- UART 是连续字节流；
- 阻塞、中断、DMA 发送的主要区别；
- 什么情况下需要 UART 发送队列；
- 普通函数封装；
- `snprintf()` 的基本用法和返回值。

目前只需要认识、尚不要求独立实现：

- C 可变参数；
- `va_list`、`va_start()`、`vsnprintf()`、`va_end()`；
- 完整环形缓冲区；
- DMA 发送队列状态机。

后续如果真实工程出现多任务发送、UART 高速数据流或队列丢包，再从对应部分继续学习和实施。
