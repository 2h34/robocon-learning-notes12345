# STM32 按键状态机作业实现记录

## 1. 作业要求

使用一个按键作为输入，设计一个 LED 状态机：

- 初始状态：4 个 LED 全灭；
- 长按：进入流水灯模式，使用 LED1、LED2；
- 短按：进入呼吸灯模式，使用 LED3、LED4；
- 状态真正发生切换时，蜂鸣器响一次；
- 按键默认状态为低电平，按下后为高电平；
- 输入引脚统一使用具有 RX 功能的引脚。

本次工程选择 **PC11** 作为按键输入引脚，并将其配置为 GPIO EXTI 输入。

---

## 2. 整体实现思路

整个程序按下面的层级组织：

```text
按键 / TIM2 / TIM3 / GPIO
        ↓
EXTI / Timer 中断与 HAL Callback
        ↓
KEY_SHORT / KEY_LONG
        ↓
状态机 current_state
        ↓
流水灯 / 呼吸灯 / 蜂鸣器
```

核心原则：

1. 中断尽量只做必要的信息采集和通知；
2. 状态切换、灯效更新等业务逻辑尽量放在主循环；
3. 使用 TIM2 提供统一的 2 ms 时间节拍；
4. 不使用 `HAL_Delay()` 实现蜂鸣器持续时间，避免阻塞主循环；
5. 状态进入时使用 `Enter()` 做一次初始化，状态运行期间使用 `Process()` 周期更新。

---

## 3. CubeMX 配置

### 3.1 按键输入 PC11

PC11 配置为：

```text
GPIO_EXTI11
Rising Edge + Falling Edge
Pull-down
```

按键逻辑：

```text
默认：低电平

按下：
0 → 1
→ 上升沿
→ 触发 EXTI

松开：
1 → 0
→ 下降沿
→ 再次触发 EXTI
```

因此一次完整的按键动作会触发两次中断：

```text
按下 → 一次中断
松开 → 一次中断
```

---

### 3.2 TIM2

TIM2 配置为周期中断，周期为：

```text
2 ms
```

因此：

```text
1 tick   = 2 ms
50 tick  = 100 ms
150 tick = 300 ms
```

TIM2 作为本程序统一的时间节拍，供以下任务使用：

- 蜂鸣器持续 100 ms；
- 流水灯每 300 ms 切换；
- 呼吸灯周期更新 PWM。

---

### 3.3 TIM3 PWM

LED3、LED4 使用 TIM3 PWM：

```text
LED3 → TIM3_CH1
LED4 → TIM3_CH2
ARR  = 999
```

PWM 比较值范围约为：

```text
0 ~ 999
```

PWM 值越大，占空比越大，LED 越亮。

---

### 3.4 普通 GPIO

```text
LED1 → PA4
LED2 → PA5
BEEP → PA8
```

LED1、LED2 使用普通 GPIO 控制。

LED3、LED4 已由 TIM3 PWM 接管，因此后续不能再按照普通 GPIO 灯的方式直接控制。

```c
typedef enum
```

含义：

```text
KEY_NONE   → 当前没有新的按键事件
KEY_SHORT  → 短按
KEY_LONG   → 长按
```

---

### 4.3 呼吸灯方向

```c
typedef enum

```

## 5. EXTI 按键中断处理

### 5.1 Callback 为什么要自己定义

HAL 内部已经提供：

```c
__weak void HAL_GPIO_EXTI_Callback(uint16_t GPIO_Pin)
{
    ...
}
```

这是一个弱定义。

我们在 `main.c` 中重新定义同名函数：

```c
void HAL_GPIO_EXTI_Callback(uint16_t GPIO_Pin)
{
    ...
}
```

链接阶段会优先采用用户提供的强定义。

需要注意：

```text
__weak 决定的是“最终采用哪个函数实现”
```

而不是：

```text
__weak 决定函数什么时候被调用
```

真正的调用链是：

```text
GPIO 电平边沿
↓
EXTI IRQ
↓
EXTI15_10_IRQHandler()
↓
HAL_GPIO_EXTI_IRQHandler()
↓
HAL_GPIO_EXTI_Callback()
```

---

### 5.2 为什么高电平时记录 press_time

本次按键设置为：

```text
默认低电平
按下高电平
```

因果顺序是：

```text
按键按下
↓
PC11 先发生 0 → 1
↓
EXTI 检测上升沿
↓
进入中断
↓
执行 Callback
↓
此时读取 PC11，通常已经是高电平
```

因此：

```c
if (pin_state == GPIO_PIN_SET)
{
    press_time = now;
}
```

表示记录按下时刻。

松开时：

```text
1 → 0
```

Callback 中读取到低电平，再计算持续时间。

---

## 6. 按键消抖与长短按判断

定义：

```c
#define KEY_DEBOUNCE_MS 20U
#define LONG_PRESS_MS   1000U
```

在 Callback 中使用：

```c
static uint32_t press_time = 0;
static uint32_t last_edge_time = 0;
```

这里使用 `static` 局部变量的原因：

- 它们只属于当前 Callback；
- 但函数退出后还要保存值；
- 下一次按键边沿进入 Callback 时还需要继续使用。

当前时间：

```c
uint32_t now = HAL_GetTick();
```

`now` 是普通局部变量，因为只在本次 Callback 执行中使用。

---

### 6.1 消抖逻辑

```text
now - last_edge_time < 20 ms
→ 认为是机械抖动
→ return

否则
→ 认为是有效边沿
→ last_edge_time = now
```

---

### 6.2 长短按判断

按下时：

```text
GPIO_PIN_SET
→ press_time = now
```

松开时：

```text
GPIO_PIN_RESET
→ duration = now - press_time
```

判断：

```text
duration < 1000 ms
→ KEY_SHORT

duration >= 1000 ms
→ KEY_LONG
```

最终只修改：

```c
key_event = KEY_SHORT;
```

或：

```c
key_event = KEY_LONG;
```

中断中不直接切换灯效。

---

## 7. 中断为什么只生成事件

本次程序采用：

```text
EXTI Callback
→ 负责识别短按 / 长按
→ 写 key_event
```

而：

```text
main()
→ 读取 key_event
→ 执行状态切换
→ 控制蜂鸣器
→ 调用对应灯效
```

这样可以让中断尽可能短。

需要明确：

> “中断只做少量工作”是本次软件架构选择，不是硬件中断机制本身强制要求。

---

## 8. key_event 为什么使用 volatile

```c
static volatile key_event_t key_event = KEY_NONE;
```

原因：

```text
EXTI Callback → 写 key_event
main()        → 读 key_event
```

它被中断和主程序共同访问，因此需要告诉编译器：

> 这个变量可能在当前代码之外被异步修改。

`volatile` 并不等于线程安全，也不等于自动保证所有并发访问安全，它主要解决编译器优化假设问题。

---

## 9. 状态机设计

当前状态：

```c
static led_state_t current_state = STATE_OFF;
```

初始状态：

```text
STATE_OFF
→ 4 个 LED 全灭
```

状态转换规则：

```text
短按
→ STATE_BREATH

长按
→ STATE_FLOW
```

当前三个已有状态规则相同，因此使用：

```c
switch (current_state)
{
    case STATE_OFF:
    case STATE_FLOW:
    case STATE_BREATH:
        if (key_event == KEY_SHORT)
        {
            current_state = STATE_BREATH;
        }
        else if (key_event == KEY_LONG)
        {
            current_state = STATE_FLOW;
        }
        break;

    default:
        break;
}
```

保留 `switch` 的原因：

> 后续如果增加新的状态，而且新的状态转换逻辑不同，可以单独添加新的 `case`，不必重构整体框架。

---

## 10. old_state 的作用

状态处理前先保存：

```c
led_state_t old_state = current_state;
```

处理事件后比较：

```c
if (current_state != old_state)
{
    ...
}
```

目的：

> 判断是否真正发生了状态切换。

例如：

```text
当前 FLOW
再次长按
→ FLOW → FLOW
```

状态没有变化，因此：

- 蜂鸣器不响；
- 流水灯不重新初始化。

而：

```text
FLOW → BREATH
```

才是真正的状态切换。

处理完事件后：

```c
key_event = KEY_NONE;
```

表示这次事件已经被消费。

否则主循环会不断重复处理同一个 `KEY_SHORT` 或 `KEY_LONG`。

---

## 11. TIM2 统一时间节拍

在 `main.c`：

```c
static volatile uint32_t tick_2ms_count = 0;
```

TIM2 每 2 ms 中断一次：

```c
if (htim->Instance == TIM2)
{
    tick_2ms_count++;
}
```

注意工程中 TIM1 已经作为 HAL Timebase，因此不能再重新定义一个新的：

```c
HAL_TIM_PeriodElapsedCallback()
```

而应该在 CubeMX 已有 Callback 内通过：

```c
htim->Instance
```

区分 TIM1 与 TIM2。

调用关系：

```text
TIM2 CNT 到 ARR
↓
Update Event
↓
TIM2 IRQ
↓
TIM2_IRQHandler()
↓
HAL_TIM_IRQHandler(&htim2)
↓
HAL_TIM_PeriodElapsedCallback(&htim2)
↓
tick_2ms_count++
```

---

## 12. 蜂鸣器模块

蜂鸣器 GPIO 已经由 CubeMX 的：

```c
MX_GPIO_Init();
```

初始化，因此不需要在 `beep.c` 中再次配置 PA8。

最基本的控制：

```c
void BEEP_ON(void)
{
    HAL_GPIO_WritePin(BEEP_GPIO_Port, BEEP_Pin, GPIO_PIN_SET);
}

void BEEP_OFF(void)
{
    HAL_GPIO_WritePin(BEEP_GPIO_Port, BEEP_Pin, GPIO_PIN_RESET);
}
```

---

### 12.1 为什么不用 HAL_Delay

如果写：

```c
BEEP_ON();
HAL_Delay(100);
BEEP_OFF();
```

主循环会被阻塞 100 ms。

这会影响：

- 流水灯周期更新；
- 呼吸灯 PWM 更新；
- 其他主循环任务。

因此采用 TIM2 tick 做非阻塞计时。

---

### 12.2 BEEP_Trigger

模块内部变量：

```c
static uint8_t beep_active = 0;
static uint32_t beep_start_tick = 0;
```

触发蜂鸣器时：

```c
void BEEP_Trigger(uint32_t current_tick)
{
    BEEP_ON();
    beep_start_tick = current_tick;
    beep_active = 1;
}
```

---

### 12.3 BEEP_Process

定义：

```c
#define BEEP_DURATION_TICKS 50U
```

因为：

```text
50 × 2 ms = 100 ms
```

主循环不断调用：

```c
void BEEP_Process(uint32_t current_tick)
{
    if (beep_active &&
        (current_tick - beep_start_tick >= BEEP_DURATION_TICKS))
    {
        BEEP_OFF();
        beep_active = 0;
    }
}
```

这样蜂鸣器可以非阻塞地响约 100 ms。

---

## 13. 流水灯模块

### 13.1 内部变量

放在 `led.c` 文件作用域：

```c
static uint8_t flow_led_index = 0;
static uint32_t flow_last_switch_tick = 0;
```

它们需要同时被：

```text
LED_FlowEnter()
LED_FlowProcess()
```

访问，因此不能做某一个函数的普通局部变量。

---

### 13.2 LED_FlowEnter

进入流水灯状态时：

1. 关闭 LED3、LED4 PWM；
2. LED1 亮；
3. LED2 灭；
4. 记录当前亮的是 LED1；
5. 从当前 tick 重新开始计时。

核心：

```c
void LED_FlowEnter(uint32_t current_tick)
{
    __HAL_TIM_SET_COMPARE(&htim3, TIM_CHANNEL_1, 0);
    __HAL_TIM_SET_COMPARE(&htim3, TIM_CHANNEL_2, 0);

    LED_ON(1);
    LED_OFF(2);

    flow_led_index = 0;
    flow_last_switch_tick = current_tick;
}
```

---

### 13.3 为什么进入 FLOW 时必须清 TIM3 CCR

之前如果处于呼吸灯状态：

```text
CCR1 = 600
CCR2 = 399
```

即使之后不再调用 `LED_BreathProcess()`：

```text
不再更新 PWM
≠
PWM 自动停止
```

TIM3 硬件仍然会根据原来的 CCR 持续输出 PWM。

因此进入 FLOW 时必须主动：

```c
CCR1 = 0;
CCR2 = 0;
```

这说明：

> 函数调用结束，不等于它启动或配置的硬件任务自动结束。

---

### 13.4 LED_FlowProcess

流水灯要求：

```text
LED1 / LED2 每 300 ms 交替
```

对应：

```text
300 ms ÷ 2 ms = 150 tick
```

判断：

```c
if (current_tick - flow_last_switch_tick < 150U)
{
    return;
}
```

达到 150 tick 后：

```text
当前 LED1 亮
→ LED1 灭
→ LED2 亮
→ index = 1

当前 LED2 亮
→ LED2 灭
→ LED1 亮
→ index = 0
```

并重新记录：

```c
flow_last_switch_tick = current_tick;
```

---

## 14. 呼吸灯模块

### 14.1 内部状态

放在 `led.c`：

```c
static uint16_t breath_value = 0;
static breath_state_t breath_state = BREATH_UP;
static uint32_t breath_last_tick = 0;
```

---

### 14.2 LED_BreathEnter

进入呼吸灯状态时：

```text
LED1、LED2 → 关闭

breath_value = 0
breath_state = BREATH_UP
breath_last_tick = current_tick

CH1 = breath_value
CH2 = 999 - breath_value
```

因此初始：

```text
LED3 较暗
LED4 较亮
```

---

### 14.3 LED_BreathProcess

每检测到新的 TIM2 tick：

```text
BREATH_UP：
0 → 1 → 2 → ... → 999

到达 999
→ breath_state = BREATH_DOWN

BREATH_DOWN：
999 → 998 → ... → 0

到达 0
→ breath_state = BREATH_UP
```

然后设置：

```c
__HAL_TIM_SET_COMPARE(&htim3, TIM_CHANNEL_1, breath_value);
__HAL_TIM_SET_COMPARE(&htim3, TIM_CHANNEL_2, 999U - breath_value);
```

因此形成：

```text
LED3 逐渐变亮
LED4 逐渐变暗
↓
达到端点
↓
LED3 逐渐变暗
LED4 逐渐变亮
```

当前代码采用：

```text
每 2 ms 改变 1
```

所以：

```text
0 → 999
约 2 s

完整 0 → 999 → 0
约 4 s
```

呼吸效果较慢，但变化比较细腻。

---

## 15. Enter 和 Process 的区别

这是本次程序结构中非常重要的一点。

### Enter

只在刚刚进入某个状态时执行一次：

```text
LED_FlowEnter()
LED_BreathEnter()
```

负责：

- 清理上一个状态留下来的输出；
- 设置新状态初值；
- 重置内部计时。

---

### Process

处于该状态期间由主循环不断调用：

```text
LED_FlowProcess()
LED_BreathProcess()
BEEP_Process()
```

负责：

- 检查时间是否到；
- 更新灯效；
- 完成非阻塞任务。

不能把 `Enter()` 放在 `while(1)` 中无条件重复调用，否则计时会不断重置，永远达不到下一次更新时间。

---

## 16. main 主循环结构

最终主循环逻辑：

```text
while(1)
│
├─ StateMachine_Process()
│   └─ 消费 KEY_SHORT / KEY_LONG
│      修改 current_state
│
├─ BEEP_Process()
│   └─ 非阻塞控制蜂鸣器关闭
│
├─ current_state == STATE_FLOW
│   └─ LED_FlowProcess()
│
└─ current_state == STATE_BREATH
    └─ LED_BreathProcess()
```

状态真正变化时：

```text
current_state != old_state
│
├─ BEEP_Trigger()
│
├─ 新状态为 FLOW
│   └─ LED_FlowEnter()
│
└─ 新状态为 BREATH
    └─ LED_BreathEnter()
```

## 18. 实现过程中出现的问题与修正

### 18.1 按键电平判断写反

最初写成：

```c
if (pin_state == GPIO_PIN_RESET)
{
    // 按下
}
```

但本题明确：

```text
默认低电平
按下高电平
```

因此正确判断应该是：

```c
if (pin_state == GPIO_PIN_SET)
{
    // 按下
}
```

---

### 18.2 长按边界判断

最初使用：

```c
duration > LONG_PRESS_MS
```

后修正为：

```c
duration >= LONG_PRESS_MS
```

因为恰好达到 1000 ms 也应该属于长按。

---

### 18.3 状态转换方向写反

最初将：

```text
短按 → FLOW
长按 → BREATH
```

写反。

题目正确要求：

```text
短按 → BREATH
长按 → FLOW
```

修正后再继续状态机设计。

---

### 18.4 状态机代码过于重复

最初为三个状态分别写一套：

```c
case STATE_OFF:
case STATE_FLOW:
case STATE_BREATH:
```

后来发现当前三个状态的事件规则相同，因此采用多个 `case` 共享一套代码。

同时保留 `switch`，为未来新增具有不同转换规则的状态保留扩展空间。

---

### 18.5 LED_FlowEnter / LED_FlowProcess 隐式声明警告

编译出现：

```text
implicit declaration of function 'LED_FlowProcess'
implicit declaration of function 'LED_FlowEnter'
```

原因：

`main.c` 调用了 `led.c` 中的函数，但编译 `main.c` 时编译器还没有看到函数声明。

解决：

在 `led.h` 中声明：

```c
void LED_FlowEnter(uint32_t current_tick);
void LED_FlowProcess(uint32_t current_tick);
```

并在 `main.c` 中：

```c
#include "led.h"
```

重新编译后 warning 消失。

---

### 18.6 呼吸灯函数声明与定义不一致

编译出现：

```text
conflicting types for 'LED_BreathProcess'
too many arguments to function call
```

原因：

`led.h` 仍然写：

```c
void LED_BreathEnter(void);
void LED_BreathProcess(void);
```

而 `led.c` 已修改为：

```c
void LED_BreathEnter(uint32_t current_tick);
void LED_BreathProcess(uint32_t current_tick);
```

头文件声明没有同步更新。

修正为：

```c
void LED_BreathEnter(uint32_t current_tick);
void LED_BreathProcess(uint32_t current_tick);
```

之后编译恢复正常。

---

### 18.7 呼吸灯两个通道初值相同

最初写：

```c
CH1 = breath_value;
CH2 = breath_value;
```

这样 LED3、LED4 会同向变化。

作业设计要求反向呼吸，因此修改为：

```c
CH1 = breath_value;
CH2 = 999 - breath_value;
```

---

### 18.8 不再执行呼吸函数不代表 PWM 自动停止

一开始容易认为：

```text
不调用 LED_BreathProcess()
→ LED3 / LED4 自动熄灭
```

后来明确：

TIM3 PWM 是硬件独立运行的。

因此必须在 `LED_FlowEnter()` 主动：

```c
__HAL_TIM_SET_COMPARE(&htim3, TIM_CHANNEL_1, 0);
__HAL_TIM_SET_COMPARE(&htim3, TIM_CHANNEL_2, 0);
```

清除之前留下的 PWM 输出。

## 21. 当前实现的一个边界

目前长按是在：

```text
按住 ≥ 1000 ms
↓
松开
↓
下降沿 Callback
↓
计算持续时间
↓
识别为 KEY_LONG
```

所以当前行为是：

> **长按达到 1 s 后，需要松开按键才会切换到流水灯。**

不是：

> 按住达到 1 s 的瞬间立即切换。

这是当前软件设计选择，不是 EXTI 或硬件本身的限制。

## 22. 本次作业最值得记住的知识

### 1. 中断触发的因果顺序

```text
电平先发生变化
→ EXTI 检测到边沿
→ 才进入中断
→ 最后才执行 Callback
```

---

### 2. `__weak` 的作用

```text
HAL Handler
→ 决定什么时候调用 Callback

__weak
→ 决定最终使用默认实现还是用户实现
```

---

### 3. 函数调用结束不等于硬件任务结束

```text
HAL_TIM_PWM_Start() 返回
≠ PWM 停止

LED_BreathProcess() 不再执行
≠ TIM3 PWM 自动归零
```

硬件定时器会继续独立工作，直到重新配置或停止。

---

### 4. 中断与业务逻辑要分层

本次采用：

```text
中断
→ 产生事件 / 更新时间基准

main
→ 状态切换 / 灯效 / 蜂鸣器
```

这样结构更容易理解和维护。

---

### 5. `Enter()` 和 `Process()` 分开

```text
Enter()
→ 状态刚进入时执行一次

Process()
→ 状态持续期间不断执行
```

这种结构后续可以继续扩展到：

- 电机模式；
- 通信状态；
- 机器人自动 / 手动状态；
- 多任务调度等。
